# Как устроена платформа

Платформа помогает повторно использовать запуск, состояния экранов, покупки и готовые пользовательские сценарии. **Приложение задаёт свой продукт; библиотеки выполняют общую работу.** Разобраться в архитектуре — значит понимать, где хранить настройку, кто выполняет действие и в каком репозитории исправлять ошибку.

Начнём с уже работающего [BroadStart](./getting-started.md), затем посмотрим, что добавляется в приложении с подпиской. Для чтения не требуется знать Clean Architecture или названия слоёв заранее.

## Две карты, которые нельзя смешивать

У платформы есть **библиотеки** — то, что Xcode подключает к приложению. Внутри библиотеки и приложения есть **слои кода** — способ разделить ответственность. Это разные разрезы: BroadCore не является «всем Domain», а BroadUIFlows — «всем UI» вашего приложения.

| Библиотека | Какую работу берёт | Что остаётся у приложения |
|---|---|---|
| [BroadCore](./broad-core.md) | Запуск шагов, состояния загрузки, кеш, ограниченные повторы, безопасные ошибки и адаптер ATT | Какие шаги запускать, какие данные хранить, как показать результат |
| [BroadExtensions](./broad-extensions.md) | Небольшие функции для цвета, шрифтов, клавиатуры и навигации | Дизайн и выбор мест, где применять утилиты |
| [BroadMonetization](./broad-monetization.md) | Каталог paywall, покупка, восстановление, проверка доступа, RU Billing | Ключи SDK, placements, backend-контракт, учётная запись и правила продукта |
| [BroadUIFlows](./broad-ui-flows.md) | Готовые экраны и общие переходы onboarding, paywall и AppFlow | Тексты, изображения, тема, конфигурация и собственные экраны |

Отдельно существуют [интеграционный репозиторий](https://github.com/BroadApps-official/broad-platform-integration) с проверенным набором версий и примерами и [репозиторий сайта](https://github.com/BroadApps-official/broad-docs) с инструкциями. Их не добавляют как библиотеку в app target.

## Какие зависимости действительно появятся

Внешняя зависимость — библиотека, которую модуль использует для своей работы. Xcode прочитает её адрес и правило версии из `Package.swift`.

| Выбранный пакет | Прямые зависимости по его Package.swift |
|---|---|
| BroadExtensions | Нет внешних пакетов |
| BroadCore | Swinject — инструмент сборки зависимостей |
| BroadMonetization | BroadCore, Adapty, Swinject |
| BroadUIFlows | BroadCore, BroadMonetization, Swinject |

Таким образом, **даже для одного onboarding пакет BroadUIFlows сейчас приводит Adapty через BroadMonetization**. Возможности можно не использовать, но они остаются зависимостями пакета. Если нужны только свои экраны и состояние списка, как в BroadStart, достаточно Core и Extensions.

Скачивание зависимости и доступ к ней из кода приложения — разные вещи. Если Swift-файл приложения содержит `import BroadCore`, добавьте product BroadCore в тот target, который компилирует этот файл. Даже если сам пакет Core уже скачан через UIFlows. Если библиотека нужна только внутреннему коду UIFlows, отдельный прямой import приложению не нужен.

[Практические наборы модулей](./module-selection.md) и [проверенные версии](./compatibility.md) объясняют настройку Xcode отдельно. Здесь важно понять направление: Core не зависит от Monetization или UIFlows; Extensions независим от остальных частей платформы.

## Одно действие в BroadStart: открыть список

В [исходниках BroadStart](https://github.com/BroadApps-official/broad-docs/tree/main/examples/first-app/Sources) пять небольших Swift-файлов. Проследите действие от кнопки до результата:

```text
LessonListView        человек нажал «Повторить»
       ↓
LessonListModel       сразу включает загрузку и запрещает второй запрос
       ↓
LoadLessonsUseCase    запрашивает материалы через договорённый интерфейс
       ↓
LessonRepository     обещает вернуть список или ошибку
       ↓
DemoLessonRepository возвращает учебные данные
       ↓
LessonListModel       выбирает loaded / empty / error / stale
       ↓
LessonListView        показывает состояние
```

`LessonRepository` — протокол, то есть описание доступной операции. `DemoLessonRepository` — конкретная реализация этого протокола. В готовом примере данные локальные. Чтобы подключить настоящий сервер, приложение создаёт другую реализацию, передаёт её при запуске и сохраняет тот же договор со сценарием загрузки.

Общий тип `LoadableState` взят из Core. Модель материала, содержимое списка и его загрузчик принадлежат BroadStart. Платформе не нужно знать, что именно продаёт или показывает конкретное приложение.

## Что означают слои на практике

| Слой | За что отвечает | Пример | Что сюда не помещать |
|---|---|---|---|
| Presentation — представление | Показывает данные и преобразует действия человека в вызовы | SwiftUI View и ViewModel со состоянием загрузки | Создание SDK, HTTP-запрос из `body`, разбор JSON |
| Application — сценарии | Выполняет действие и согласует несколько участников | «Загрузить материалы», «купить выбранный продукт» | Цвет кнопки или расположение карточек |
| Domain — правила и договоры | Описывает данные, допустимые результаты и интерфейсы | Модель продукта, статус доступа, протокол repository | Типы Adapty, URLSession, SwiftUI |
| Data — работа с данными | Получает, сохраняет и преобразует данные по договору | Repository, объединяющий сервер и кеш | Решение, какой экран нарисовать |
| Infrastructure — внешние системы | Изолирует конкретный SDK, сеть и хранилище | Адаптер Adapty, HTTP transport, системный ATT | Продуктовые правила отдельного экрана |

В маленьком BroadStart некоторые связанные объявления находятся в одном файле. Пять отдельных каталогов не обязательны для пяти типов. Важна зависимость: сценарий знает протокол, а конкретный сетевой клиент можно заменить, не переписывая экран.

**MVVM** описывает пару View + ViewModel: экран отображает состояние, модель представления управляет им. **Clean Architecture** направляет зависимости к правилам и протоколам. **SOLID** помогает удерживать небольшие обязанности и заменяемые реализации. Это не требование создать дополнительный класс для каждой строки кода. [Определения с примерами](./glossary.md).

## Где создать и связать объекты

Место, в котором приложение создаёт свои зависимости, называют **composition root — точка сборки зависимостей**. Обычно это код рядом с запуском приложения. В BroadStart он находится в [BroadStartApp.swift](https://github.com/BroadApps-official/broad-docs/blob/main/examples/first-app/Sources/BroadStartApp.swift).

Порядок простой: repository → use case → ViewModel → View. Долгоживущая ViewModel сохраняется как `StateObject`, поэтому пересчёт SwiftUI `body` не создаёт новый загрузчик и новую сессию.

В большом приложении эту работу могут выполнять сборки Swinject: Core, затем Monetization, затем UIFlows и собственные объекты приложения. Создаются только используемые сборки. Прямые initializer-вызовы тоже подходят: BroadStart обходится ими.

Не вызывайте `resolve` из View и не передавайте контейнер Swinject внутрь `Task`. Асинхронная операция получает уже созданную безопасную зависимость. Один общий сервис оплаты и один координатор запуска должны жить столько, сколько требуется всему приложению, а не одному пересозданному экрану.

## Что меняется, когда появляется оплата

Экран передаёт в сценарий **именно выбранный продукт**. Monetization связывает его с исходным продуктом провайдера, запускает операцию и отдельно проверяет право на доступ. UIFlows отображает результат; AppFlow решает переход.

| Событие | Что оно означает | Чего из него нельзя заключить |
|---|---|---|
| Каталог загрузился | Есть варианты для отображения | Пользователь что-то купил |
| Пользователь выбрал карточку | Изменился выбор на экране | Запущена покупка |
| Закрыл paywall | Можно продолжить разрешённый маршрут без покупки | Premium активен |
| Вернулся из банка | Приложение снова активно и может проверить операцию | Платёж уже подтверждён |
| Проверка доступа вернула active | Можно открыть подтверждённые возможности | Любой флаг Remote Config может выдать такой же доступ |

Каталог не обрезается до двух карточек, одинаковые SKU не объединяются. Общая логика принимает все продукты в порядке провайдера. Для RU Billing есть отдельный backend-каталог и отдельная проверка платежа. При недоступном Adapty явно подключённый резерв загружает этот каталог, если Storefront или регион телефона RU/RUS; полученный `ru_pay=false` остаётся запретом. Этот каталог нельзя подменять списком продуктов Apple. [Оплата](./broad-monetization.md) · [RU Billing](./ru-billing.md).

## В каком месте исправлять проблему

| Наблюдение | Где начать | Что проверить перед изменением |
|---|---|---|
| Не тот текст, изображение или placement | Приложение | Его конфигурацию и исходные требования |
| Кнопка дважды запускает запрос | ViewModel приложения или готового экрана | Загрузка включается до `Task`? Общий сервис не создан дважды? |
| Один app неправильно разбирает JSON своего сервера | Repository/decoder приложения | Совпадает ли код с backend-контрактом |
| Общий механизм timeout теряет результат | Core | Контракт шага, отмену и поведение позднего ответа |
| Общая покупка теряет выбранный продукт | Monetization | Полный список, исходную позицию и registry провайдера |
| Готовый onboarding неверно переходит на следующий слайд | UIFlows | Конфигурацию страниц и общую логику перехода |
| В статьях описаны разные правила | broad-docs и документация владельца API | Какая выпущенная версия фактически реализует поведение |

Сначала воспроизведите проблему и найдите владельца. Не переносите файл библиотеки в приложение ради быстрого исправления: локальная копия продолжит работать отдельно после следующего обновления пакета.

## Как менять платформу без сюрпризов для приложений

Новую необязательную возможность добавляют так, чтобы прежние initializer-вызовы, значения по умолчанию и отключённый сценарий продолжали работать. Пример — дополнительные настройки RU A/B: само обновление библиотеки не должно включать эксперимент или менять существующую оплату.

Если старое поведение действительно меняется, это оформляется как несовместимость: новая major-версия, инструкция перехода и проверка зависимых модулей. Даже исправление без изменения сигнатуры может изменить поведение, поэтому одного успешного compile недостаточно.

Практическая проверка архитектуры: можно ли заменить источник данных через протокол, собрать приложение без ненужных функций и найти одного владельца каждого действия? Если да, разделение помогает работе. Если одна кнопка создаёт SDK, читает JSON и сама выдаёт Premium, границы надо исправить.
