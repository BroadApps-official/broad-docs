# Как устроена платформа

BroadApps iOS — четыре библиотеки общего кода, интеграционный репозиторий для
проверки версий и этот сайт с инструкциями. В приложение попадают только
выбранные библиотеки.

## Общая схема

```text
Ваше iPhone-приложение
 ├─ BroadExtensions                         независимые Swift-утилиты
 ├─ BroadCore                               запуск, кеш и логи
 ├─ BroadMonetization ────────────────────→ BroadCore
 └─ BroadUIFlows ─────→ BroadMonetization → BroadCore

 broad-platform-integration   проверяет версии вместе, но не входит в приложение
 broad-docs                   хранит общие инструкции, но не входит в приложение
```

Например, если добавить `BroadUIFlows`, Xcode сам загрузит
`BroadMonetization`, `BroadCore`, Adapty и Swinject. Добавлять их повторно не
нужно, пока код приложения не импортирует их API напрямую.

## Зачем делить на четыре модуля

- Приложение не получает ненужные SDK и экраны.
- Изменение видно в небольшом репозитории конкретного владельца.
- Исправление одного модуля можно выпустить без новой версии всей платформы.
- Проверенные сочетания версий записаны в одном каталоге.
- README и DocC конкретной версии остаются рядом с её кодом.
- Старое приложение можно переводить безопасными проверяемыми шагами.

## Кто за что отвечает

| Место | Что там должно находиться | Чего там быть не должно |
|---|---|---|
| Репозиторий модуля | Общий Swift-код, README, DocC, история изменений и версия | Ключи, тексты и изображения одного приложения |
| `broad-platform-integration` | Проверенные версии, пример их совместной сборки и общая автоматическая проверка | Код, который приложение обязано подключить |
| `broad-docs` и сайт | Общие объяснения, поиск и ссылки на точный источник | Единственная копия API конкретной версии |
| Репозиторий приложения | Ключи, Bundle ID, placement, backend, тексты, изображения и продуктовые правила | Копии общего кода платформы |

У каждого значения должен быть один понятный владелец. Если один и тот же код
скопирован в приложение и одновременно подключён как package, Xcode получает
две версии одного модуля и сборка становится непредсказуемой.

## Границы внутри модуля

```text
Экран → пользовательское действие → бизнес-правило
                                  ↓
                         данные → внешний сервис
```

- SwiftUI-экран не обращается к Adapty или backend напрямую.
- Внешние модели SDK переводятся в модели платформы через adapter.
- Бизнес-правило не зависит от конкретного UI.
- Ключи, токены и сырые ошибки внешнего сервиса не попадают в логи.
- Тексты, изображения и решения продукта приходят из приложения.

Такие границы позволяют заменить экран или внешний SDK, не переписывая весь
сценарий.

## Если изменение касается нескольких модулей

Сначала изменяется самый нижний модуль, владеющий нужным API. Затем повторно
проверяются зависящие от него модули, интеграционный пример и документация.
Новая версия зависимого модуля нужна только тогда, когда ему действительно
требуется новое API или меняется его публичное поведение.
