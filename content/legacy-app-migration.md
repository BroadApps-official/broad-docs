# Переход со старого BroadCore

Эта инструкция предназначена для работающего приложения со старым BroadCore, локальными пакетами или скопированными Swift-файлами платформы. Цель — подключить актуальные публичные модули, сохранив нужные функции приложения и понятный путь возврата.

Миграция зависимостей не является поводом заново рисовать экраны или менять серверный контракт. Если новый API требует изменения реализации, запишите его отдельно и проверьте прежнее поведение.

## Зафиксируйте рабочее состояние

Перед изменениями соберите Debug и Release, запустите приложение и пройдите затрагиваемые сценарии. Запишите коммит и фактические ограничения: ошибка, существовавшая до миграции, не должна внезапно считаться результатом нового подключения.

```bash
git status --short
git rev-parse HEAD
```

Первая команда показывает незаписанные изменения, вторая — идентификатор текущего коммита. Если изменения есть, сохраните их отдельно и проверьте содержимое. Не выполняйте `reset --hard` или очистку папки, чтобы получить «чистый» старт.

Создайте отдельную ветку для миграции. В `Documentation/AppIntegrationPlan.md` запишите исходные зависимости, используемые функции, целевые версии и порядок проверки. Это план приложения; в общую платформу его переносить не нужно.

## Найдите все способы старого подключения

В Xcode проверьте **Project → Package Dependencies**, список **Frameworks, Libraries, and Embedded Content**, **Build Phases → Compile Sources** и добавленные локальные пакеты. Если приложение использует CocoaPods, посмотрите также Podfile и открываемый workspace.

Для поиска в Terminal запустите из корня приложения:

```bash
rg -n 'BroadApps-official/BroadCore|XCLocalSwiftPackageReference|XCRemoteSwiftPackageReference' \
  -g project.pbxproj -g Package.swift -g Package.resolved -g '!Pods/**'
rg -n 'import Broad(Core|Extensions|Monetization|UIFlows)' \
  -g '*.swift' -g '!Pods/**' -g '!.build/**'
```

Команды только читают файлы. Отсутствие совпадений не доказывает отсутствие скопированного кода: переименованные классы и встроенные файлы нужно сопоставить с реальной сборкой.

| Что нашли | Что записать |
|---|---|
| Старый GitHub URL | URL, версия или коммит, предоставляемые products |
| Локальный Swift Package | Путь и target, который его использует |
| Скопированные Swift-файлы | Какие входят в Compile Sources и чем отличаются от общего кода |
| Собственная обёртка | Публичные методы, которые вызывает приложение, и прежнее поведение |
| Несколько способов сразу | Где могут появиться одинаковые модули или реализации |

## Сопоставьте функции с новой платформой

Заполните таблицу именно по вашему коду. Не подставляйте предполагаемые названия новых классов вместо проверки деклараций.

| Используемая область | Целевой модуль | Что сравнить |
|---|---|---|
| Запуск, кеш, состояния и ошибки | BroadCore | Порядок запуска, ограничения ожидания, правила устаревших данных |
| Утилиты интерфейса | BroadExtensions | Сигнатуры, формат цвета, поведение навигации |
| Покупка и подтверждённый доступ | BroadMonetization | Источник продуктов, обработку отмены, pending и восстановления |
| Onboarding и paywall | BroadUIFlows | Число страниц, ATT, момент показа и закрытия, собственный дизайн |
| Запросы и бизнес-правила конкретного приложения | Код приложения | Поля, параметры и действия backend; платформа не угадывает их |

Адреса и распределение функций: [куда переехал BroadCore](./legacy-broadcore.md). Версии берите из [каталога совместимости](./compatibility.md); на время перехода фиксируйте exact-версии и Package.resolved.

## Определите, что переключать вместе

Нельзя допускать, чтобы старая и новая зависимости одновременно предоставляли одно и то же имя Swift-модуля. При этом не все зависимости приложения обязаны меняться одним большим шагом.

| Как устроен старый код | Безопасная единица изменения |
|---|---|
| Один пакет предоставляет Core, оплату и экраны | Удаление старой ссылки и добавление всех реально используемых замен — одним изменением |
| Модули независимы и не пересекаются | Можно переключать по одному |
| Файлы встроены прямо в app target | Добавление product и исключение совпадающих файлов из сборки — согласованно |
| Перед платформой стоит своя обёртка | Сохранить интерфейс обёртки, заменить внутреннюю реализацию и проверить вызовы |

Например, если приложение импортирует Core и Monetization из одного старого пакета, замена только Core может оставить конфликт. Сначала установите состав пакета, затем определите минимальную группу замены. Не выбирайте её по одному сообщению компилятора.

## Выполните одно переключение

1. Проверьте, что рабочий коммит и незаписанные изменения сохранены.
2. В той же группе отключите подтверждённые старые package references и подключите новые публичные URL.
3. Добавьте products для всех прямых `import` приложения; автоматически скачанный пакет не заменяет product в target.
4. Исправьте только несовместимые вызовы API и сохраните изменения, принадлежавшие приложению.
5. Выберите **File → Packages → Resolve Package Versions** и проверьте получившийся Package.resolved.
6. Соберите Debug, Release для Simulator и iphoneos без подписи.
7. Пройдите один затронутый пользовательский путь целиком, затем остальные пути этой группы.

![Ожидаемый вид актуального подключения: products в target и публичные пакеты слева; показан учебный BroadStart](../public/guides/start/xcode-target.png)

Скриншот показывает конечную форму настройки. Это не снимок миграции вашего приложения; его состав products определяется предыдущим аудитом.

## Проверьте сохранение поведения

| Область | Что должно остаться правильным |
|---|---|
| Запуск | Первый экран появляется; ошибка и отсутствие сети не дают вечный loader |
| Onboarding | Согласованные страницы и порядок; ATT после видимого первого слайда, Rate Us вне onboarding |
| Обычный paywall | Все продукты в исходном порядке, включая одинаковые SKU; выбор не мигает |
| Special Offer | Опционален; открывается только по правилам после закрытия обычного paywall |
| Финансовые операции | Доступ только после подтверждения; неизвестный результат остаётся pending |
| Повторные нажатия | Кнопка блокируется до первого await; дубликат операции не запускается |
| RU Billing | Свежий разрешающий `ru_pay`, Storefront RU или регион iPhone RU, проверенный backend-контракт |
| RU Billing A/B | Подключается явно; отсутствие tracker сохраняет прежний сценарий |
| Поддержка | Чат или письмо открываются действием пользователя, возврат работает |
| Перезапуск | Незавершённые операции и состояние аккаунта не подменяются локальным «успехом» |

Покупки, restore и RU-платежи в автоматической проверке не выполняются по-настоящему. Для проверки этих веток используйте согласованные локальные ответы и сверку контракта; не запускайте финансовую операцию ради видео или зелёного отчёта.

## Если результат не совпал

Сохраните конкретную ошибку и сценарий её воспроизведения. Возвращайте согласованную группу изменений целиком: старые зависимости, их версии, Package.resolved и связанные адаптеры. Не смешивайте половину старой группы с половиной новой.

Если изменение уже оформлено отдельным коммитом миграции, его можно отменить отдельным `git revert` после просмотра diff. Не используйте массовое удаление файлов и не откатывайте чужие изменения. После возврата повторите исходную сборку и сценарий.

## Работа с Codex или Claude

Откройте **Repository приложения** — репозиторий самого приложения. [broad-platform-integration](https://github.com/BroadApps-official/broad-platform-integration) и старый исходник нужны агенту для чтения. Готовая подробная инструкция: [LegacyAppMigrationAgent.md](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Documentation/LegacyAppMigrationAgent.md).

Агент сначала читает зависимости, показывает сопоставление функций и план. После подтверждения переключает одну группу, проверяет её сценарии и возвращает результат разработчику. Если нет актуального каталога или подтверждённого соответствия, он сообщает **APP MIGRATION · BLOCKED** с конкретным недостающим источником.

Если план уже существует, агент **не перезаписывает его пустым** шаблоном: сохраняет решения и дополняет изменившиеся сведения. После паузы перечитывает план, последний принятый этап и diff, затем продолжает незавершённую группу.

### Как читать поля плана

| Поле | Что записать |
|---|---|
| `platform_set` | Номер проверенного сочетания версий |
| `Cutover topology` | Как подключена старая платформа: пакет, локальная папка, файлы, обёртка |
| `Legacy owner` | Точная старая ссылка или расположение кода |
| `Conflicting targets` | Какие имена модулей столкнутся при двойном подключении |
| `Atomic cutover group` | Минимальная группа удалений и добавлений, выполняемая вместе |
| `Runtime slices after cutover` | Какие пользовательские пути подтвердят сохранение поведения |

## Когда переход закончен

В сборке остались только согласованные источники; прямые imports обеспечены products; версии зафиксированы; изменения приложения сохранены; затронутые сценарии приняты. Старые файлы удаляются окончательно только после сравнения и проверки, а не потому, что новый пакет скачался.

Передайте QA коммит, версии, список проверенных путей и ограничения. Успешный общий platform gate не заменяет проверку конкретного приложения.
