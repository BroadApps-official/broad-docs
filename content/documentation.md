# Как исправлять документацию

У документации три уровня. Каждый отвечает на свой вопрос и все остаются в
публичных репозиториях.

## Где должна лежать информация

| Вопрос | Правильное место |
|---|---|
| Что это за платформа, какой модуль выбрать и как пройти сценарий | Этот сайт и `broad-docs/content/*.md` |
| Как подключить конкретный модуль и использовать его текущую версию | README модуля |
| Какие типы, методы и параметры существуют в API | DocC рядом с кодом модуля |
| Какие версии уже проверены вместе | `Compatibility/current.yml` в `broad-platform-integration` |
| Как собирается общий пример | README интеграционного репозитория |

Сайт не удаляет README и DocC. Он даёт понятную точку входа, а точный API
остаётся рядом с той версией кода, к которой относится.

## Как предложить правку

Внизу каждой статьи есть четыре ссылки:

- **Исходник** — открыть Markdown в GitHub;
- **Изменения** — посмотреть историю файла;
- **Чистый текст** — открыть raw Markdown;
- **Предложить правку** — отредактировать файл и создать pull request.

После объединения изменений сайт пересобирается. Закрытая CMS и отдельный
пароль читателя не нужны.

## Как запустить сайт локально

Нужны Node.js `22.13+` и pnpm `10.15.1`.

```bash
git clone https://github.com/BroadApps-official/broad-docs.git
cd broad-docs
pnpm install --frozen-lockfile
pnpm run dev
```

Откройте адрес, который напечатала последняя команда; обычно это
`http://localhost:3000`. Тексты страниц находятся в `content/*.md`. После
сохранения Markdown обновите страницу браузера.

## Как написать понятную статью

Каждый раздел должен отвечать хотя бы на один конкретный вопрос:

1. Что это такое?
2. Зачем это нужно приложению?
3. Когда разработчику открыть эту страницу?
4. Что именно сделать?
5. Как выглядит успешный результат?
6. Что эта проверка не доказывает?

Не оставляйте список английских терминов без расшифровки. При первом появлении
напишите обычное русское объяснение, а точное название из Xcode или API оставьте
в скобках или в коде.

## Картинки и ссылки

- Картинка должна лежать в `public/` и иметь понятное описание.
- Используйте путь вида `../public/...`, чтобы изображение работало и на сайте,
  и в Markdown GitHub.
- После переименования проверьте регистр букв в имени файла.
- Общая статья должна ссылаться на точный README или DocC модуля, а не копировать
  большую таблицу API вручную.

## Проверка перед pull request

Запустите:

```bash
pnpm run check
```

Команда проверит структуру статей, ссылки на локальные страницы, медиафайлы,
статический анализ сайта и production-сборку.

Перед отправкой также убедитесь:

- в тексте нет настоящих ключей, пользовательских данных и сырых ответов SDK;
- примеры соответствуют выпущенному публичному API;
- новые термины расшифрованы;
- изменённое поведение отражено в changelog;
- сайт и Markdown в GitHub рассказывают одно и то же.
