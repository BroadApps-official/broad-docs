# Keychain: стабильный идентификатор

Keychain помогает приложению сохранить свой customer ID между запусками и узнать прежний аккаунт после переустановки, если запись сохранилась. Эта страница посвящена хранению ID, миграции и ограничениям iCloud.

Баланс, расходы и бонусы разобраны отдельно в [данных аккаунта на сервере](./backend-account-data.md), а порядок действий после чистой установки — в [восстановлении аккаунта и покупок](./account-recovery.md).

> [!CAUTION]
> **Найденный ID не подтверждает вход или оплату.** Доступ к данным и серверной сессии проверяет backend; `AccountIdentifierSource` описывает только источник локального чтения.

## Как работает решение в BroadCore

`KeychainAccountIdentifierStore` входит в [BroadCore 2.1.0](https://github.com/BroadApps-official/broad-core-ios/releases/tag/2.1.0) и [набор платформы 4.1.0](./compatibility.md). Решение из [PR BroadCore #6](https://github.com/BroadApps-official/broad-core-ios/pull/6) доработано и объединено: окончательный ID выбирается до публикации локальной записи. Live-пример шаблона использует его для Adapty; серверную авторизацию и баланс подключает конкретное приложение.

Store выбирает идентификатор в таком порядке:

1. `legacyIdentifier` — ID уже работающего приложения, под которым существуют покупки и backend-аккаунт.
2. Локальная запись Keychain — свой ID устройства имеет приоритет над другой записью из iCloud.
3. Синхронизируемая запись Keychain — кандидат на восстановление существующего аккаунта.
4. Новый UUID — если пригодного ID нет и чтение завершилось определённым результатом.

Результат содержит ID и источник: `legacy`, `device`, `iCloudKeychain` или `generated`. Один экземпляр `actor` последовательно разрешает запросы и кеширует успешный результат. Ошибку локального чтения он возвращает как `.failed`, чтобы приложение могло повторить попытку позже.

У записи настраиваются `service`, `account` и при необходимости `accessGroup`. Имена должны оставаться стабильными при обновлении приложения: изменение этих значений делает прежнюю запись недоступной для нового запроса. В API модуля синхронизация включена по умолчанию; `synchronizesThroughICloudKeychain: false` отключает чтение и запись синхронизируемой копии. Шаблон явно выбирает `false` до определения серверного восстановления аккаунта. [Реализация Core 2.1.0](https://github.com/BroadApps-official/broad-core-ios/blob/2.1.0/Sources/BroadCore/Infrastructure/Keychain/KeychainAccountIdentifierStore.swift).

## Границы Keychain и iCloud

Сохранение Keychain после удаления приложения — наблюдаемое поведение, на которое нельзя опирать единственный путь восстановления. Apple DTS указывает, что это не документированная гарантия. Предусмотрите вход в существующий аккаунт или подтверждённое восстановление через поддержку, если запись утрачена. [Пояснение Apple](https://developer.apple.com/forums/thread/36442).

Общий Apple Account для iCloud и аккаунт **«Медиаматериалы и покупки»** могут различаться. Синхронизация Keychain не доказывает, какой App Store account оплатил подписку. Получение общей записи через iCloud также не является механизмом Apple Family Sharing. [Аккаунты для iCloud и покупок](https://support.apple.com/en-us/117294).

iCloud доставляет запись не мгновенно. Первый запуск до её появления может создать локальный ID; последующая доставка прежнего ID уже не переключает этот телефон. Поэтому обещание «тот же Apple ID всегда автоматически возвращает аккаунт» слишком сильное. Не исправляйте задержку слепой заменой ID: на новом аккаунте уже могли появиться покупки. Нужен предусмотренный приложением путь подтверждения и серверного объединения аккаунтов.

`synchronizesThroughICloudKeychain: false` означает отсутствие iCloud-синхронизации этой записи. Это не обещание, что запись никогда не переносится другим способом: store использует `kSecAttrAccessibleAfterFirstUnlock`, а не класс `ThisDeviceOnly`. Выбор класса защиты и перенос через резервную копию — отдельные параметры. [Классы защиты Keychain](https://support.apple.com/guide/security/keychain-data-protection-secb0694df1a/web).

## Как обработаны ошибки и конфликты

Модуль различает отсутствие записи и недоступность Keychain. Legacy и найденный iCloud ID считаются принятыми только после успешного локального сохранения. При создании аккаунта сначала выбирается окончательный ID с учётом синхронизируемой записи, затем он добавляется локально.

| Случай | Поведение Core 2.1.0 |
|---|---|
| Первое чтение Keychain недоступно | `.failed`, без создания другого аккаунта |
| Добавление в iCloud обнаружило существующий ID, но перечитать его не удалось | `.failed`; новый локальный ID не публикуется, повтор может восстановить прежний |
| Legacy или iCloud ID не удалось сохранить локально | `.failed`; миграция остаётся незавершённой |
| Другой экземпляр store обращается к записи во время разрешения iCloud-конфликта | Он не видит промежуточный новый локальный ID |
| Свою локальную запись успел добавить другой писатель | Принимается уже сохранённый локальный ID |

Ошибка не кешируется. После восстановления доступа повторяется тот же сценарий; приложение не должно обходить ошибку новым временным аккаунтом. Уже подтверждённый локальный ID сохраняет приоритет перед поздно пришедшим iCloud ID. Изменение legacy ID или переключение пользователя требует отдельного согласованного перехода на уровне приложения.

Проверка использует контролируемое чередование операций хранилища. Она не имитирует транспорт и разрешение конфликтов настоящего iCloud между двумя телефонами.

Исправления проверены существующим исполняемым contract probe, включая повтор после недоступного чтения, неудачной записи и работу двух экземпляров. Штатный `module_gate.sh` прошёл все девять этапов; совместная проверка платформы выполняется с указанными версиями. Эти результаты подтверждают клиентский алгоритм и сборки, но не фактическую доставку iCloud или настройку backend приложения.

## Общий Apple Account и личная история

Если два человека пользуются одной связкой iCloud, синхронизированный ID может привести их в один аккаунт приложения. Заранее определите, допускается ли это для подписки, баланса и личных данных.

> [!CAUTION]
> **Источник iCloudKeychain не является проверкой права на личную историю.** После успешного сохранения и перезапуска тот же ID уже возвращается как `.device`. Запрет загрузить историю только на первом запуске перестанет действовать на следующем.

Для личных чатов нужен подтверждённый вход или предусмотренное сервером восстановление аккаунта. Право читать данные проверяется сервером при каждом обращении; оно не зависит от источника локального чтения ID. При отсутствии такой модели автоматическое присоединение через iCloud следует отключить до её определения.

Сам `customerUserId` связывает записи, но не заменяет подтверждение владения аккаунтом. Если действующий backend использует случайный ID как единственный ключ входа, его копирование фактически переносит и доступ: это нужно явно учитывать в контракте приложения.

## Порядок подключения в шаблоне

В шаблоне 4.1.0 live-пример Adapty использует `ExamplePersistentAdaptyIdentityProvider`. Один store передаёт стабильный customer ID и проверяется перед активацией SDK и загрузкой paywall. При ошибке Keychain запрос останавливается: возврат `nil` прямо в Adapty иначе разрешил бы создать анонимный профиль. Имя сервиса — `<bundle identifier>.account`. [Подключение в шаблоне](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Examples/BroadAppTemplate/BroadAppTemplate/Infrastructure/Monetization/ExampleLiveAdaptyServicesFactory.swift).

Шаблон сохраняет анонимный Adapty customer ID. Это ещё не вход в backend-аккаунт. iCloud-синхронизация явно выключена; для её включения сначала определите серверное подтверждение аккаунта и правила доступа к личным данным. Обычные демонстрационные сценарии не обращаются к настоящему Keychain; live-схемы в автоматической проверке только собираются.


Для действующего приложения передайте прежний customer ID через `legacyIdentifier`. Сохраните точное значение и стабильные имена Keychain; изменение ID не объединяет уже существующие профили и покупки. Удалять legacy-значение можно только после подтверждённого сохранения.

Создавайте один store на согласованный жизненный цикл аккаунта. Дождитесь результата до запросов Adapty и backend; при `.failed` предложите повтор. При смене пользователя пересоздайте зависимые привязки: успешный результат store кешируется и сам не переключает аккаунт.

Отсутствие флага первого запуска в UserDefaults не является поводом чистить Keychain. Ручная очистка в платформе разрешена только в Debug для явно перечисленных записей приложения; незавершённые платежи она не стирает.

Следующий шаг — [восстановление сессии, прав и баланса](./account-recovery.md).

## Что проверить

- Миграция сохраняет прежний ID; ошибка записи не завершает её.
- Недоступное чтение и конфликт iCloud возвращают ошибку без нового локального аккаунта.
- Повтор после восстановления доступа возвращает прежний ID.
- Два экземпляра store не получают промежуточный ID при конфликте создания.
- При выключенной синхронизации store не читает и не пишет iCloud-копию.
- Потеря записи оставляет предусмотренный приложением путь входа в аккаунт.

Используйте контролируемое хранилище для ошибок и чередования операций. Сборка Simulator или generic iOS без подписи проверяет код, но не фактический перенос iCloud; устройства и синхронизация проверяются отдельно.
