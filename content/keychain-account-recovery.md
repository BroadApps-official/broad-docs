# Keychain: аккаунт, покупки и защита от сброса лимитов

После удаления приложения пользователь не должен получать новый бесплатный лимит, а после смены телефона — терять оплаченную подписку или токены. Для этого приложению нужен стабильный аккаунт, а серверу — сохранённые права и история начислений. Keychain помогает вернуть идентификатор этого аккаунта.

> [!CAUTION]
> **ID в Keychain сам по себе не подтверждает оплату и не гарантирует защиту от злоупотреблений.** Подписки проверяются платёжными источниками, баланс и использованные лимиты — сервером текущего аккаунта. Найденная запись не означает `isPremium = true`.

## Что именно нужно восстановить

| Сценарий | Роль Keychain | Откуда приходит результат |
|---|---|---|
| Удаление и повторная установка | Помогает узнать прежний аккаунт, если запись сохранилась | Сервер возвращает прежний лимит, права и баланс |
| Новый iPhone | Синхронизируемая запись может принести прежний ID через iCloud Keychain | Приложение подтверждает аккаунт и запрашивает его данные |
| Подписка Apple | Помогает сохранить связь с профилем приложения | StoreKit, Adapty и подключённый сервер проверки прав |
| Подписка картой или СБП | Помогает найти прежний аккаунт | Backend RU Billing |
| Купленные расходуемые токены | Помогает запросить прежний аккаунт | Полный актуальный серверный баланс |
| Повторное получение бесплатного бонуса | Сохраняет связь установки с аккаунтом | Сервер проверяет, был ли бонус уже выдан |

Apple-подписка может появиться на новом устройстве через обычную синхронизацию StoreKit/Adapty. Это не означает, что найден прежний аккаунт вашего backend. Adapty отдельно связывает профили по `customerUserId`; для сохранения этой связи нужен стабильный ID аккаунта. Ручная кнопка «Восстановить покупки» остаётся доступной пользователю. [Идентификация в Adapty](https://adapty.io/docs/identifying-users), [восстановление через SDK](https://adapty.io/docs/restore-purchase).

Расходуемые покупки не восстанавливают баланс кнопкой StoreKit Restore. Приложение читает баланс с backend; оно не складывает повторно старые покупки. Для RU-платежа тоже требуется серверный аккаунт. [Контракт восстановления платформы](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Documentation/AccountRecovery.md).

## Как работает решение в BroadCore

**Статус на 11 сентября 2026 года:** `KeychainAccountIdentifierStore` предложен в [PR BroadCore #6](https://github.com/BroadApps-official/broad-core-ios/pull/6), повторно проверена ревизия `388a65f` после исправлений. PR открыт; это кандидат на Core 2.1.0. В проверенном [наборе платформы 4.0.0](./compatibility.md) используется Core 2.0.0; нового store там ещё нет. Ниже описаны устройство кандидата и требования к подключению, а не инструкция установки выпущенного API.

Store выбирает идентификатор в таком порядке:

1. `legacyIdentifier` — ID уже работающего приложения, под которым существуют покупки и backend-аккаунт.
2. Локальная запись Keychain — свой ID устройства имеет приоритет над другой записью из iCloud.
3. Синхронизируемая запись Keychain — кандидат на восстановление существующего аккаунта.
4. Новый UUID — если пригодного ID нет и чтение завершилось определённым результатом.

Результат содержит ID и источник: `legacy`, `device`, `iCloudKeychain` или `generated`. Один экземпляр `actor` последовательно разрешает запросы и кеширует успешный результат. Ошибку локального чтения он возвращает как `.failed`, чтобы приложение могло повторить попытку позже.

У записи настраиваются `service`, `account` и при необходимости `accessGroup`. Имена должны оставаться стабильными при обновлении приложения: изменение этих значений делает прежнюю запись недоступной для нового запроса. В кандидате синхронизация включена по умолчанию; `synchronizesThroughICloudKeychain: false` отключает чтение и запись синхронизируемой копии. [Реализация кандидата](https://github.com/BroadApps-official/broad-core-ios/blob/388a65ff1ebba35f0976314aa8ed1471a8f4c4e5/Sources/BroadCore/Infrastructure/Keychain/KeychainAccountIdentifierStore.swift).

## Границы Keychain и iCloud

Сохранение Keychain после удаления приложения — наблюдаемое поведение, на которое нельзя опирать единственный путь восстановления. Apple DTS указывает, что это не документированная гарантия. Предусмотрите вход в существующий аккаунт или подтверждённое восстановление через поддержку, если запись утрачена. [Пояснение Apple](https://developer.apple.com/forums/thread/36442).

Общий Apple Account для iCloud и аккаунт **«Медиаматериалы и покупки»** могут различаться. Синхронизация Keychain не доказывает, какой App Store account оплатил подписку. Получение общей записи через iCloud также не является механизмом Apple Family Sharing. [Аккаунты для iCloud и покупок](https://support.apple.com/en-us/117294).

iCloud доставляет запись не мгновенно. В текущем кандидате первый запуск до её появления создаёт локальный ID; последующая доставка прежнего ID уже не переключает этот телефон. Это описанное ограничение решения, поэтому обещание «тот же Apple ID всегда автоматически возвращает аккаунт» слишком сильное. Не исправляйте задержку слепой заменой ID: на новом аккаунте уже могли появиться покупки. Нужен предусмотренный приложением путь подтверждения и серверного объединения аккаунтов.

`synchronizesThroughICloudKeychain: false` означает отсутствие iCloud-синхронизации этой записи. Это не обещание, что запись никогда не переносится другим способом: кандидат использует `kSecAttrAccessibleAfterFirstUnlock`, а не класс `ThisDeviceOnly`. Выбор класса защиты и перенос через резервную копию — отдельные параметры. [Классы защиты Keychain](https://support.apple.com/guide/security/keychain-data-protection-secb0694df1a/web).

## Что доработать в PR перед подключением

В ревизии `388a65f` исправлены замечания к первоначальному решению: недоступность iCloud при первом чтении возвращает ошибку, миграция legacy и импорт iCloud требуют успешного локального сохранения, а добавление синхронизируемой записи больше не перезаписывает существующий ID.

Повторная проверка реального resolver с подставным хранилищем выявила два оставшихся случая в `shareGenerated`.

| Случай | Поведение ревизии `388a65f` | Требуемое изменение |
|---|---|---|
| После генерации ID добавление в iCloud сообщает о существующей записи, но её перечитывание недоступно или локальная замена не удалась | Возвращается успешный новый ID; он уже записан локально и кешируется, поэтому повтор не возвращает прежний аккаунт | Не завершать выбор нового аккаунта при неразрешённом конфликте; сохранить возможность повторить восстановление |
| Два экземпляра store используют одну запись: второй уже вернул новый локальный ID, а первый затем обнаружил прежний iCloud ID | Первый заменяет локальный ID, а второй продолжает возвращать кешированный новый; клиенты расходятся по аккаунтам | Согласовать окончательный ID до публикации локальной записи и не менять уже выданный ID побочным действием |

Просто вернуть `.failed` в первом случае недостаточно: уже записанный новый ID победит при следующем чтении. Нужно изменить порядок выбора и сохранения либо явно хранить незавершённое состояние. Второй случай требует двух экземпляров store или процессов с общим хранилищем; последовательные вызовы одного `actor` сами по себе его не воспроизводят.

Проверка использует контролируемое чередование операций хранилища. Она не имитирует транспорт и разрешение конфликтов настоящего iCloud между двумя телефонами.

Штатный `module_gate.sh` прошёл все девять этапов на проверенной ревизии, включая сборки и встроенные проверки контрактов. Эти проверки не покрывают перечисленные сбои. До исправлений кандидат не следует считать готовым способом гарантированного восстановления аккаунта.

## Общий Apple Account и личная история

Если два человека пользуются одной связкой iCloud, синхронизированный ID может привести их в один аккаунт приложения. Заранее определите, допускается ли это для подписки, баланса и личных данных.

> [!CAUTION]
> **Источник iCloudKeychain не является проверкой права на личную историю.** После успешного сохранения и перезапуска тот же ID уже возвращается как `.device`. Запрет загрузить историю только на первом запуске перестанет действовать на следующем.

Для личных чатов нужен подтверждённый вход или предусмотренное сервером восстановление аккаунта. Право читать данные проверяется сервером при каждом обращении; оно не зависит от источника локального чтения ID. При отсутствии такой модели автоматическое присоединение через iCloud следует отключить до её определения.

Сам `customerUserId` связывает записи, но не заменяет подтверждение владения аккаунтом. Если действующий backend использует случайный ID как единственный ключ входа, его копирование фактически переносит и доступ: это нужно явно учитывать в контракте приложения.

## Порядок подключения в шаблоне

Добавление store в пакет ещё не подключает восстановление к приложению. В проверенном шаблоне live-пример Adapty использует `ExampleAnonymousAdaptyIdentityProvider`, который возвращает `nil`. PR #6 этот пример, авторизацию backend и проверенный набор версий не меняет. [Текущее место подключения](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Examples/BroadAppTemplate/BroadAppTemplate/Infrastructure/Monetization/ExampleLiveAdaptyServicesFactory.swift).

Общий сценарий восстановления в BroadMonetization уже есть, но серверный адаптер передаёт приложение. В шаблоне подключён `ExampleTokenFulfillmentRepository`: баланс начинается со 120, а баланс и обработанные transaction ID живут только в памяти экземпляра. Это демонстрация покупки и восстановления; она не подтверждает сохранение реальных средств после перезапуска или переустановки. Для выпуска требуется подключить backend конкретного приложения. [Сборка примера](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Examples/BroadAppTemplate/BroadAppTemplate/Application/AppCompositionRoot%2BTokens.swift), [демонстрационное хранилище](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Examples/BroadAppTemplate/BroadAppTemplate/Infrastructure/Monetization/ExampleTokenFixtures.swift).

После исправления и выпуска модуля подключайте сценарий в следующем порядке:

1. Зафиксируйте, где сейчас хранится ID и какие серверные записи к нему привязаны. Миграция должна сохранить точный существующий ID; не генерируйте его заново при каждом запуске.
2. Создайте единый сервис идентичности на уровне приложения. Чтение ID завершается до зависящих от него запросов Adapty и backend. При ошибке предложите повтор; не создавайте временный финансовый аккаунт.
3. Подтвердите серверную сессию и свяжите восстановленный ID с текущим аккаунтом по контракту backend. Для приложения с логином главным остаётся подтверждённый аккаунт пользователя.
4. Передайте согласованную идентичность в платёжный слой и сформируйте текущие `EntitlementSubject` и `SubjectAuthorizationBinding`. Не допускайте запросов со старой сессией и новым ID.
5. Выполните общий `RecoverCustomerAccessUseCase`: обновите права, получите серверный баланс и состояние RU-подписки. Откройте Premium только после подтверждённого `active`.
6. После смены аккаунта пересоздайте зависимые привязки и исключите применение старых ответов. Кешированный результат store сам по себе не переключится на другой аккаунт.

Это последовательность подключения, а не новые backend endpoints. Методы входа, привязки и объединения аккаунтов берутся из контракта вашего приложения. [Восстановление платформы](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Documentation/AccountRecovery.md), [ошибки и восстановление](./runtime-reliability.md).

Legacy-значение удаляется только после подтверждённого сохранения и завершения миграции. Отсутствие флага первого запуска в UserDefaults не является поводом чистить Keychain. В платформе ручная очистка допускается только в Debug, после подтверждения и для перечисленных записей приложения; незавершённые платежи такой очисткой не стираются.

## Что backend должен помнить после удаления приложения

Сервер сохраняет изменения при каждой покупке, выдаче бонуса и расходовании токенов. Не откладывайте запись до закрытия или удаления приложения. Переустановка не должна создавать новый финансовый профиль, обнулять историю операций или повторно выдавать стартовый пакет.

| Данные на сервере | Зачем они нужны |
|---|---|
| Стабильный аккаунт и подтверждённые способы входа или восстановления | Найти прежнего пользователя даже при утрате Keychain; одного присланного ID недостаточно для доступа |
| Текущий баланс и учёт начислений, списаний и возвратов по аккаунту | Вернуть оставшиеся токены и объяснить изменение остатка |
| Уникальная связка провайдера, окружения и ID платёжной операции с её владельцем | Не зачислить одну покупку дважды, в том числе на другой аккаунт |
| Выданные бонусы, использованные лимиты и период их действия | Не выдать предложение заново из-за чистой установки и не сбросить расход |

Например: пользователь купил 500 токенов, потратил 200, удалил приложение и вошёл снова. Backend возвращает **300 токенов**. Чтение прежних покупок не начисляет ещё 500, а отсутствие локального флага первого запуска не даёт новый бонус.

Удаление приложения и удаление аккаунта — разные действия. Переустановка не является запросом удалить серверный профиль. Явное удаление аккаунта обрабатывается отдельным сценарием приложения и не заменяется бессрочным хранением всех пользовательских данных.

Здесь баланс токенов означает расходуемые единицы продукта. Access/refresh-токены авторизации — отдельные секреты: если приложение их хранит, используйте Keychain с подходящей политикой доступа и сроками сессии. Истёкшая или отозванная сессия требует предусмотренного повторного входа; наличие старого ID не делает её действительной. PR #6 хранит идентификатор, а не реализует управление этими сессиями.

## Как защищать бесплатные лимиты и начисления

Храните выдачу бонуса и расход лимита на сервере по аккаунту. Проверка возможности использования и изменение остатка должны быть атомарными: два телефона одного аккаунта не должны одновременно потратить один остаток или дважды получить один бонус. Локальный счётчик допустим для отображения, но не для решения сервера о доступе.

Покупки учитываются один раз по уникальному идентификатору операции провайдера. Повторная доставка той же операции возвращает текущий баланс и не добавляет токены ещё раз. При восстановлении выполняется чтение баланса, а не новая выдача начального пакета. [Начисление и восстановление токенов](./token-paywall.md).

Если ограничение должно действовать на устройство даже при создании другого аккаунта, одного Keychain ID недостаточно. Apple предлагает DeviceCheck для серверных отметок об использовании предложения, а App Attest — для проверки подлинности запросов приложения. Это отдельная интеграция клиента и backend, которой PR #6 не содержит; она также не устраняет все виды злоупотреблений. [DeviceCheck и App Attest](https://developer.apple.com/documentation/devicecheck).

## Что проверить разработчику

| Проверка | Ожидаемый результат |
|---|---|
| Обновление старой установки | Старый ID и серверный аккаунт сохранены |
| Переустановка при сохранившейся записи | Возвращаются прежние лимиты и баланс, бонус повторно не выдаётся |
| Переустановка без записи Keychain, затем подтверждённый вход в прежний аккаунт | Backend возвращает остаток и использованные лимиты прежнего пользователя |
| Keychain недоступен | Повтор чтения, без нового аккаунта и обнуления баланса |
| Ошибка локального сохранения legacy или iCloud ID | Миграция не считается завершённой, повтор остаётся возможным |
| Задержка iCloud или разные ID на двух телефонах | Предусмотрен путь восстановления, нет скрытой смены аккаунта |
| Общая связка iCloud, затем перезапуск | Личные данные по-прежнему требуют права доступа |
| Отключённая синхронизация | Store не обращается к синхронизируемой записи |
| Потеря сети при восстановлении | Статус остаётся неизвестным/недоступным, не превращается в отсутствие покупки |
| Повтор начисления и два одновременных запроса | Сервер не дублирует начисление и не превышает лимит |
| Backend зачислил покупку, ответ потерялся, приложение удалили | Серверная запись сохраняется; после входа возвращается баланс без повторного начисления |
| Выход и вход в другой аккаунт | ID, сессия, платёжные привязки и ответы относятся к одному текущему пользователю |

Для логики используйте контролируемые хранилища и ответы без реальных платежей. Simulator и сборка generic iOS без подписи проверяют код, но не доказывают перенос через iCloud. Проверка двух реальных устройств, если доступна в компании, выполняется отдельно и не заменяется заявлением о прохождении сборки. Покупка, restore и RU-платёж для этих автоматических проверок не нужны.
