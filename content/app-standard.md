# Стандарт приложения

Для нового приложения берём общую логику из платформы, подключаем свой дизайн
и конфигурацию, затем проверяем весь пользовательский путь.

## Выберите следующий шаг

| Задача | Куда перейти |
|---|---|
| Первый раз подключаю библиотеки | [BroadStart: готовый проект и запуск](./getting-started.md) |
| Нужны онбординг, пейвол и оплата | [Выбор модулей](./module-selection.md), затем [подключение Adapty](./adapty-integration-guide.md) |
| Приложение уже написано | Запустите проверку ниже; при старых зависимостях — [переход на текущую платформу](./legacy-app-migration.md) |
| Создаю приложение с агентом | [Требования, план и работа по одному сценарию](./app-creation.md) |

## Что брать готовым

| Часть | Общая реализация | Что задаёт приложение |
|---|---|---|
| Онбординг | BroadUIFlows: страницы, переходы и ATT lifecycle | Содержимое, количество страниц и дизайн |
| Пейвол | BroadMonetization + BroadUIFlows: загрузка, выбор, оплата, restore и ошибки | Placements, оформление, тексты и legal links |
| RU-оплата | Общие правила, каталог, checkout и подтверждение доступа | Подтверждённые backend endpoints, DTO и авторизация |
| Tokens и special offer | Отдельные общие сценарии, если нужны продукту | Включение, свои placements и backend tokens |
| Загрузка и ошибки | LoadableState, общие UI-состояния, retry и loader | Понятные тексты и действие повтора |
| Стиль кода | SwiftFormat, SwiftLint и правила зависимостей | Применение правил к исходникам приложения |

Своя View может использовать общую ViewModel. Экран не обязан выглядеть как
демонстрационный. App-owned адаптер backend — нормальная часть интеграции;
повторная реализация всей оплаты или ATT требует проверки.

Готовые примеры: [BroadStart](./getting-started.md) — небольшой первый экран;
[BroadAppTemplate](https://github.com/BroadApps-official/broad-platform-integration/tree/main/Examples/BroadAppTemplate)
— каталог онбординга, пейволов, RU и ошибок. Подключайте только используемые
модули; список совместимых версий — в [каталоге](./compatibility.md).

## Настройте места показа один раз

Пейвол из настроек использует placement settings. Его Remote Config имеет
приоритет; main заполняет только отсутствующие ключи. False, null и ошибочное
значение своего paywall не заменяются разрешением из main.

Для token/tokens платформа сначала пробует настроенное имя. Продукты токенов
и special offer сохраняют свой каталог. Подробные примеры для разработчика
и аккаунт-менеджера — в [настройке Adapty](./adapty-setup.md).

## Запустите одну проверку

Команды выполняются из checkout
[broad-platform-integration](https://github.com/BroadApps-official/broad-platform-integration).
Замените путь и схему на своё приложение:

```bash
bash Scripts/agent_review_and_fix.sh app "/path/to/MyApp" --scheme MyApp --doctor
bash Scripts/agent_review_and_fix.sh app "/path/to/MyApp" --scheme MyApp
```

Агент проверит общие компоненты, placements/fallback, loader и повторные
нажатия, онбординг, оплату и стиль. Он отличает старую версию пакета от ошибки
подключения и отсутствующей возможности платформы.

Отчёт находится в папке приложения: `.build/AgentReview/app/latest.md`.
Каждое замечание содержит **проблему, файл, причину и нужное исправление**.
PASS означает, что в рамках аудита нет открытых замечаний; ISSUES — есть
нарушения; BLOCKED — обязательную проверку выполнить не удалось.
Зелёная сборка не отменяет замечания по логике.

Для разработчика самой платформы есть второй режим:

```bash
bash Scripts/agent_review_and_fix.sh platform
```

Он проверяет четыре module repositories рядом с integration и сам integration.
Явные режимы только проверяют; `--fix` разрешает минимальные исправления.
Платформа не публикует отчёты конкретных приложений.
[Полная инструкция и запуск внутри открытого агента](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Documentation/AgentReview.md).

## Передайте разработчику короткий результат

Пройдите первый запуск и онбординг, откройте пейвол из настроек, проверьте
отсутствие сети, пустой каталог, повторное нажатие и выход из ошибки. Для
подключённой оплаты проверьте отмену, pending и возврат из платёжного экрана
на согласованных локальных сценариях.

К результату приложите commit приложения, версии модулей, отчёт проверки и
оставшиеся ограничения. Сборка не подтверждает настоящий платёж или работу
внешнего backend. Юнит-тесты и новые test targets для этого процесса не нужны.
