# RU Billing: A/B-тесты для разработчика

Подключение готовой логики BroadMonetization 1.4.1, выбор продуктов и
интерактивная проверка настроек: [RU Billing A/B в платформе](./ru-billing-ab-platform.md).
Ниже сохранён контракт эксперимента и распределение ответственности.

Adapty умеет и назначать вариант paywall, и считать по нему конверсию — но
выручку он видит только через StoreKit. Под RU-оплатой покупка через StoreKit не
идёт вовсе: приложение создаёт платёжную ссылку на своём backend, пользователь
платит в браузере, деньги приходят в платёжный кабинет.

Получается разрыв: **Adapty видит показ и не видит оплату, платёжный кабинет
видит оплату и не знает варианта.** Конверсия по сегменту не считается нигде.

Закрывается это тем, что приложение само кладёт на backend знаменатель —
«пользователю назначен сегмент, paywall показан» — рядом с числителем, который
приходит туда сам: платёж лежит под тем же идентификатором пользователя.
Отдельного события покупки не отправляется именно поэтому — склейка идёт по id.

Перед этой страницей должен быть настроен обычный RU Billing по статье
[«RU Billing: карта и СБП»](./ru-billing.md) и получен каталог по статье
[«Продукты с backend»](./backend-product-catalog.md).

## Ответ за 30 секунд

```text
вариант paywall выбирает Adapty (всегда)
  → RU-gate закрыт  → показ и оплата считаются в Adapty
  → RU-gate открыт  → показ уходит на backend приложения,
                      оплата приходит туда же из платёжного кабинета,
                      склейка по идентификатору пользователя из JWT
```

Показ уходит ровно в **один** счётчик и никогда в оба.

## Кто чем управляет

| Решение | Источник | Как попадает в приложение |
|---|---|---|
| Какой вариант показать | Adapty | запрос placement, назначение остаётся за профилем |
| Какие продукты в варианте | Adapty | список `vendorProductId` placement |
| Цена и название продукта | backend | каталог продуктов, всегда в рублях |
| Флаги поведения | Adapty | Remote Config выбранного варианта `main` |
| Код сегмента для отчёта | Adapty | ключ `segment_code` в Remote Config `main` |
| Действующее назначение | backend | ответ `assign` — он авторитетнее запрошенного |

## Кто что готовит перед запуском

Ни одна роль не запускает тест в одиночку: коды и id должны совпасть с двух
сторон, иначе эксперимент выглядит исправным, но измеряет не ту гипотезу.

| Роль | Что заводит | Где |
|---|---|---|
| Продакт | Варианты paywall с весами и продуктами каждого сегмента | Adapty |
| Продакт | `experiment_code` и `segment_code` в Remote Config каждого варианта `main` — на вкладке той локали, которую запрашивает клиент | Adapty |
| Продакт | Эксперимент и сегменты под **теми же** кодами, что в Remote Config | админка RU-платежей |
| Продакт | Продукты всех сегментов с теми же id, что в Adapty, с рублёвой ценой | админка RU-платежей |
| Продакт | Запуск и остановка теста — с обеих сторон одновременно | Adapty и админка RU-платежей |
| Backend | Поле `isDefault` в каталоге продуктов и значение `true` у набора по умолчанию: подписок, токен-паков и офферных продуктов | каталог продуктов |
| Backend | Ручки `assign` и `paywall-shown`, включённые на установке | API приложения |
| Backend | Отчёт конверсии: показы из `paywall-shown` и платежи склеиваются по идентификатору пользователя | отчётность |
| Разработчик | RU-gate, ветвление показа, отбор каталога по id placement, два запроса, дедупликация и логи | приложение |

Коды сегментов — это не id paywall и не `variationId`. Это произвольные строки
вроде `a` и `b`, которые продакт задаёт одинаково в Remote Config Adapty и в
админке RU-платежей.

## Что заводится в Adapty

У каждого используемого варианта paywall **плейсмента `main`** в Remote Config
должны стоять три ключа ниже. Из `main` также читаются `auto_revenue_view`
и `special_offer`. Это единый источник настроек во всех экранах платформы 2.0.0;
дублировать ключи в остальных placements не нужно, их конфигурации игнорируются.
Без кодов отчёты не отправляются; без разрешающего RU gate оплата не включается.
Используйте стандартные имена ниже или явно согласованный custom registry.

| Ключ | Тип | Что делает |
|---|---|---|
| `experiment_code` | string | Код эксперимента. Нет ключа — отчёты не отправляются вовсе |
| `segment_code` | string | Код сегмента — произвольная строка вроде `a`, `b`, одинаковая в Adapty и на backend |
| `ru_pay` | bool | Открывает RU-оплату, а вместе с ней и RU-ветку отчётов |

### Одно распределение на все placement

Если эксперимент cross-placement, Adapty распределяет пользователя по вариантам
один раз и запоминает выбор сразу для всех экранов. Поэтому он не увидит сегмент
`a` на онбординге и `b` в настройках.

```text
Cross-AB-test placementId = main, BEGIN -> variationId = 19095be6-… DRAW
  main: 19095be6…   onboarding: ec8953ec…   icon_pro: e9127f92…
  settings: 17227c97…   tokens: a0fb7125…   send_messange: 27d2d691…
  special_offer: 424b80fd…
```

Значения — `variationId`, идентификаторы вариантов paywall, назначенных этому
пользователю на каждом placement. Все они из одной ветки эксперимента:
распределение по весам произошло один раз, на `main`, и вместе с выпавшим
вариантом Adapty прислала парные варианты остальных экранов. В интеграции
`variationId` не используется как код RU-сегмента — приложение читает
`segment_code` из Remote Config выбранного paywall `main`, — но по логу видно,
в какую ветку попал пользователь, ещё до первого
отчёта.

### Пример эксперимента

Два сегмента с весами 50/50. Приложение получает выбранный для `main`
`AdaptyPaywall` с уже определённым `variationId` и читает Remote Config у него.
Продукты загружаются из placement открываемого экрана. В отчёте `placement`
остаётся фактически показанным экраном, а коды эксперимента и сегмента — из `main`.
Выбор детерминирован по id профиля, поэтому один и тот же пользователь всегда
попадает в одну ветку.

| Сегмент | Вес | Гипотеза | Продукты варианта | Есть в каталоге backend |
|---|---|---|---|---|
| `a` | 50 | неделя + год | `yearly_49.99_not_trial`, `week_9.99_not_trial` | да, на экране рублёвые цены из каталога |
| `b` | 50 | месяц + год | `yearly_59.99_nottrial`, `monthly_19.99_nottrial` | нет, сработает набор по умолчанию |

Второй сегмент здесь — типовая ошибка запуска: продукты завели в Adapty, но не
завели в каталоге backend. Клиент не сломается, но вместо продуктов варианта `b`
покажет набор с отметкой `isDefault` — тот же, что достаётся пользователям с
пустым или недоступным placement. Сравнивать в итоге будут не те две ветки,
которые задумывали.

## Placement называет, backend оценивает

Под RU-оплатой пробить можно только продукт backend — продукты Adapty
номинированы в долларах. Но **какие** из них показать, решает вариант:
приложение берёт `vendorProductId` продуктов placement и ищет их по id в
каталоге backend. Схема работает при одном условии: **оба каталога живут в одном
пространстве id.**

1. Совпал хотя бы один id — показываем только совпавшие. Отметка набора по
   умолчанию не смотрится. Непокрытые id уходят в лог как `warning`.
2. Не совпал ни один — placement пуст или Adapty недоступна — включается
   fallback на продукты с отметкой набора по умолчанию.
3. В fallback пусто — показываем весь каталог. Это значит «backend ещё не
   публикует набор по умолчанию», а не «показывать нечего».

Третий шаг важнее, чем кажется: без него выкатка отметки на backend и выкатка
клиента должны совпасть по времени, иначе пользователи увидят пустой paywall.

| Экран | Каталог | Fallback |
|---|---|---|
| Подписки | подписки без офферных | `isDefault` |
| Токены | токен-паки | `isDefault` |
| Special Offer | подписки целиком | `isSpecialOffer && isDefault`, затем просто `isSpecialOffer` |

## Две ручки, одно тело

Обе живут на backend приложения и требуют JWT: **пользователь берётся из токена,
а не из тела запроса.** Это тот же идентификатор, под которым создаётся платёжная
ссылка и лежит платёж, — выбирать нечего, и ошибиться идентификатором
невозможно.

```text
POST /v1/billing/cloudpayments/experiments/assign
POST /v1/billing/cloudpayments/experiments/paywall-shown
```

Тело у обеих ручек одинаковое, все три поля обязательны, длина 1–64 символа:

```json
{
  "experimentCode": "yearly_monthly_dojim",
  "segmentCode": "a",
  "placement": "main"
}
```

Ответы:

```json
{
  "segment": { "code": "a", "isControl": true },
  "requestedSegmentMatches": true,
  "created": true
}
```

```json
{ "logged": true }
```

Правила вызова:

- **в `paywall-shown` уходит код из ответа `assign`**, а не запрошенный;
- `assign` идемпотентен — повтор вернёт `created: false`. Вызывается на каждый
  показ: он нужен, чтобы узнать действующий сегмент;
- `paywall-shown` намеренно не дедуплицируется на сервере, поэтому клиент
  отправляет его ровно раз на показ экрана;
- `502`, `429`, `503` — не ошибка для пользователя. Paywall рисуется, попытка
  повторится при следующем показе. `503` означает, что возможности нет на этой
  установке backend.

### Когда сегменты разъехались

При `requestedSegmentMatches: false` у пользователя уже есть другое назначение, и
оно авторитетно. Контракт просит рисовать paywall по вернувшемуся коду — **а
этого нельзя сделать:** вариант выбирает Adapty, и запроса «дай paywall сегмента
X» у неё нет. Есть только «вариант этого профиля» и «вариант аудитории по
умолчанию»; передать код сегмента нельзя ни в одном.

Поэтому: рисуем вариант Adapty, отчитываемся по действующему сегменту, пишем
`warning`. Назначение Adapty остаётся за профилем, так что расхождение — редкий
край.

## Показ уходит ровно в один счётчик

Ветвление одно и стоит в том месте, где логируется показ. Под RU-gate событие в
Adapty не отправляется вовсе: покупку Adapty всё равно не увидит, и показ без
покупки только испортил бы её конверсию.

```swift
guard !usesRussianWebCheckout else {
    return await trackPaywallExperiment(paywall: paywall, placementId: placementId)
}
// …Adapty.logShowPaywall / logShowFlow…
```

Возвращаемое значение — «показ действительно записан». `false` сбрасывает на
экране отметку «уже отправлено», и попытка повторится при следующем открытии: так
переживаются неготовый токен, `5xx` и недоступная возможность backend.

### Что нужно в коде

| Узел | Ответственность |
|---|---|
| RU-gate | Российский регион устройства или Storefront + разрешение обычного сценария либо явно подключённый резерв при недоступном Adapty; полученный false запрещает RU. Разрешение не сохраняется на диск |
| Слой монетизации | Ветвление показа, отбор каталога по id placement, чтение Remote Config |
| Слой API | Два POST-запроса рядом с checkout; авторизация общая с остальными запросами |
| Модель продукта | Поля `isSpecialOffer` и `isDefault` с терпимым разбором имён |
| Конфигурация | Имена ключей Remote Config и id placement — в одном месте |

### Дедупликация и повторы

Один показ экрана — одна пара запросов. Нужны два ограничителя: отметка «уже
отправлено», живущая столько же, сколько открытый экран, и защита от
параллельных вызовов, чтобы одновременные попытки не отправили дубль. Запоминать
успех дольше, чем открыт экран, не нужно — каждое открытие paywall это отдельный
показ.

## Частые ошибки

Каждая из них тихая: ничего не падает, просто цифры не сходятся.

| Ошибка | Что происходит |
|---|---|
| Вкладка локали в Adapty | Remote Config, заполненный на вкладке RU, до клиента не доедет, если paywall запрашивается без локали: SDK подставит `en`. В 4.x проблема меняет форму — приходят все локали сразу, и выбирать нужную должен клиент |
| Показ вне эксперимента не считается нигде | Ветки взаимоисключающие, поэтому paywall без `experiment_code` под RU-gate не попадает ни в Adapty, ни на backend. Это осознанный размен, но при чтении отчётов о нём надо помнить: знаменатель покрывает только paywall внутри эксперимента |
| Назначение создаётся при первом показе | `assign` вызывается при первом показе paywall, а не на старте. Пока RU-пользователь не открыл ни одного paywall, в эксперименте его нет: «сколько в сегменте» и «сколько увидели» на backend будут одним и тем же числом |
| Продукты сегмента забыли на backend | Вариант в Adapty ссылается на id, которых нет в каталоге backend, — сработает fallback, и вместо продуктов варианта покажется набор с отметкой `isDefault`. Сегмент будет измерять не свою гипотезу, а выглядеть при этом исправным. Перед запуском сверьте списки id обоих каталогов |

## Что проверить перед запуском

**В Adapty — продакт:**

- варианты paywall с весами и продуктами каждого сегмента;
- `experiment_code`, `segment_code`, `ru_pay` в Remote Config каждого варианта `main`;
- коды сегментов совпадают с теми, под которыми сегменты заведены на backend, — и
  это не id paywall;
- Remote Config заполнен на вкладке локали, которую реально запрашивает клиент.

**На backend — продакт и бэкендер:**

- эксперимент и сегменты заведены под тем же кодом;
- продукты всех сегментов есть в каталоге, id совпадают с Adapty;
- поле `isDefault` есть в каталоге и проставлено подпискам, токен-пакам и
  офферным продуктам набора по умолчанию;
- ручки `assign` и `paywall-shown` включены на установке;
- отчёт конверсии умеет соединить показы из `paywall-shown` с платежами по
  идентификатору пользователя — без этого собранные данные останутся лежать.

**В приложении — разработчик:**

- RU-gate: российский регион устройства **или** Storefront, затем обычное разрешение либо [резерв при сбое Adapty](./ru-billing.md); полученный false резерв не обходит;
- отбор каталога по id placement с двухступенчатым fallback;
- ветвление показа: ровно один счётчик, никогда оба;
- `segmentCode` в `paywall-shown` — из ответа `assign`;
- неуспех отчёта сбрасывает отметку «уже отправлено» и повторяется при следующем
  показе;
- логи: выбранная ветка, итог отчёта, fallback каталога, непокрытые id.
