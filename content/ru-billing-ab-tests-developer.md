# RU Billing: A/B-тесты для разработчика

Это отдельная инструкция для разработчика приложения. Здесь описано, **откуда
взять вариант A/B-теста, что сделать в коде и как доказать аккаунт-менеджеру,
что тест можно запускать**.

Главное правило: кабинет создаёт эксперимент, но сам по себе не меняет экран в
приложении. Приложение должно получить один подтверждённый вариант и выполнить
согласованный сценарий.

## Короткий ответ: нужно ли менять приложение

Зависит от источника варианта:

| Источник A/B | Что делает разработчик |
|---|---|
| **Adapty** | Использует готовую assignment-логику Adapty, один identity provider и существующие placement. Собственный randomizer не пишет. |
| **RU Billing / backend** | Подключает app-owned получение сегмента, сопоставляет сегмент с экраном и добавляет проверяемую аналитику. В общей платформе готового RU Billing assignment сейчас нет. |

Если никто не может назвать источник варианта, тест запускать нельзя.

## Шаг 1. Зафиксируйте источник A/B

До изменения кода получите один ответ:

```text
Источник варианта: Adapty / RU Billing backend
```

Нельзя одновременно назначать одному пользователю вариант в Adapty и RU
Billing. Два независимых источника могут отправить человека в разные сегменты,
и результат теста станет недостоверным.

## Вариант A. A/B назначает Adapty

Это готовый стандартный маршрут платформы. Adapty выбирает variation,
`BroadMonetization` сохраняет её вместе с показом и покупкой, а приложение не
создаёт второе распределение.

Разработчик должен:

1. активировать одну конфигурацию Adapty для приложения;
2. использовать один и тот же identity provider для load, show, purchase и restore;
3. передать точные logical placement → Adapty placement ID;
4. загружать каждый нужный placement через существующий платёжный слой;
5. не подменять variation локальным `Bool`, случайным числом или собственным сегментом;
6. проверить, что variation попадает в app analytics показа и покупки;
7. на одном тестовом профиле сверить variation приложения с Adapty dashboard.

Для cross-placement сценария связь между обычным paywall и Special Offer тоже
настраивает Adapty. Приложение только запрашивает согласованные placement и
выполняет полученный сценарий.

## Вариант B. A/B назначает RU Billing или backend

Это **не готовая функция общей платформы**. Такой маршрут можно делать только
после подтверждённого backend-контракта конкретного приложения.

До кода разработчик должен получить:

- метод или поле backend, которое возвращает назначенный сегмент;
- стабильный `experimentCode`;
- точные `controlSegmentCode` и `testSegmentCode`;
- правило идентификации пользователя;
- срок стабильности назначения;
- поведение при отсутствии, ошибке или неизвестном сегменте;
- событие аналитики фактического показа варианта.

Если этих данных нет, не придумывайте endpoint, сегмент или локальный
randomizer. Сообщите менеджеру: «RU Billing A/B пока не поддержан этой
сборкой».

## Что добавить в код приложения для RU Billing A/B

В host app нужен маленький app-owned адаптер. Названия ниже — пример формы
контракта, а не готовый backend API:

```swift
enum RUBillingExperimentVariant: String {
    case control
    case specialOffer
}

protocol RUBillingExperimentVariantProviding {
    func variant(experimentCode: String) async throws
        -> RUBillingExperimentVariant
}
```

Последовательность в приложении:

```text
получить подтверждённый segment code
                ↓
преобразовать только известный code в typed variant
                ↓
control      → закрыть paywall и открыть main
specialOffer → открыть RU Billing Special Offer
                ↓
после фактического показа отправить exposure analytics
```

Обязательные правила:

- неизвестный или отсутствующий сегмент не превращается в тестовый вариант;
- случайное распределение на iPhone не добавляется;
- один пользователь не должен менять вариант между экранами и сессиями;
- A/B-вариант решает только, какой сценарий показать;
- покупка, checkout и открытие Premium продолжают использовать обычный
  `BroadMonetization` и подтверждённый backend-статус;
- возврат из браузера не считается успешной оплатой.

## Что уже делает платформа, а что делает приложение

| Уже есть в BroadMonetization | Делает разработчик приложения |
|---|---|
| загрузка продуктов и точное сопоставление по ID | получение app-owned RU Billing segment |
| Apple purchase, RU checkout и restore | typed mapping segment → control / Special Offer |
| pending и подтверждение Premium | выбор нужного UI-сценария |
| Adapty variation attribution | exposure analytics для RU Billing A/B |
| защита от второго клиентского randomizer | проверка конкретной test-сборки |

Не переносите app-owned RU Billing assignment внутрь общей библиотеки без
отдельно согласованного межмодульного контракта.

## Что проверить перед запуском

Для двух тестовых пользователей или двух подтверждённых fixture-сценариев
проверьте:

1. контроль получает только контрольный экран;
2. тест получает только согласованный Special Offer;
3. повторный запуск сохраняет тот же вариант;
4. неизвестный сегмент безопасно ведёт в контроль, а не в Special Offer;
5. аналитика записывает `experimentCode`, `segmentCode` и факт показа;
6. покупка и restore не открывают второй экран;
7. Premium открывается только после подтверждённой покупки или backend-статуса;
8. в коде нет второго randomizer поверх выбранного источника.

Настоящая оплата для этой проверки не нужна.

## Что передать аккаунт-менеджеру

После проверки отправьте одну заполненную карточку:

```text
RU Billing A/B — подтверждение разработчика

Поддержка в текущей сборке: да / нет
Версия и номер сборки:
Источник варианта: Adapty / RU Billing backend
Experiment code:
Control segment code и поведение:
Test segment code и поведение:
Событие exposure analytics:
Неизвестный сегмент ведёт в:
Кто проверил:
Дата проверки:
Можно активировать эксперимент: да / нет
```

Пока последняя строка не подтверждена разработчиком, аккаунт-менеджер не
активирует эксперимент.

## Когда запускать нельзя

- источник варианта не выбран;
- RU Billing/backend не возвращает стабильный сегмент;
- коды сегментов в кабинете и приложении отличаются;
- приложение распределяет пользователей случайно само;
- неизвестный сегмент открывает тестовый экран;
- нет события фактического показа;
- тестовую сборку никто не проверил;
- Adapty и RU Billing одновременно назначают вариант одной аудитории.
