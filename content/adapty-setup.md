# Adapty: что нужно передать

Чтобы загрузить экран оплаты, приложению нужны только две вещи:

1. **Публичный ключ Adapty** — Adapty понимает, от какого приложения пришёл запрос.
2. **Имя места показа** — Adapty понимает, какой экран вернуть: например
   `settings`, `tokens` или `special_offer`. В интерфейсе Adapty это поле
   называется placement.

Больше ничего для обычной загрузки не требуется. Не нужно создавать второй
сетевой клиент или отдельную систему проверки ответа Adapty.

## Как данные доходят до экрана

```text
публичный ключ + имя нужного экрана
  → Adapty находит paywall нужного плейсмента
  → его Remote Config задаёт настройки экрана
  → отсутствующие ключи берутся из paywall main
  → возвращает все варианты покупки
  → платформа сохраняет весь список
  → приложение показывает его пользователю
```

Например, имя `settings` может означать подписку из настроек, а `tokens` — покупку
пакетов токенов. Сами имена выбирает команда приложения в Adapty.

## Что где настраивается

| Значение | Где оно живёт | Почему |
|---|---|---|
| Публичный ключ Adapty | В настройке приложения при запуске | Он относится к конкретному приложению |
| Имена мест показа | В одном списке внутри приложения | Каждый экран выбирает понятное имя, например `settings` |
| Экраны оплаты и варианты покупки | В панели управления Adapty | Их можно изменить без новой сборки приложения |
| Тексты и внешний вид | В ответе Adapty и/или UI приложения | Платформа не навязывает дизайн продукта |

Приложение хранит только те имена мест показа, которые действительно использует.

## Какие имена уже приняты в команде

Не надо придумывать новое имя, если экран подходит под обычный сценарий.
Для новых приложений уже используются такие базовые placement ID:

| Где показывается экран | Placement ID |
|---|---|
| Сразу после onboarding | `onboarding` |
| Из кнопки Premium / Pro | `pro_icon` |
| Из настроек | `settings` |
| Основной и резервный плейсмент | `main` |
| Отдельная CTR-кампания | `CTR` |
| Спешл оффер от Adapty | `special_offer` |

Это базовые имена, а не закрытый список. Если у приложения есть другой сценарий,
команда передаёт разработчику его placement ID, а приложение добавляет
явное сопоставление.

Точный Placement ID для обычного paywall передаёт команда приложения.
`main` — **идентификатор плейсмента**: места показа, к которому в Adapty
привязывают paywall или A/B-тест. У самого paywall есть отдельный идентификатор.
Главный экран приложения здесь не имеется в виду.
[Как Adapty определяет Placement ID](https://adapty.io/docs/create-placement).

`tokens` и `special_offer` нужны только тем приложениям, где есть соответствующий
экран. Идентификаторы в коде и кабинете должны совпадать точно: используйте
`main` в нижнем регистре.

## Если плейсмент недоступен

> [!CAUTION]
> **Обычный плейсмент недоступен — fallback на main.**
> Если плейсмент обычного paywall не создан, к нему не привязан опубликованный
> paywall или его не удалось загрузить, приложение запрашивает резервный
> плейсмент `main`. Правило действует для `onboarding`, `pro_icon`, `settings`,
> `CTR` и дополнительных точек показа обычного paywall.
> **Исключения:** для `tokens` и `special_offer` fallback на `main`
> не выполняется — у них отдельные продукты, цены и пейволы.

Плейсменты `tokens` и `special_offer` загружаются независимо. Если один из них
недоступен, нельзя подставлять продукты или цены `main`. Обрабатывайте ошибку
загрузки соответствующего экрана без замены его предложения обычной подпиской.

Разработчик реализует этот переход в общей логике загрузки плейсментов.
Это правило интеграции BroadApps; само имя `main` не включает автоматический
переход в Adapty SDK. Команда приложения должна создать плейсмент `main`
и привязать к нему опубликованный paywall с продуктами.

1. Загрузить paywall нужного Placement ID и прочитать его Remote Config.
2. Для отсутствующих ключей использовать текущий paywall `main`. Явные
   `false` и некорректные значения своего placement не заменять fallback.
   Если обычный paywall недоступен, загрузить paywall и продукты `main`.
3. Сохранить весь массив продуктов, variation и SDK-объекты фактически
   полученного paywall. Показ и покупку связывать с ним.
4. Если недоступен и `main`, обработать недоступность Adapty по настройкам
   приложения, включая подключённый [RU Billing](./ru-billing.md). Если данные
   для оплаты получить не удалось, показать ошибку с повторной попыткой.
   Повторно переходить с `main` на `main` и оставлять бесконечный loader нельзя.

## Пробных периодов нет

**В приложениях BroadApps нет trial — бесплатного пробного периода.**
Разработчик не добавляет логику trial, его проверки или предложения пробного
доступа в интерфейсе.

Названия продуктов в кабинете задаёт **аккаунт-менеджер**. Например,
`Weekly 9.99 Not Trial` — название для работы в кабинете. Разработчик не
переименовывает продукты и не добавляет к ним суффиксы. Код не разбирает
названия и не определяет по словам `Trial`, `Not Trial` или `nottrial`
поведение покупки. Для цены и периода подписки используются данные продукта,
полученные от Adapty.

## Главное правило продуктов

Платформа передаёт экрану весь список Adapty: ноль, один или любое количество
вариантов, в исходном порядке. Она не оставляет «лучшие два» и не сортирует по
цене.

Экран тоже показывает весь набор. Для двух карточек настройте два продукта
в Adapty для нужного placement. Обрезание списка в коде отдельного старого
приложения — частная реализация, а не правило для новых приложений.

## Remote Config

> [!CAUTION]
> **Ключи — из пейвола текущего placement. `main` — только fallback.**
> Например, пейвол в настройках открывается через `settings`: читаем Remote Config
> именно того пейвола, который Adapty выбрал для `settings`.
> Только если ключа в нём нет, берём этот ключ из пейвола `main`.
> Явные `false`, `null` и некорректные значения текущего пейвола не заменяются значениями из `main`.

С BroadMonetization 2.0.1 экран из настроек запрашивает `settings` и читает
Remote Config выбранного paywall в `settings`. Для `onboarding`, `pro_icon`,
`CTR`, `tokens`, `special_offer` и других мест действует то же правило.
Remote Config принадлежит paywall, привязанному к placement, а не самому
placement. При A/B-тесте учитывается выбранный Adapty вариант и его локаль.

| Пример | Результат |
|---|---|
| В `settings` есть `auto_revenue_view: false`, в `main` — `true` | Используется `false` из `settings` |
| В `settings` нет `auto_revenue_view`, в `main` — `true` | Используется `true` из `main` |
| `main` недоступен, в `settings` есть ключ | Используется ключ из `settings` |
| Обычный paywall `settings` недоступен | Загружается резервный paywall `main` с его продуктами и ключами |

| Ключ в Remote Config | Тип для настройки | Назначение |
|---|---|---|
| `ru_pay` | bool | Разрешение RU-ветки; дополнительно действуют регион, подключение backend и проверка authority |
| `auto_revenue_view` | bool | Настройка представления для host app; передаётся как `isAutomaticRevenueViewEnabled` |
| `special_offer` | строго bool | Разрешение спецпредложения |
| `experiment_code` | string | Код эксперимента, совпадающий с RU-админкой |
| `segment_code` | string | Код сегмента, например `a` / `b`, совпадающий с RU-админкой |

Пример значений для paywall, привязанного к `settings`:

```json
{
  "ru_pay": true,
  "auto_revenue_view": true,
  "special_offer": true,
  "experiment_code": "ru_payment_example",
  "segment_code": "a"
}
```

Для `special_offer` только точное булево `true` разрешает второй экран. `false`, отсутствие поля в обоих источниках,
строка `"true"`, число `1` или ошибка продолжают маршрут на главный экран
приложения.

Для продуктов второго экрана используется отдельный placement `special_offer`.
Совпадение имени placement и ключа не объединяет их: флаг обычного paywall
разрешает показ, а отдельный placement отдаёт все продукты оффера.

Приоритет у текущего placement: `ru_pay=true` в `settings` не заменяется
`false` из `main`, а `false` в `settings` не заменяется разрешением из `main`.
Если ключ отсутствует в обоих текущих ответах, gate остаётся закрытым.
Старое разрешение не восстанавливается из кеша; ошибка продуктов не отменяет
полученный запрет. Для RU-резерва сохраняются отдельные
[правила доступности](./ru-billing.md).

Пара `experiment_code` / `segment_code` берётся целиком из одного paywall.
Если текущий placement содержит только часть пары, отчёт не отправляется:
коды разных A/B-вариантов не смешиваются.

`auto_revenue_view` передаётся host app как настройка представления.
Готовая RU-форма платформы требует обязательные согласия независимо от этого
флага; он не разрешает пропускать подтверждение согласий.

**Обновление с 2.0.0:** проверьте ключи во всех используемых paywall.
Их собственные значения теперь имеют приоритет; `main` заполняет пропуски.

### Частные имена в существующих приложениях

Например, у 5007 ключ называется `sp_of`, а placement — `SpecialOffer`.
Эти имена были согласованы для 5007 и должны совпадать с его кодом. Для нового
приложения используйте общий `special_offer`; код не подменяет имена
автоматически. [Таблица соответствий 5007](./adapty-integration-guide.md).

### Общий сценарий RU Billing Special Offer

В RU Billing флаг текущего paywall с fallback на `main` разрешает показ по тем же правилам, но
RU-продукт выбирается в платёжном каталоге backend по отметке `isSpecialOffer`.
Adapty и App Store не являются источником RU-продукта.
[Полный разбор](./ru-special-offer.md).

Время жизни Special Offer Remote Config не задаёт — цикл «окно оффера →
cooldown» приложение ведёт само по этому флагу. Пока флаг `true`, оффер
показывается внутри окна показа (в текущей реализации — 24 часа), после
истечения окна наступает cooldown такой же длительности, затем цикл повторяется.
Выключение флага, покупка или restore сбрасывают цикл к началу.

При fallback обычного paywall на `main` меняется источник продуктов;
Remote Config тоже берётся из фактически загруженного paywall `main`. Для Special Offer продукты
загружаются только из отдельного плейсмента `special_offer`. Если он недоступен,
fallback на `main` не выполняется: продукты и цены основного paywall
не подставляются вместо оффера. Условия показа по флагу, окну и cooldown
продолжают действовать.

## Как проверить

1. Публичный ключ передаётся один раз при запуске приложения.
2. Экран запрашивает имя места показа из общего списка.
3. В диагностике видно, какое имя запросили и какое фактически получили.
4. На экран приходит полный массив продуктов.
5. Покупка использует вариант из уже загруженного экрана.
6. Автоматическая проверка не списывает настоящие деньги.
