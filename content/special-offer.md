# Спешл оффер (от Adapty)

Это второй экран покупки. Он открывается, когда пользователь закрыл обычный
paywall без покупки или restore. Продукты берутся из отдельного Adapty placement
`special_offer`.

Если в приложении подключён RU Billing, сначала настройте оффер по этой статье,
а затем завершите RU-flow по статье
[«RU Billing: спешл оффер»](./ru-special-offer.md).

## Что должно быть настроено в Adapty

1. Placement с продуктами оффера.
2. В Remote Config основного paywall — булев флаг `special_offer`. `true`
   разрешает показ; любое другое значение или отсутствие поля — нет.

Точные имена placement и флага, а также product ID уточняйте у аккаунт-менеджера.

## Когда показывается

```text
обычный paywall
  ├─ purchase / restore подтвердили Premium → главный экран
  └─ пользователь закрыл экран без покупки
       └─ special_offer == true в текущем Remote Config?
            ├─ нет / нет поля → главный экран
            └─ да → окно показа или cooldown?
                     ├─ идёт cooldown → главный экран
                     └─ окно активно → показать Special Offer
```

## Окно показа и cooldown

Пока флаг `true`, оффер показывается не постоянно, а циклом:

- **окно оффера — 24 часа:** отсчёт стартует в момент первого закрытия обычного
  paywall при активном флаге; внутри окна оффер появляется после каждого
  закрытия;
- **cooldown — 24 часа:** начинается ровно тогда, когда истекло окно оффера, и
  длится 24 часа от этого момента — а не от того, когда пользователь в следующий
  раз откроет приложение. Пока идёт cooldown, оффер не показывается, даже если
  флаг всё ещё `true`;
- после cooldown открывается новое окно, и цикл повторяется.

Обратный отсчёт на экране идёт до конца окна; на нуле экран закрывается и
начинается cooldown. Цикл сбрасывается при выключении флага, подтверждённой
покупке или restore.

## Второй режим: кампания без флага

Всё выше описывает режим по флагу. Рядом с ним есть второй, независимый режим —
**по наличию кампании**. Проект выбирает один из двух при сборке; переключателя в
рантайме нет, и режим по флагу от появления второго не меняется.

Он нужен там, где кампанией управляют самим плейсментом, а не дополнительным
значением рядом с ним. На практике в кабинетах так и настроено: плейсмент
`special_offer` отвечает своим экраном со скидочным продуктом, а ключа
`special_offer` в его Remote Config нет вообще — и режим по флагу такую живую
кампанию не покажет.

```text
обычный paywall закрыт без покупки
  → запросить placement special_offer
      ├─ ответил не свой экран (подстановка main)     → не показывать
      ├─ payload восстановлен из кэша платформы       → не показывать
      ├─ в кампании нет продуктов                     → не показывать
      ├─ special_offer == false (kill switch)         → не показывать
      └─ иначе                                        → показать
```

Ключ `special_offer` здесь не обязателен: явный `false` остаётся выключателем из
кабинета без релиза, отсутствие ключа ничего не значит.

### Сутки через сутки, по серверному времени

В этом режиме у оффера есть кадэнс: сутки он показывается после каждого закрытия
обычного paywall, потом сутки тихо, потом снова. Длительности можно переопределить
из Remote Config кампании.

Отсчёт идёт **по серверному времени**, которое приложение берёт из заголовка
`Date` ответов собственного бэкенда. Часы устройства не участвуют: перевод даты
вперёд не заканчивает окно раньше, перевод назад не открывает новое. Пока бэкенд
ни разу не ответил, оффер по умолчанию не показывается вообще — это осознанный
отказ вместо тихой работы по часам пользователя.

### Кто решает, когда показывать

Платформа. Она слышит закрытие paywall по событиям, которые он и так шлёт, сама
спрашивает кампанию и отдаёт приложению готовое решение. Приложению остаётся
нарисовать экран. Собственный экран оффера кампанию не вызывает, а подтверждённая
покупка или restore гасят окно.

Активная подписка отсекается **до** любых обращений к Adapty, кэшу и сети:
платящему скидка не показывается никогда. Это важно не только на обычном пути —
приложение может открыть подписочный экран и подписчику, например из управления
подпиской. Экран откроется, это решение приложения; оффера после него не будет.

Покупка не просто прячет оффер, а гасит окно. Следующая кампания начнётся с
нуля, а не доживёт остаток прежней — если подписка потом закончится или будет
возвращена, пользователь получит полные сутки, а не хвост от старого окна.

### Как проверить режим по наличию

1. Кампания настроена в кабинете, ключа `special_offer` у неё нет: обычный
   paywall закрыт без покупки → второй экран открылся.
2. Экран открылся ещё раз в тот же день → окно то же самое, счётчик продолжает
   прежний отсчёт, а не начинает новые сутки.
3. Прошли сутки → тихий период, оффер не показывается.
4. Часы устройства переведены вперёд или назад → срок не изменился.
5. Приложение перезапущено посреди окна → остаток тот же.
6. Куплена подписка → окно погашено; после её отмены новая кампания начинается
   с полных суток.
7. Закрыт экран пачек токенов → оффер не появился.
8. Закрыт сам экран оффера → второй оффер за ним не пришёл.
9. Подписка активна, подписочный экран открыт и закрыт → оффера нет.

## Как проверить

1. Обычный paywall открывается первым; подтверждённый Premium сразу ведёт на главный экран.
2. Без `special_offer = true` второй экран не появляется.
3. При `special_offer = true` и активном окне экран появляется со всеми продуктами placement в порядке Adapty.
4. После истечения окна оффер уходит в cooldown, затем цикл повторяется.
5. Выключение флага, покупка или restore сбрасывают цикл.
