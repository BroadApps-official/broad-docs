# Почему платформу разделили

Разделение решает практическую задачу: **приложение получает нужные возможности, а исправление выпускается у владельца кода**. Вместо одного старого BroadCore существуют четыре библиотеки, отдельный пример их совместной работы и этот сайт с инструкциями.

Эта статья объясняет устройство и последствия решения. Если нужно обновить работающее приложение, откройте [переход со старого BroadCore](./legacy-app-migration.md): там есть аудит, порядок переключения и сохранение правок приложения.

## Что было неудобно в одном репозитории

Когда общий код хранится и выпускается одной большой библиотекой, небольшая утилита оказывается рядом с оплатой и готовыми экранами. Изменение одной части выглядит как новая версия всей платформы. Разработчику сложнее понять, что действительно затронуто и какие зависимости придут в его приложение.

Большой README тоже выполнял слишком много задач: вводная инструкция, API, продуктовые правила и история изменений. Поэтому разделили не только исходники, но и ответственность за объяснения и совместимость.

Это решение зафиксировано в [ADR-0006 от 24 августа 2026 года](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Documentation/ADR/0006-federated-public-repositories.md). ADR — короткая запись: какая была проблема, что выбрали и чем за это заплатили.

## Что теперь находится в каждом репозитории

| Репозиторий | Что в нём хранится | Когда его открывать |
|---|---|---|
| [broad-extensions-ios](https://github.com/BroadApps-official/broad-extensions-ios) | Цвет, шрифты, клавиатура и другие независимые утилиты | Нужна небольшая функция интерфейса |
| [broad-core-ios](https://github.com/BroadApps-official/broad-core-ios) | Общие состояния, запуск, кеш, ошибки, повтор и ATT-адаптер | Нужна основа без платёжного SDK |
| [broad-monetization-ios](https://github.com/BroadApps-official/broad-monetization-ios) | Продукты, покупки, восстановление и подтверждение доступа | Нужна оплата со своим или готовым UI |
| [broad-ui-flows-ios](https://github.com/BroadApps-official/broad-ui-flows-ios) | Готовые экраны и логика пользовательских переходов | Нужен onboarding, paywall или общий маршрут |
| [broad-platform-integration](https://github.com/BroadApps-official/broad-platform-integration) | BroadAppTemplate, точные версии, общая проверка и инженерные инструкции | Нужно проверить библиотеки вместе |
| [broad-docs](https://github.com/BroadApps-official/broad-docs) | Статьи сайта, поиск, медиа и учебный BroadStart | Нужно понять применение и предложить правку |

Первые четыре строки — пакеты для приложения. Последние две — инструменты разработки и источники знаний. Не подключайте integration repository как обязательную «пятую библиотеку».

## Что изменилось для разработчика приложения

| Задача | Результат разделения | Что всё равно нужно сделать |
|---|---|---|
| Нужен только цвет из HEX | Можно взять Extensions без остальных модулей | Добавить его product в нужный target |
| Нужны только свои экраны и состояния | Можно взять Core без Adapty | Написать свой UI и сценарии данных |
| Нужна общая оплата | Monetization приносит Core и Adapty | Передать конфигурацию конкретного приложения |
| Нужен готовый onboarding | Можно использовать UIFlows | Учесть, что текущий пакет также приводит Monetization и Adapty |
| Требуется исправить один модуль | У него отдельная версия и changelog | Проверить зависимые модули и фактический набор приложения |
| Xcode скачал пакет без аккаунта | Исходники публичны | Настроить разрешённые ключи SDK и backend отдельно, когда они нужны |

Разделение не означает полной независимости всех четырёх пакетов. Есть направленные зависимости. Поэтому нижние библиотеки можно использовать отдельно, а UIFlows включает необходимую ему основу. [Полная карта зависимостей](./architecture.md).

## Пример: меняется маленькая утилита

Предположим, исправляется разбор цвета в BroadExtensions. Изменение и описание идут в репозиторий Extensions. Выпускается его новая версия после проверки. Core и Monetization не обязаны получать новые номера: они не зависят от Extensions.

В приложении, которое использует утилиту, разработчик обновляет выбранную версию, собирает проект и проверяет цвет в нужном экране. В каталоге совместимости фиксируется новый проверенный набор. Он может содержать новую версию Extensions и прежние версии остальных модулей.

Это пример процесса, а не сообщение о новом опубликованном исправлении. Актуальные номера всегда берутся из [каталога совместимости](./compatibility.md).

## Пример: меняется общее правило покупки

Если изменяется public API Monetization, его использует и UIFlows. Сначала готовят и проверяют изменение Monetization, затем проверяют код UIFlows с этим кандидатом и общий пример. Если UIFlows нужен новый API, его минимальная версия зависимости повышается.

Публичные выпуски идут снизу вверх: сначала должна существовать необходимая версия Monetization, затем — версия UIFlows, которая на неё ссылается. После проверки опубликованных тегов обновляется точный общий набор. [Пошаговый выпуск](./release-process.md).

Отдельные репозитории не позволяют пропустить эту общую проверку. Они делают её участников явными.

## Что сохранилось для существующих приложений

Сам факт разделения репозиториев не меняет установленное приложение у пользователей. Точное подключение к старому тегу не переключается на другой адрес автоматически. Изменения появятся в новой сборке приложения после того, как разработчик обновит зависимости и выпустит её.

Имя модуля `BroadCore` могло сохраниться, а адрес пакета — измениться. Поэтому одного `import BroadCore` недостаточно, чтобы определить старую или новую платформу. Проверьте URL в Xcode, правило версии, записи `Package.resolved` и локальные копии Swift-файлов.

Не удаляйте изменения приложения вместе со старой платформой. Сначала отделите общие исходники от собственных обёрток, конфигурации и дизайна. Затем переносите по одному сценарию и проверяйте прежнее поведение. [Как распознать старое подключение](./legacy-broadcore.md) · [Миграция приложения](./legacy-app-migration.md).

## Зачем остался общий пример

Отдельная библиотека может собираться, а сочетание нескольких библиотек — нет. `BroadAppTemplate` нужен, чтобы увидеть межмодульные ошибки: недоступный API, несовместимую версию, неправильную сборку зависимостей или сломанный переход.

`Compatibility/current.yml` хранит точные номера проверенного набора. Его `platform_set` — номер набора, а не версия каждого модуля и не пакет, который надо установить. Сборка примера не подтверждает настоящий backend, реальную оплату или дизайн вашего приложения.

Учебный BroadStart решает другую задачу: показывает маленькое первое подключение Core и Extensions. Он не заменяет интеграционную проверку платёжных сценариев.

## Чем команда платит за разделение

| Дополнительная работа | Как её удерживать понятной |
|---|---|
| Версии модулей различаются | Хранить один точный каталог совместимости |
| Изменение пересекает несколько репозиториев | Описывать порядок и связывать pull requests ссылками |
| README, DocC и сайт могут разойтись | Указывать владельца документа и проверяемую версию |
| Локальная сборка может отличаться от выпуска | Повторять сборку с опубликованными тегами и проверять Package.resolved |
| Ошибочный тег уже скачали разработчики | Выпускать исправление новым номером, не переписывать существующий тег |

## Как пользоваться результатом разделения

Для нового приложения начните с [первого подключения](./getting-started.md), выберите [нужные части](./module-selection.md) и их [версии](./compatibility.md). Для старого приложения используйте [миграцию](./legacy-app-migration.md). Для изменения общего кода сначала найдите [владельца](./architecture.md), затем следуйте [процессу выпуска](./release-process.md).

Если вопрос касается только непонятной статьи, исправляйте документацию. Для этого не требуется менять Swift API или выпускать новую версию каждого модуля. [Как предложить и опубликовать правку](./documentation.md).
