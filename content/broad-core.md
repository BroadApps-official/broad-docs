# BroadCore

`BroadCore` — невидимая основа приложения. Он не рисует экран и не принимает оплату. Его задача — помочь приложению **нормально запуститься и понятно пережить медленную сеть, ошибку или устаревшие данные**.

> Пример: пользователь открыл приложение в метро без сети. Core может прочитать допустимый кеш, сообщить экрану, что данные устарели, и безопасно повторить запрос. Как именно выглядит предупреждение, решает приложение или `BroadUIFlows`.

Если ссылка привела вас в старый `BroadApps-official/BroadCore`, откройте [страницу перехода](./legacy-broadcore.md). Старый монолитный репозиторий больше не является актуальной платформой.

## Что меняется для пользователя

Пользователь не видит название BroadCore, но замечает результат его работы:

- приложение не зависает навсегда на splash screen;
- загрузка имеет конечный timeout;
- повторный запрос не создаёт несколько одинаковых операций;
- при допустимом кеше человек видит контент, а не пустой экран;
- при ошибке интерфейс получает понятное состояние для Retry;
- системный запрос ATT не выскакивает раньше первого видимого экрана;
- в логах остаётся полезная диагностика без секретов и персональных данных.

## Четыре главные задачи Core

### 1. Управляемый запуск приложения

`AppBootstrapCoordinator` выполняет начальные действия в заданном порядке. Для каждого шага приложение указывает:

- что именно нужно сделать;
- критичен ли результат для первого экрана;
- сколько максимально ждать;
- можно ли повторить действие и сколько раз.

Критический шаг — то, без чего нельзя выбрать безопасный первый маршрут. Например, прочитать локальную конфигурацию. Фоновый шаг — полезная работа, которую можно закончить позже, не удерживая интерфейс.

> Важно: ATT, просьба оценить приложение, чат поддержки, purchase, restore и банковская оплата не относятся к bootstrap. Они требуют видимого UI или прямого действия пользователя.

### 2. Одни и те же состояния загрузки

`LoadableState<Value>` описывает не дизайн, а факты, которые должен отобразить экран.

| Состояние | Простое значение | Что обычно показывает UI |
|---|---|---|
| `idle` | Действие ещё не начиналось | Нейтральный экран или ничего |
| `loading` без старых данных | Идёт первая загрузка | Loader |
| `loading` со старым значением | Данные обновляются | Старый контент и небольшой индикатор |
| `loaded` | Есть актуальные данные | Основной экран |
| `empty` | Запрос успешен, но данных нет | Объяснение и доступное следующее действие |
| `stale` | Есть разрешённый устаревший кеш | Контент и предупреждение |
| `error` | Получить допустимый результат не удалось | Понятная ошибка и Retry или Close |

Core не выбирает текст и картинку ошибки. Он даёт интерфейсу точное состояние, чтобы UI не угадывал его по нескольким несогласованным `Bool`.

### 3. Версионный кеш

`VersionedJSONCacheRepository` хранит JSON вместе с технической информацией: схемой, версией и временем записи. При чтении Core различает:

- `fresh` — запись ещё годна;
- `stale` — срок истёк, но приложение может сознательно разрешить fallback;
- `missing` — записи нет или она несовместима;
- повреждённую запись — JSON нельзя безопасно прочитать.

Решение «можно ли показать stale» всегда принимает конкретная feature. Старый каталог статей может быть допустим без сети, а устаревший баланс или Premium — нет.

Для маленьких флагов есть `UserDefaultsKeyValueStore`. Для более крупных offline-данных — `FileSystemKeyValueStore` с ограничением размера и атомарной записью.

### 4. Ошибки, timeout, retry и безопасные логи

`NetworkFailureClassifier` переводит низкоуровневую сетевую ошибку в понятную категорию: offline, timeout, отмена или другой сбой. `RetryPolicy` и `TimeoutPolicy` ограничивают повтор и ожидание.

`BroadLoggerProtocol` принимает заранее определённые события. Логировать исходный URL, секреты авторизации, чек покупки, платёжную ссылку, персональные данные или целиком ответ сервиса нельзя. Готовый `OSLogBroadLogger` принимает subsystem как `String` (`init(subsystem:)`), поэтому его можно задать из `Bundle.main.bundleIdentifier` без литерала.

## Один понятный сценарий: запуск без сети

1. Приложение начинает bootstrap и сразу знает, какие шаги критичны.
2. Core пытается получить актуальную конфигурацию с конечным timeout.
3. Сеть недоступна; ошибка классифицируется как offline.
4. Core читает кеш и проверяет его схему, версию и срок.
5. Feature решает, что такой stale-контент разрешён.
6. ViewModel получает `LoadableState.stale` с данными.
7. UI показывает рабочий контент и небольшое предупреждение, а не вечный loader.
8. При Retry запускается одна новая попытка.

Без Core этот сценарий часто превращается в набор `isLoading`, `hasError`, `cachedValue`, `isOffline`, которые могут одновременно противоречить друг другу.

## Что именно есть в публичном API

| Тип | Для чего нужен |
|---|---|
| `AppBootstrapCoordinator` | Запускает critical и background steps с timeout и retry |
| `BootstrapStep` | Описывает один шаг запуска и его правила |
| `LoadableState` | Однозначно описывает состояние данных для UI |
| `AppError` | Передаёт typed-ошибку без показа сырого SDK error пользователю |
| `RetryPolicy`, `TimeoutPolicy` | Ограничивают повторы и ожидание |
| `VersionedJSONCacheRepository` | Читает и пишет кеш со схемой, версией и TTL |
| `UserDefaultsKeyValueStore` | Хранит небольшой локальный state |
| `FileSystemKeyValueStore` | Хранит более крупные payload в файлах |
| `BroadLoggerProtocol` | Записывает только разрешённые диагностические события |
| ATT adapter/use case | Вызывает системный API, когда UI выбрал правильный момент |
| `DebugFlagStore` | Хранит `#if DEBUG`-переключатели поверх key-value store с launch-argument override |
| `DebugKeychainCleaner` | `#if DEBUG`-очистка названных app-owned Keychain-сервисов для сброса состояния между прогонами |

## Что Core не делает

- не содержит paywall, onboarding или другой готовый SwiftUI экран;
- не активирует Adapty и не выполняет purchase или restore;
- не решает, какие продукты показывать;
- не объявляет устаревший кеш доказательством Premium или платежа;
- не хранит ключи, URLs и тексты конкретного приложения;
- не вызывает ATT автоматически из bootstrap, loader или `init`;
- не зависит от `BroadMonetization`, `BroadUIFlows` или `BroadExtensions`.

## Когда подключать напрямую

Подключайте `BroadCore`, если приложение самостоятельно строит UI и ему нужна хотя бы одна из функций: bootstrap, typed loading states, versioned cache, bounded retry/timeout, safe logging или ATT adapter.

Не подключайте Core отдельно, если уже выбран `BroadMonetization` или `BroadUIFlows` и приложение не импортирует Core API напрямую: Swift Package Manager скачает совместимую зависимость автоматически.

Если нужны только HEX-цвета, шрифты, клавиатура или swipe-back, выберите независимый `BroadExtensions`.

## Как подключить

```text
https://github.com/BroadApps-official/broad-core-ios.git
```

В target выберите product `BroadCore`. Из внешних зависимостей Xcode загрузит Swinject. Adapty, StoreKit, готовые paywall и onboarding не появятся.

Текущая проверенная версия — [`1.0.0`](https://github.com/BroadApps-official/broad-core-ios/releases/tag/1.0.0).

## Как проверить интеграцию

1. Соберите приложение до изменений, затем после подключения Core.
2. Проверьте успешный запуск и ошибку каждого critical шага.
3. Добавьте искусственный timeout: splash не должен зависнуть навсегда.
4. Отключите сеть и отдельно проверьте fresh, stale, missing и повреждённый кеш.
5. Быстро нажмите Retry дважды: должна существовать одна активная операция.
6. Просмотрите логи и убедитесь, что в них нет ключей, токенов, receipts и raw payload.
7. Если используется ATT, системный запрос должен появиться после видимого первого onboarding-экрана.
8. Соберите Debug, Release и общую iPhone-сборку без подписи.
