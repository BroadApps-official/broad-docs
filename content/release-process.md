# Как выпускать новые версии

Выпуск платформы заканчивается не появлением тега, а **проверенным опубликованным сочетанием библиотек и понятной инструкцией для приложения**. Разработчик должен знать, что изменится после обновления, что продолжит работать и какие настройки новой функции добавляются отдельно.

Эта страница предназначена для команды, которая меняет общие библиотеки. Если вы только обновляете зависимости своего приложения, начните с [выбора версий](./compatibility.md).

## Разделите три результата

| Результат | Что подтверждает | Что ещё требуется |
|---|---|---|
| Выпуск модуля | Конкретный код доступен под неизменяемым номером | Проверить его с зависимыми модулями |
| Проверенный platform set | Точные версии собраны и проверены вместе | Проверить настройки и сценарии конкретного приложения |
| Новая версия приложения | Приложение собрано с выбранными зависимостями | Выпуск и приёмка по процессу самого приложения |

Тег Core не выпускает автоматически новую версию UIFlows или приложения в App Store. Изменение текста на сайте тоже не требует синхронно повышать номера всех модулей.

## Шаг 1. Найдите владельца и опишите изменение

Исправление цвета относится к Extensions, общего timeout — к Core, подтверждения покупки — к Monetization, готового экрана — к UIFlows. Конфигурация и уникальное поведение одного приложения остаются в его репозитории. [Карта ответственности](./architecture.md).

В задаче и pull request напишите конкретный сценарий «до → после». Например: «при ошибке обновления списка экран терял прежний контент; теперь оставляет его и показывает сообщение». Укажите затронутый public API, значения по умолчанию, состояние на диске и зависимые модули.

Для новой опциональной возможности обязательно опишите отключённый вариант. Обновление библиотеки без новой конфигурации должно сохранять старое поведение, если выпуск объявлен совместимым.

## Шаг 2. Выберите номер по совместимости

| Изменение | Номер | Условный пример |
|---|---|---|
| Исправление с сохранением публичного контракта | Patch — последняя часть | 1.4.1 → 1.4.2 |
| Новая возможность, совместимая со старым кодом | Minor — средняя часть | 1.4.1 → 1.5.0 |
| Несовместимый API или прежнее поведение | Major — первая часть | 1.4.1 → 2.0.0 |

Это примеры выбора номера, не объявление новых релизов. Семантическая совместимость шире одинаковых сигнатур: иной default, другое значение старого JSON или новая обязательная конфигурация тоже могут сломать приложение.

Проверьте существующие initializer-вызовы, перегрузки и ссылки на конструкторы как на функции. Новый параметр со значением по умолчанию не всегда сохраняет точный тип такой ссылки. При необходимости оставьте прежний initializer и добавьте новый отдельно.

Для несовместимости подготовьте инструкцию перехода: старый вызов, новый вызов, настройка, поведение и ограничения отката. Только документация или CI без изменения пакета не требуют нового номера всех библиотек; отдельный patch нужен, если командой решено доставлять эти изменения новым package release.

## Шаг 3. Подготовьте код и документы модуля

Работайте в ветке владельца изменения. Сохраните чужие незавершённые правки и исходное рабочее состояние. Обновите README, DocC и `CHANGELOG.md`: что изменилось, зачем, для кого и что требуется после обновления.

Публичные объявления сверяются с `Documentation/PublicAPI.md`. Если API намеренно изменён, изучите diff, затем в корне модуля обновите отчёт:

```bash
bash Scripts/generate_public_api_report.sh --update
```

Команда использует собранный модуль; если сборки ещё нет, выполните подготовку из README владельца. Обновление отчёта принимает новый снимок API, но само по себе не доказывает совместимость. Нельзя механически обновить отчёт только ради исчезновения ошибки.

В README и changelog согласуйте целевой номер. Текущий `check_release_version.sh` сравнивает первый версионный раздел changelog, маркеры Release, badge и пример `from` в README с выпускаемым тегом.

## Шаг 4. Выполните проверку модуля

В корне изменённого модуля выполните:

```bash
bash Scripts/module_gate.sh
```

Точный состав задаётся скриптом конкретного репозитория. У текущих модулей он проверяет структуру и зависимости, документацию, релизные метаданные, формат, статический анализ, Swift Package, публичный API, отдельный iPhone-пример, privacy и DocC. Исполняемые проверки отдельных контрактов предусмотрены соответствующим модулем.

Различайте две сборки: пример модуля собирается в Debug для Simulator и в Release для generic iOS без подписи; общая интеграционная проверка дополнительно покрывает Debug/Release Simulator и другие сценарии. Не приписывайте одному скрипту результат другого.

Для обязательных проверок используются iPhone Simulator и неподписанная iOS-сборка, `Team = None`. Наличие платного Apple Developer аккаунта не требуется. По правилам репозиториев не добавляются XCTest, Swift Testing, test targets и реальные финансовые операции. Это не отменяет предусмотренные исполняемые сценарии и проверки контракта.

## Шаг 5. Проверьте зависимых потребителей до выпуска тега

| Что изменилось | Что проверить дополнительно |
|---|---|
| Extensions | Его пример и приложения/общий пример, которые его используют |
| Core | Monetization, UIFlows и общий пример |
| Monetization | UIFlows и общий пример |
| UIFlows | Его примеры и общий маршрут BroadAppTemplate |
| Только статья | Контент, ссылки и сборку сайта; Swift-выпуск обычно не требуется |

До публичного тега проверьте кандидат в изолированной рабочей копии зависимого проекта: временно привяжите нужный пакет к candidate commit или local package. Зафиксируйте, что проверялся именно кандидат. Временное подключение не должно попасть в релизную конфигурацию приложения или финальный каталог.

Полный gate каталога проверяет точные версии, lockfiles, публичные releases и метаданные. Поэтому сборка кандидата до тега — отдельное предварительное доказательство; она не подменяет финальный gate опубликованного набора.

Если верхний модуль использует новое API нижнего, поднимите минимальную версию его зависимости. Если прежний диапазон и API достаточны, не выпускайте новый номер верхнего модуля только для выравнивания номеров. Всё равно проверьте сочетание.

## Шаг 6. Опубликуйте модуль и дождитесь Release workflow

После проверки кандидата и согласованного review объедините изменение. Проверьте конкретный commit выпуска, чистое рабочее состояние и успешный CI на нём. Создайте **аннотированный тег** формата `x.y.z`, затем отправьте именно этот тег. Не отправляйте все локальные теги одной командой.

В текущих модулях публикация такого тега запускает [Release workflow](https://github.com/BroadApps-official/broad-core-ios/blob/main/.github/workflows/release.yml). Он проверяет номер, повторяет module gate и создаёт GitHub Release с changelog. Дождитесь его успешного окончания: наличие тега ещё не означает, что выпуск завершён.

После публикации сравните номер, commit тега, release и журнал CI. Если workflow упал, разберите причину; не объявляйте модуль готовым и не создавайте успешный отчёт вручную.

**Существующий опубликованный тег не передвигайте.** Разработчики и SwiftPM уже могли запомнить его исходный commit. Другой код под тем же номером приводит к несовпадению ревизий и ломает воспроизводимость. Исправленный код выпускайте новым номером.

## Шаг 7. Соберите окончательный набор из публичных версий

Когда нужные нижние и верхние модули опубликованы, обновите согласованный набор в integration repository:

| Файл или группа | Что согласовать |
|---|---|
| `Compatibility/current.yml` | Platform set, версии модулей, ссылки на releases и результаты проверки |
| Корневой `Package.swift` | Точные ограничения модулей |
| `Examples/BroadAppTemplate/project.yml` | Точные версии для примера |
| Сгенерированный `.xcodeproj` | Тот же набор, без временного candidate/local подключения |
| Оба `Package.resolved` | Реальные версии и ревизии пакета и примера |
| README, changelog и отчёт | Тот же номер набора и честная область проверки |

Проект примера генерируется штатным `Scripts/generate_example.sh`. После согласования файлов в корне integration repository выполните:

```bash
bash Scripts/agent_gate.sh
```

Успешный запуск заканчивается `BroadApps iOS Platform agent gate passed.` Он включает проверки правил, форматирования, анализа, сборок Package/Simulator/generic iOS и две Adapty-конфигурации **только на сборку**. Ошибка любого этапа не разрешает объявить набор проверенным.

`current.yml` — публичный каталог уже принятого сочетания. Не заменяйте его в main непроверенной комбинацией со статусом `passed`. Изменения следующего набора готовятся в рабочей ветке; публикуются вместе с действительным подтверждением всех перечисленных проверок. CI интеграционного репозитория должен пройти и после отправки.

## Шаг 8. Обновите объяснение для приложений

Обновите [таблицу версий](./compatibility.md), затронутые статьи и поисковый индекс сайта. Проверьте ссылки на точные tags, README и API. Опубликуйте сайт отдельным шагом и проверьте, что видимый текст соответствует принятому исходнику. [Процесс документации](./documentation.md).

В инструкции приложения должны быть понятны четыре вещи: целевые версии, требуемые правки, поведение без новой настройки и способ проверки. Ссылка только на огромный changelog не заменяет короткую инструкцию перехода.

## Если обнаружилась ошибка после выпуска

Сначала определите область: библиотека, конкретный app, неверная конфигурация или только документация. Для регрессии пакета подготовьте исправление новым номером и повторите затронутые проверки. До принятия нового сочетания у разработчиков должен оставаться последний проверенный набор и понятное сообщение о проблеме.

Если требуется откат приложения, восстановите согласованные настройки и lockfile, затем пересоберите и проверьте его. Откат не гарантирует обратную миграцию уже изменённых данных. Этот риск надо описать до выпуска несовместимого изменения.

Срочность сокращает объём изменения, но не позволяет пропустить проверку и написать `passed` заранее.

## Как должен выглядеть итог выпуска

Описание должно содержать проблему и новое поведение, выпущенный модуль, совместимый набор, действия разработчика и реальные результаты проверок. Например: «Новая возможность выключена по умолчанию; старые вызовы сохраняются; для включения передайте конфигурацию. Проверены прежний и новый сценарии. Production backend приложения требует отдельной проверки».

Не называйте это подтверждённой реальной покупкой, если выполнялись только compile и локальные ответы. Не называйте `main` готовым выпуском, пока конкретный тег и общий набор не прошли необходимые этапы.
