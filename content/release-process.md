# Как выпускать новые версии

Каждый модуль выпускается отдельно. Цель процесса — изменить нужный код, снова
проверить зависимые модули и только после этого объявить новую версию
совместимой.

## Как выбрать номер версии

| Изменение | Какая часть номера меняется | Пример |
|---|---|---|
| Исправление без изменения публичного API | Patch | `1.0.0 → 1.0.1` |
| Новая возможность, совместимая со старым кодом | Minor | `1.0.0 → 1.1.0` |
| Несовместимое изменение API или поведения | Major | `1.0.0 → 2.0.0` |

В `CHANGELOG.md` напишите не только что изменилось, но и зачем принято решение
и что должен сделать разработчик приложения.

## Порядок выпуска

1. Измените модуль, который действительно владеет кодом.
2. Запустите его автоматическую проверку и соберите iPhone-пример.
3. Проверьте README, DocC и публичный API.
4. Создайте Git-тег с выбранным номером версии.
5. Повторно проверьте модули, которые от него зависят.
6. Выпустите их новые версии только если им требуется новое API.
7. Обновите точные версии в `broad-platform-integration`.
8. Соберите общий пример и обновите каталог совместимости и сайт.

## Что проверяет автоматическая проверка

- формат и статический анализ Swift-кода;
- соблюдение архитектурных границ;
- privacy manifest;
- сборку Swift Package;
- Debug и Release для iPhone Simulator;
- сборку для физического iPhone без подписи;
- безопасные исполняемые сценарии без реальных платежей;
- README, DocC, ссылки, изображения и отчёт публичного API.

По решению владельца репозитории модулей не используют XCTest и Swift Testing.
Это не разрешает пропускать перечисленные проверки.

## Срочное исправление

Срочность не отменяет проверку. Пока новый набор версий не прошёл общую сборку,
каталог совместимости не должен показывать его как проверенный. Иначе
разработчик приложения не сможет отличить готовый набор от случайного сочетания
версий.
