# Как подготовить приложение к отправке в Codemagic

> **Главное правило:** приложение продолжаем разрабатывать в основной ветке `main`, где пакеты платформы подключены как обычно. Ветка `release/<версия>` нужна **только для сборки и отправки этой версии** через Codemagic. Новые правки в неё не вносим.

Перед началом сохраните изменения приложения в коммит и выставьте нужную версию в Xcode. Работайте в обычной ветке приложения: вручную создавать релизную ветку не требуется.

## Зачем нужен скрипт и что он делает

Во время разработки приложение может скачивать пакеты нашей платформы из Git. Перед релизом скрипт готовит **отдельную версию проекта для сборки**:

1. Проверяет, что изменения сохранены в коммит, а версия приложения указана в Xcode.
2. Копирует код пакетов нашей платформы внутрь проекта и переключает Xcode на эти локальные копии. Сторонние зависимости не меняет.
3. Проверяет, что в подготовленном проекте нет ссылок на Git нашей платформы, и пробует собрать его без подписи. Короткий отчёт сохраняет вне релизной ветки и IPA.
4. Создаёт ветку `release/<версия>` с подготовленным проектом и загружает её в GitHub. Обычная ветка разработки остаётся прежней.

После этого разработчик выбирает релизную ветку в Codemagic.

Так в проекте, который собирает Codemagic, нет прямых Git-ссылок на пакеты нашей платформы. Подготовка уменьшает количество явных технических связей с общими пакетами в релизном проекте.

## Что делать после отправки

Ветка `release/<версия>` нужна только для сборки и отправки **этой версии**. Не продолжайте в ней разработку и не переносите её обратно в `main`.

Если позже понадобятся исправления или новые функции, работайте в `main` с пакетами платформы. Для следующей версии снова запустите подготовку: появится новая релизная ветка.

## Где взять скрипт

Проверьте, есть ли в репозитории приложения файл `Scripts/prepare_release.sh`. Его **один раз добавляет владелец приложения** из актуального [инструмента платформы](https://github.com/BroadApps-official/broad-platform-integration/blob/main/ReleaseTools/install.sh). Каждому разработчику отдельно устанавливать его не нужно.

Если файла нет, владелец приложения открывает актуальный `broad-platform-integration` и из его корня запускает одну из команд. После пути к приложению укажите путь к проекту или workspace относительно корня приложения и имя схемы:

```bash
# Xcode project only
bash ReleaseTools/install.sh /path/to/App ios/App.xcodeproj AppScheme

# CocoaPods workspace; it may not exist before pod install
bash ReleaseTools/install.sh /path/to/App ios/App.xcodeproj AppScheme --workspace ios/App.xcworkspace

# Custom workspace without CocoaPods
bash ReleaseTools/install.sh /path/to/App ios/App.xcworkspace AppScheme
```

Для workspace с несколькими проектами приложения добавьте `--project ios/App.xcodeproj`. Если Podfile лежит не рядом с проектом или workspace, добавьте `--podfile path/to/Podfile`. Пути с пробелами заключите в кавычки. Схема должна быть **Shared**: в Xcode откройте **Product → Scheme → Manage Schemes**, включите **Shared** и сохраните `.xcscheme` в Git.

Установщик сам добавляет универсальный шаблон `Scripts/codemagic.release.yaml`, если файла ещё нет. Настройте в нём пути `XCODE_PROJECT`, `XCODE_WORKSPACE` (пустая строка означает сборку проекта), при необходимости `XCODE_PODFILE`, схему, подпись и публикацию. После проверки сохраните добавленные файлы в коммит приложения. Если старый релизный инструмент уже есть, установщик не перезапишет его: владелец сравнивает его с актуальным и обновляет вручную.

### Приложение на CocoaPods (например, с Usedesk)

Скрипт работает и с `.xcworkspace`: установщику можно передать и `App.xcworkspace`, и `App.xcodeproj` — Podfile рядом он найдёт сам. Для Xcode 27 и новее проверьте `Podfile`: у старых подов минимальная версия iOS ниже 15, и сборка падает с ошибкой `The iOS deployment target ... is set to 12.0, but the range of supported deployment target versions is 15.0 to ...`. Добавьте в конец `Podfile` и выполните `pod install`:

```ruby
post_install do |installer|
  installer.pods_project.targets.each do |target|
    target.build_configurations.each do |config|
      # Use the app's minimum iOS version.
      config.build_settings['IPHONEOS_DEPLOYMENT_TARGET'] = '16.0'
    end
  end
end
```

Сохраните изменённые `Podfile` и `Podfile.lock` в коммит — без этого не соберётся ни скрипт, ни Codemagic.

При подготовке релиза Pods устанавливаются в копии приложения до resolve. Сборка использует workspace, если он задан или создан CocoaPods; иначе использует проект. Codemagic умеет собирать workspace — прежняя проблема была в скрипте подготовки. Если в workspace несколько проектов с пакетами BroadApps, скрипт переключит ссылки во всех. Если он не может однозначно выбрать проект приложения, передайте `--project`.

Версия Swift-пакетов платформы в приложении может быть старой. **Обновлять пакеты только ради появления скрипта не нужно:** инструмент берёт версии, закреплённые в приложении. Если конкретную старую версию он не сможет подготовить, команда остановится с ошибкой — тогда обратитесь к владельцу платформы.

## Вариант 1. Подготовить вручную

1. Откройте терминал в корне репозитория приложения и запустите:

   ```bash
   bash Scripts/prepare_release.sh
   ```

2. Дождитесь сообщения `Ветка release/<версия> отправлена в GitHub`. Команда сама проверит проект, создаст отдельную ветку с локальным кодом платформы и загрузит её. Обычная ветка останется прежней. Например, для версии `1.4.0` появится ветка `release/1.4.0`.
3. В Codemagic нажмите **Start new build**. Выберите эту ветку и workflow для App Store. Сборка должна идти именно из релизной ветки.

Готовый IPA проверяется до отправки в App Store Connect. Если проверка не прошла, публикация не начинается.

## Вариант 2. Поручить Codex или Claude

Откройте агента в репозитории приложения и отправьте ему этот текст. Он выполнит те же шаги: подготовит и загрузит ветку в GitHub, а при наличии доступа запустит сборку в Codemagic.

```text
Подготовь релиз этого приложения. Если Scripts/prepare_release.sh отсутствует или устарел, возьми актуальный ReleaseTools из BroadApps-official/broad-platform-integration, подключи его к приложению и настрой Scripts/codemagic.release.yaml под его схему, подпись и публикацию. Версии Swift-пакетов только ради этого не обновляй. Проверь текущие изменения и версию в Xcode; готовые изменения приложения сохрани в коммит, ничего не удаляя. Запусти bash Scripts/prepare_release.sh без флагов. Убедись, что ветка release/<версия> создана, в ней код нашей платформы подключён локально, внутреннего отчёта в ветке нет и ветка загружена в GitHub. Если у тебя есть доступ к Codemagic, запусти релизный workflow именно из этой ветки и дождись результата проверки IPA. Релизную ветку используй только для сборки и отправки этой версии; дальнейшие правки делай в обычной рабочей ветке. При любой ошибке остановись, не обходи проверку и скажи, что мне нужно исправить. В конце сообщи название ветки, результат сборки и ссылку на неё, если сборка запускалась.
```

## Если что-то пошло не так

- Команда не появилась в репозитории? Используйте раздел «Где взять скрипт» выше: владелец приложения подключает инструмент один раз.
- Ошибка про `IPHONEOS_DEPLOYMENT_TARGET` и `Pods.xcodeproj`? Добавьте в `Podfile` блок `post_install` из раздела про CocoaPods выше.
- Команда завершилась ошибкой? Не запускайте Codemagic. Прочитайте последнюю строку ошибки и передайте её владельцу приложения или платформы.
- Ветка создана, но не загрузилась в GitHub? Нужен доступ на запись. После получения доступа выполните подсказанную команду `git push origin release/<версия>`.

Внутренний отчёт о подготовке хранится отдельно от релизной ветки и IPA. Сторонние зависимости приложения остаются как были.
