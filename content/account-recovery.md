# Восстановление аккаунта и покупок

После переустановки приложение возвращает пользователя в прежний аккаунт и читает его текущее состояние. Восстановление не должно заново начислять покупки или выдавать начальный пакет.

До подключения определите [данные аккаунта на сервере](./backend-account-data.md) и [способ сохранения ID](./keychain-account-recovery.md). Здесь описаны порядок запуска и проверка результата.

## Откуда возвращаются права и баланс

| Что восстанавливаем | Источник | Что требуется |
|---|---|---|
| Apple subscription или lifetime | StoreKit, Adapty и подключённый сервер проверки прав | Прежний аккаунт покупок; согласованная связь с аккаунтом приложения |
| Подписку картой или СБП | Backend RU Billing | Вход в тот же app account |
| Купленные расходуемые токены Apple или RU | Полный серверный баланс | Подтверждённый текущий аккаунт, без повторного сложения покупок |
| Бесплатные лимиты и бонусы | Серверный учёт использования | Прежний аккаунт и сохранённая история выдачи |
| Личную историю | Backend приложения | Подтверждённое право доступа к этим данным |

Apple-подписка может появиться через синхронизацию StoreKit/Adapty, даже если прежний backend-аккаунт ещё не найден. Стабильный `customerUserId` связывает профили Adapty, но не заменяет серверный вход. Ручная кнопка «Восстановить покупки» остаётся доступной. [Идентификация Adapty](https://adapty.io/docs/identifying-users), [восстановление покупок](https://adapty.io/docs/restore-purchase).

> [!CAUTION]
> **StoreKit Restore не возвращает баланс расходуемых токенов.** Для него нужен backend того же аккаунта. Клиент не начисляет повторно сумму старых покупок. [Контракт восстановления платформы](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Documentation/AccountRecovery.md).

## Порядок на чистой установке

1. Получите прежний ID и восстановите подтверждённую серверную сессию. Если запись Keychain утрачена, используйте предусмотренный вход; ошибка чтения не должна создавать временный финансовый аккаунт.
2. Согласуйте пользователя для Adapty и backend. Для приложения с логином главным остаётся подтверждённый серверный аккаунт.
3. Создайте текущие `EntitlementSubject` и `SubjectAuthorizationBinding`. Старые credentials и новый ID не должны участвовать в одном запросе.
4. Выполните `RecoverCustomerAccessUseCase`: обновите права, получите полный баланс токенов и состояние RU-подписки через адаптеры приложения.
5. Откройте Premium только после подтверждённого `active`. Примените к UI только подтверждённый баланс текущего аккаунта.

Методы входа, привязки и объединения аккаунтов берутся из контракта приложения. Платформа не создаёт эти endpoints автоматически. Без подключённого компонента восстановления нельзя считать его данные восстановленными.

## Перезапуск, сеть и смена аккаунта

При обычном возвращении в приложение сначала завершите сверку незавершённых покупок, затем обновите состояние аккаунта. Pending-покупка и чтение баланса — разные операции: [порядок вызовов token manager](./token-paywall.md).

Потеря сети оставляет данные неизвестными или недоступными. Не показывайте выдуманный ноль и не превращайте timeout в отсутствие подписки. После возвращения связи повторите чтение и сверку; новая покупка для этого не нужна.

После выхода или смены пользователя пересоздайте зависимые привязки. Поздний ответ старой сессии не должен примениться к новому аккаунту, а старый баланс — появиться у другого пользователя.

Если приложение удалили после оплаты, локальная pending-запись может исчезнуть. Backend должен уметь найти и обработать покупку независимо от неё, с проверенной привязкой к аккаунту. Способы сверки и однократного начисления описаны в [документации по токенам](./token-paywall.md).

## Проверки перед выпуском приложения

| Сценарий | Ожидаемый результат |
|---|---|
| Переустановка с сохранившимся ID | Прежний аккаунт, остаток и лимиты; бонус повторно не выдан |
| Переустановка без записи Keychain, затем вход | Сервер возвращает данные прежнего аккаунта |
| Куплено 500, потрачено 200, выполнен повторный вход | Остаток 300, без повторного начисления |
| Backend начислил покупку, ответ потерялся, приложение удалили | После входа возвращается сохранённый баланс |
| Сеть недоступна | Статус неизвестен/недоступен; есть повтор без новой покупки |
| Пользователь сменился во время запроса | Старый ответ не меняет данные нового аккаунта |
| Общая связка iCloud, затем перезапуск | Личная история по-прежнему требует права доступа |

Для клиентской логики используйте контролируемые хранилища и ответы без реальных платежей. Проверка production backend и переноса между устройствами выполняется отдельно: успешная сборка платформы не доказывает эти сценарии.
