# Аккаунт и данные на сервере

Удаление приложения не должно обнулять купленные токены, использованные лимиты и историю начислений. Для этого backend хранит данные по устойчивому аккаунту, а приложение после входа получает его текущее состояние.

Раздел «Аккаунт и восстановление» состоит из трёх инструкций:

| Задача | Где читать |
|---|---|
| Определить данные аккаунта, баланс и защиту от повторной выдачи | Эта страница |
| Сохранить и перенести идентификатор приложения | [Keychain: стабильный идентификатор](./keychain-account-recovery.md) |
| Вернуть сессию, права и остаток после чистой установки | [Восстановление аккаунта и покупок](./account-recovery.md) |

## Аккаунт не должен зависеть от установки

Backend определяет текущего пользователя по подтверждённой сессии. Присланный customer ID помогает связать записи, но сам по себе не доказывает право читать историю или тратить баланс.

При утрате Keychain нужен предусмотренный вход либо подтверждённое восстановление. Повторная установка не создаёт новый финансовый профиль для уже известного пользователя. Объединение двух существующих аккаунтов выполняется по серверному контракту с проверкой владения; клиент не меняет ID молча.

Удаление приложения и удаление аккаунта — разные действия. Переустановка не является запросом удалить профиль. Явное удаление аккаунта обрабатывается отдельным сценарием и не заменяется бессрочным хранением всех пользовательских данных.

## Какие данные сохранять

Сервер фиксирует изменения при каждой покупке, выдаче бонуса и расходовании токенов. Запись нельзя откладывать до закрытия или удаления приложения.

| Данные | Зачем они нужны |
|---|---|
| Стабильный аккаунт и подтверждённые способы входа или восстановления | Узнать прежнего пользователя при утрате локальных данных |
| Остаток токенов и учёт начислений, списаний и возвратов | Вернуть актуальный баланс и объяснить его изменение |
| Провайдер, окружение и уникальный ID платёжной операции с её владельцем | Не зачислить одну покупку дважды, в том числе на другой аккаунт |
| Выданные бонусы, использованные лимиты и период их действия | Не выдать предложение заново из-за чистой установки |

Пример: пользователь купил 500 токенов, потратил 200, удалил приложение и вошёл снова. Backend возвращает **300 токенов**. Чтение прежних покупок не начисляет ещё 500; отсутствие локального флага первого запуска не даёт новый бонус.

## Защита начислений и расходов

Проверка остатка и его изменение выполняются атомарно. Два телефона одного аккаунта не должны одновременно потратить один остаток или дважды получить один бонус. Локальный счётчик допустим для отображения, но не для решения сервера о доступе.

Backend проверяет покупку и учитывает её один раз по уникальной операции провайдера. Повторная доставка возвращает текущий баланс без второго начисления. При обычном восстановлении выполняется чтение состояния аккаунта. Проверка доказательства покупки, результаты `credited` / `alreadyCredited` и обработка повторов подробно описаны в [документации по токенам](./token-paywall.md).

Если ограничение должно действовать на устройство даже при создании другого аккаунта, одного Keychain ID недостаточно. DeviceCheck позволяет вести серверные отметки об использовании предложения, App Attest помогает проверять подлинность запросов приложения. Это отдельная интеграция клиента и backend; её нет в Core 2.1.0, и она не устраняет все виды злоупотреблений. [DeviceCheck и App Attest](https://developer.apple.com/documentation/devicecheck).

## Баланс токенов и токены входа

Расходуемые токены продукта — это серверный баланс. Access/refresh-токены авторизации — секреты с отдельным жизненным циклом. Если приложение их хранит, используйте Keychain с подходящей политикой доступа и сроками сессии.

Истёкшая или отозванная сессия требует предусмотренного повторного входа. Наличие старого ID не делает её действительной. `KeychainAccountIdentifierStore` хранит идентификатор и не реализует управление сессиями.

## Что уже есть в платформе

BroadMonetization предоставляет контракты начисления и восстановления баланса, привязку запросов к текущему пользователю и обработку неопределённых результатов. Реальный серверный адаптер передаёт приложение. [Контракт платформы](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Documentation/AccountRecovery.md).

В шаблоне `ExampleTokenFulfillmentRepository` начинает с 120 токенов и хранит баланс и обработанные transaction ID в памяти экземпляра. Это демонстрация; она не подтверждает сохранение средств после перезапуска или переустановки. Перед выпуском её нужно заменить backend конкретного приложения. [Подключение примера](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Examples/BroadAppTemplate/BroadAppTemplate/Application/AppCompositionRoot%2BTokens.swift), [демонстрационное хранилище](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Examples/BroadAppTemplate/BroadAppTemplate/Infrastructure/Monetization/ExampleTokenFixtures.swift).

Готовность backend проверяется отдельно: сохранение остатка после переустановки, повтор одной покупки, одновременное списание с двух устройств и повторная попытка получить бонус. Успешная клиентская сборка этих свойств не доказывает.
