# Интеграция Adapty в iOS-приложении

> Эта расширенная инструкция показывает прямую работу с Adapty SDK и реальный
> пример приложения 5007. В новых приложениях BroadApps сначала используйте
> общий маршрут [BroadMonetization](./broad-monetization.md), а эту страницу —
> для проверки placements, кастомного paywall, показов и A/B-тестов.
> Принятые в BroadApps названия приведены ниже; отдельно согласованные названия
> из 5007 разобраны в конце статьи с таблицей соответствий.

## Что делает Adapty

Adapty связывает приложение с подписками в App Store и помогает:

- получать доступные продукты и актуальные цены;
- показывать разные варианты пейволов;
- проводить A/B-тесты;
- выполнять покупки и восстановление подписок;
- определять, есть ли у пользователя Premium;
- собирать статистику показов, покупок и конверсии.

## Основные понятия

**Product** — подписка или покупка, созданная в App Store Connect. Например, недельная или годовая подписка.

**Paywall** — набор продуктов и настроек предложения в Adapty.

**Placement** — место в приложении, где может открыться пейвол. Например: после онбординга, перед анализом фотографии или из настроек.

**Variant** — один из вариантов пейвола в A/B-тесте. Adapty выбирает вариант для пользователя и возвращает его приложению.

**Кастомный пейвол** — экран, внешний вид которого полностью сделан в коде приложения. Adapty передаёт данные и продукты, но не управляет показом самого экрана.

## Какие названия использовать в BroadApps

Для новых приложений используйте базовые placement ID из
[настройки Adapty](./adapty-setup.md):

| Где показывается экран | Placement ID |
| --- | --- |
| Сразу после онбординга | `onboarding` |
| Из кнопки Premium / Pro | `pro_icon` |
| Из настроек | `settings` |
| Основной paywall или запасной маршрут | `main` |
| Отдельная CTR-кампания | `CTR` |
| Спешл оффер от Adapty | `special_offer` |

`main` — **Placement ID, идентификатор плейсмента**. К этому месту показа
в Adapty привязывается paywall или A/B-тест. У paywall есть собственный
идентификатор; главный экран приложения здесь не имеется в виду.
[Определение Placement ID в Adapty](https://adapty.io/docs/create-placement).

Точный Placement ID для обычного paywall и дополнительных сценариев передаёт
команда приложения. В коде и Adapty он должен совпадать полностью, включая
регистр: резервный плейсмент — `main`.

### Если плейсмент недоступен

> [!CAUTION]
> **Обычный плейсмент недоступен — fallback на main.**
> Если плейсмент обычного paywall не создан, к нему не привязан опубликованный
> paywall или его не удалось загрузить, приложение запрашивает резервный
> плейсмент `main`. Правило действует для `onboarding`, `pro_icon`, `settings`,
> `CTR` и дополнительных точек показа обычного paywall.
> **Исключения:** для `tokens` и `special_offer` fallback на `main`
> не выполняется — у них отдельные продукты, цены и пейволы.

Разработчик реализует fallback в общей логике загрузки. В Adapty должен быть
создан `main` с опубликованным paywall и продуктами. Для показа и покупки
используется фактически полученный paywall вместе с его продуктами.
Все Remote Config ключи читаются только из выбранного paywall `main`.
Если недоступен и `main`, дальнейшее поведение определяется настройками
оплаты приложения, включая подключённый [RU Billing](./ru-billing.md).
Если данные для оплаты получить не удалось, покажите ошибку с повторной
попыткой, без циклического перехода на `main`.
[Полное правило](./adapty-setup.md#если-плейсмент-недоступен).

### Trial и названия продуктов

**В приложениях BroadApps нет бесплатного пробного периода (trial).**
Разработчик не добавляет проверки trial или предложение пробного доступа.
Названия продуктов, включая `Weekly 9.99 Not Trial`, задаёт аккаунт-менеджер.
Код не разбирает эти названия и не определяет по ним поведение покупки.
Цену и период подписки он получает из данных продукта Adapty.

### Special Offer: placement и флаг — две разные настройки

В общем [сценарии Special Offer](./special-offer.md) они называются одинаково,
но выполняют разные задачи:

- **Ключ `special_offer` в Remote Config выбранного paywall `main`** разрешает показ
  второго экрана только при точном булевом `true`.
- **Отдельный placement `special_offer`** отдаёт продукты для этого экрана.

Одного создания placement недостаточно: нужен и флаг в выбранном paywall `main`.
Дальше показ следует правилам окна и cooldown из статьи Special Offer.
При настройке нового приложения ориентируйтесь на этот общий сценарий;
ниже отдельно разобраны имена, согласованные для существующего проекта 5007.

## Общая схема работы

Интеграция работает в следующем порядке:

1. При запуске приложения активируем Adapty SDK.
2. Перед открытием пейвола запрашиваем данные по нужному `placement`.
3. Получаем пейвол и связанные с ним продукты.
4. Показываем пользователю кастомный экран с ценами и условиями.
5. Сообщаем Adapty, что пейвол действительно появился на экране.
6. При нажатии на кнопку покупки передаём выбранный продукт в Adapty.
7. После покупки или восстановления проверяем, появился ли активный уровень доступа.

## 1. Подключение и запуск SDK

Adapty SDK добавляется в проект через Swift Package Manager. SDK нужно активировать один раз при запуске приложения с публичным SDK-ключом.

```swift
let configuration = AdaptyConfiguration
    .builder(withAPIKey: "PUBLIC_SDK_KEY")
    .build()

try await Adapty.activate(with: configuration)
```

Остальные методы Adapty следует вызывать после успешной активации SDK. Ошибку активации нужно записывать в логи, чтобы её можно было заметить при тестировании.

## 2. Получение пейвола и продуктов

Приложение сначала получает настройки из `main`, затем продукты нужного
`placement`. В BroadMonetization 2.0.0 это уже делает адаптер:

```swift
let mainPaywall = try await Adapty.getPaywall(placementId: "main")
let remoteConfig = mainPaywall.remoteConfig?.dictionary ?? [:]
let paywall = if placementId == "main" {
    mainPaywall
} else {
    try await Adapty.getPaywall(placementId: placementId)
}
let products = try await Adapty.getPaywallProducts(paywall: paywall)
```

> **Главное правило разработчика:** показывайте все продукты, которые Adapty
> вернул для текущего `placement`. Не фильтруйте их по `productId`, цене,
> периоду или локальному списку — иначе приложение изменит состав выбранного
> варианта A/B-теста.

Это сокращённый пример успешного пути. Обработку ошибок, fallback и provenance
выполняет адаптер платформы. `ru_pay`, `auto_revenue_view`, `special_offer`,
`experiment_code`, `segment_code` и остальные настройки берутся из `remoteConfig`
выше. Конфигурации других placements не участвуют. Показ логируется только
для реально показанного `paywall`; запрос `main` ради настроек не является показом.

Из полученных продуктов берутся цена, период подписки и другая информация для интерфейса. В приложениях BroadApps trial не используется. Не следует прописывать цену вручную: она может отличаться в зависимости от страны и валюты пользователя.

Важно, чтобы идентификатор `placement` в коде полностью совпадал с идентификатором в Adapty. Также к placement должен быть привязан опубликованный пейвол или A/B-тест.

Получение или предварительная загрузка пейвола ещё не означает, что пользователь его увидел. На этом этапе показ регистрировать не нужно.

## 3. Регистрация показа — обязательный шаг

Если интерфейс пейвола сделан в коде приложения, Adapty самостоятельно не знает, появился ли экран перед пользователем. Поэтому в момент фактического появления пейвола нужно отправить показ.

Для Adapty SDK 3.x:

```swift
try await Adapty.logShowPaywall(paywall)
```

Для Adapty SDK 4.x метод переименован:

```swift
try await Adapty.logShowFlow(flow)
```

Это один и тот же по смыслу шаг: сообщить Adapty, что выбранный пейвол или flow действительно показан пользователю.

### Когда вызывать метод

Метод вызывается, когда:

- данные пейвола уже получены;
- нужный экран действительно появился на устройстве;
- пользователь может видеть предложение.

Каждое отдельное открытие пейвола считается новым показом. При этом повторная перерисовка того же экрана не должна отправлять второй показ. Если пользователь закрыл пейвол и позднее открыл его снова, это уже новый показ.

В метод нужно передавать тот же объект `paywall` или `flow`, который был получен для текущего placement. В этом объекте есть информация о выбранном варианте A/B-теста.

### Когда метод вызывать не нужно

Показ не отправляется:

- во время предварительной загрузки;
- если пейвол загрузился, но экран не был открыт;
- для варианта теста, который пользователь не увидел;
- повторно из-за обновления состояния или перерисовки того же экрана.

Если экран полностью отображается через Adapty Paywall Builder или Flow Builder, Adapty регистрирует показ автоматически. Ручной вызов нужен именно для кастомного интерфейса.

### Почему этот шаг важен

Без `logShowPaywall` или `logShowFlow` покупки могут работать, но Adapty не получит информацию о показах. В результате:

- в статистике может быть `0` показов;
- конверсия из показа в покупку будет неправильной;
- результаты A/B-теста будут неполными;
- нельзя будет корректно сравнить варианты пейвола.

Отдельное событие `Views` в Amplitude или другой аналитике не заменяет этот вызов. Для статистики Adapty нужен именно метод Adapty SDK.

## 4. Как работает A/B-тест

> **Правило A/B-теста:** Adapty определяет вариант и набор продуктов. Код
> приложения отображает весь полученный набор без собственной фильтрации и
> использует тот же объект paywall или flow при регистрации показа.

1. В Adapty создаются два или больше вариантов пейвола.
2. Варианты добавляются в A/B-тест и привязываются к placement.
3. Тест публикуется.
4. Приложение запрашивает пейвол по placement.
5. Adapty выбирает вариант и возвращает его приложению.
6. Приложение показывает этот вариант и отправляет `logShowPaywall` или `logShowFlow`.
7. Покупка выполняется с продуктом из полученного пейвола.

Так Adapty понимает, какой вариант пользователь увидел и к какому варианту относится покупка.

## 5. Покупка и восстановление

Покупка выполняется с продуктом, который вернул Adapty:

```swift
let result = try await Adapty.makePurchase(product: product)
```

Нужно корректно обработать все результаты:

- успешная покупка;
- отмена пользователем;
- покупка ожидает подтверждения;
- ошибка.

Для восстановления ранее купленной подписки используется:

```swift
let profile = try await Adapty.restorePurchases()
```

После покупки или восстановления нельзя выдавать Premium только по факту завершения метода. Сначала нужно проверить активный уровень доступа в профиле пользователя — `profile.accessLevels`.

В приложении BroadApps это чтение не подменяет настроенный authoritative
entitlement-путь: окончательный Premium выдаёт тот источник, который выбран в
композиции конкретного приложения.

Кнопка восстановления должна быть доступна на пейволе или в настройках приложения.

## 6. Обработка ошибок

Ошибки загрузки, регистрации показа, покупки и восстановления должны попадать в логи.

Если плейсмент обычного paywall недоступен, приложение выполняет fallback
на плейсмент `main` по [общему правилу](./adapty-setup.md#если-плейсмент-недоступен).
Для `tokens` и `special_offer` этот переход запрещён: их продукты и цены
нельзя заменять предложением из `main`.
Если недоступен и `main`, обработайте недоступность Adapty по настройкам
оплаты приложения, включая подключённый [RU Billing](./ru-billing.md).
Если данные для оплаты получить не удалось, покажите ошибку с повторной
попыткой. Приложение не должно зависать, циклически запрашивать `main`
или показывать пустые цены.

Предварительно загруженный или закешированный пейвол можно использовать повторно, но при каждом новом реальном открытии всё равно нужно отдельно регистрировать показ.

## 7. Что проверить перед релизом

- SDK успешно активируется.
- Идентификаторы placement совпадают в приложении и Adapty.
- К каждому placement привязан опубликованный пейвол или A/B-тест.
- Все продукты и локальные цены загружаются и показываются без фильтрации в
  приложении.
- Кастомный пейвол отправляет показ только после появления на экране.
- Для показа используется объект, полученный для текущего placement и варианта.
- Покупка, отмена, ожидание и ошибка обработаны.
- Восстановление покупки работает.
- Premium выдаётся только при наличии активного access level.
- В логах нет ошибок Adapty.
- После тестового открытия в Adapty появляется статистика Views. Обновление Views в панели может происходить не мгновенно.

## Пример 5007: отдельно согласованные названия

Если нужно посмотреть, как такая интеграция работает в готовом приложении, можно использовать проект [5007 CheaterBuster](https://github.com/BroadApps-official/5007CheaterBuster). Репозиторий можно открыть на GitHub или скачать и запустить локально.

В 5007 имена placement и ключ Special Offer были согласованы отдельно, поэтому
они отличаются от базовых имён BroadApps. Этот раздел помогает читать код
5007. Для новых приложений используйте названия из начала статьи.

Пример помогает разобраться с загрузкой продуктов и регистрацией показов SDK.
Его таймер и состав карточек относятся к реализации 5007. Общие требования —
показать все продукты, закрыть экран по окончании окна 24 часа и выдержать
cooldown 24 часа — задаёт [статья Special Offer](./special-offer.md).
[Другие отличия записанных приложений](./ui-flows-paywall.md).

### Как соотносятся названия

| Настройка | В общем сценарии BroadApps | В проекте 5007 |
| --- | --- | --- |
| Placement основного paywall | `main` | `main` |
| Placement после онбординга | `onboarding` | `Onbording` |
| Placement из настроек | `settings` | `Settings` |
| Placement из кнопки Premium / Pro | `pro_icon` | `IconPro` |
| Placement Special Offer | `special_offer` | `SpecialOffer` |
| Ключ в Remote Config основного paywall | `special_offer` | `sp_of` |

Это соответствие по назначению. Код не заменяет одно имя другим
автоматически. Например, `Onbording` — точное написание ID в 5007,
а `Settings` и `settings` — разные строки.

Ещё в 5007 есть placement для собственных сценариев приложения:

| Место открытия в 5007 | Placement ID в 5007 |
| --- | --- |
| Поиск по фотографии | `SearchByPhoto` |
| Анализ Cheater | `AnalyzeCheater` |
| Анализ Location | `AnalyzeLocation` |

Для таких сценариев используйте ID, согласованные для вашего приложения.
При работе с самим 5007 сохраняйте соответствие имён в его коде и Adapty:
переименование требует согласованного изменения обеих сторон.

### Где смотреть реализацию 5007

В проекте используется кастомный пейвол на SwiftUI и Adapty SDK `3.15.7`. Поэтому показ регистрируется методом `Adapty.logShowPaywall(paywall)`. При переходе на SDK 4.x этот метод меняется на `Adapty.logShowFlow(flow)` вместе с остальными API новой версии.

Основные файлы, которые стоит посмотреть:

- `AppDelegate.swift` — активация Adapty и синхронизация профиля;
- `AdaptyPaywallManager.swift` — загрузка и кеширование пейволов и продуктов;
- `PaywallView.swift` — отображение кастомного пейвола и регистрация показа;
- `SubscriptionServiceAdapty.swift` — покупка и восстановление;
- `SubscriptionPlan.swift` — список placement.

В 5007 обычные пейволы открываются через `PaywallView`. При его появлении вызывается `AdaptyPaywallManager.logPaywallShown`, а внутри — `Adapty.logShowPaywall`.

При закрытии обычного paywall **код 5007** проверяет ключ `sp_of` в его Remote
Config для перехода к офферу из placement `SpecialOffer`. Показ оффера
регистрируется отдельно. В общем сценарии BroadApps для этих двух настроек
используются ключ `special_offer` и placement `special_offer`, как описано выше.

В реализации 5007 fallback на `main` есть у обычных плейсментов,
а для `SpecialOffer` такого перехода нет. Это соответствует
[общему правилу BroadApps](./adapty-setup.md#если-плейсмент-недоступен):
отдельные продукты и цены Special Offer не заменяются продуктами `main`.

Для диагностики в 5007 используются сообщения:

- `Logged paywall show` — показ успешно отправлен;
- `Failed to log Adapty paywall show` — показ отправить не удалось;
- `Paywall loaded` — пейвол получен;
- `Paywall products loaded` — продукты получены.

Если в A/B-тесте отображается `0` показов, сначала нужно проверить эти сообщения, правильность placement и публикацию теста в Adapty.
