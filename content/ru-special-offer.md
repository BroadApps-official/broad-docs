# RU Billing: спешл оффер

## Что это вообще такое

У приложения есть обычный экран оплаты. Пользователь посмотрел его, ничего не
купил и нажал крестик.

После этого приложение может показать **второй экран с другим предложением**.
Например: Premium на месяц по специальной цене.

На втором экране пользователь может заплатить:

- через Apple;
- через СБП;
- банковской картой.

Это и есть спешл оффер с RU Billing.

## Самое главное

Разработчик **не настраивает платёжный кабинет**. Ему должны заранее сообщить:

1. когда показывать второй экран;
2. какой товар продавать;
3. сколько он стоит и на какой срок даёт Premium;
4. можно ли платить через Apple, СБП и карту;
5. какие серверные методы использовать;
6. какие тексты и таймеры должны быть на экране.

Если чего-то из этого нет — спросите тимлида. Не берите настройки из другого
приложения и не придумывайте их сами.

## Как это работает — шесть простых шагов

### Шаг 1. Пользователь закрывает обычный экран оплаты

Если пользователь уже купил Premium или восстановил покупку, второй экран не
нужен. Сразу открываем приложение с Premium.

Если покупки нет и пользователь нажал крестик — переходим к следующей проверке.

### Шаг 2. Приложение спрашивает: «Можно показать предложение?»

Ответ приходит из заранее указанной настройки — например из Adapty.

```text
true  → можно продолжать
false → второй экран не показываем
ошибка или ответа нет → второй экран не показываем
```

Без явного `true` предложение не показывается.

### Шаг 3. Приложение загружает цены

Цены могут прийти из двух мест:

```text
Adapty / Apple → цена для оплаты через Apple
backend        → цена для оплаты через СБП и карту
```

Запросы независимы. Если RU backend временно не отвечает, Apple всё ещё может
работать. Если Apple не вернул товар, СБП и карта всё ещё могут работать.

### Шаг 4. Приложение показывает только работающие способы оплаты

Например:

- загрузился только Apple-товар → показываем Apple;
- загрузился только RU-товар → показываем СБП и карту;
- загрузились оба → показываем все разрешённые способы;
- не загрузилось ничего → показываем понятную ошибку, а не пустой экран.

### Шаг 5. Пользователь платит

Apple-покупка проходит через обычный Apple-маршрут.

Для СБП или карты приложение:

1. отправляет на backend точный ID выбранного товара;
2. получает безопасную `https`-ссылку;
3. открывает платёжную страницу;
4. ждёт возвращения пользователя.

### Шаг 6. Приложение проверяет результат

Возврат из браузера **не означает, что пользователь заплатил**. Он мог закрыть
страницу или не закончить оплату.

После возврата приложение спрашивает backend о статусе:

```text
active  → открыть Premium
pending → показать «Проверяем оплату» и проверить ещё раз
failed  → показать ошибку
```

Premium открывается только после подтверждённого `active`.

## Что именно должны передать разработчику

До начала кода заполните короткий список:

| Что сообщить | Простой пример |
|---|---|
| Где читать разрешение на показ | Adapty remote config |
| Как называется разрешающий флаг | `special_offer_ru` |
| Какое значение разрешает показ | `true` |
| ID товара для СБП/карты | `premium_offer_month_ru` |
| ID товара Apple | `premium_offer_month` |
| На какой срок покупка | один месяц |
| Покупка разовая или продлевается | разовая / с автопродлением |
| Сколько действует Premium | 30 дней |
| Какие способы оплаты доступны | Apple, СБП, карта |
| Методы backend | каталог, создание оплаты, проверка статуса |
| Сколько работают таймеры | значения от тимлида |
| Что написать и нарисовать | готовые тексты и изображения |

Разработчику не нужно знать, как менеджер создавал товары в кабинете. Ему нужны
только готовые значения из этой таблицы.

## Почему ID товара должен совпадать точно

У каждого товара есть имя для кода — product ID.

```text
premium_offer_month_ru
```

Это как номер заказа. Если изменить хотя бы один символ, получится уже другой
товар.

Правильно:

```text
нужен premium_offer_month_ru
найден premium_offer_month_ru
→ совпало
```

Неправильно:

```text
нужен premium_offer_month_ru
найден Premium_Offer_Month_RU
→ не совпало
```

Нельзя выбирать товар потому, что он самый дешёвый, первый в списке или похож
по названию. Используйте только точный ID, который вам передали.

## Когда можно показать СБП и карту

СБП и карта появляются, только если всё ниже выполнено одновременно:

1. RU Billing подключён в приложении.
2. Получен свежий `ru_pay = true`.
3. Storefront App Store российский **или** в настройках iPhone выбран регион Россия.
4. Backend вернул товар с нужным точным ID.
5. Backend разрешил создать оплату.
6. У пользователя ещё нет Premium.

Если `ru_pay` отсутствует, равен `false` или пришёл из старого кеша — СБП и
карта не показываются.

Русский язык телефона сам по себе ничего не включает.

## Зачем нужны два таймера

Таймеры отвечают на разные вопросы.

### Таймер между показами

Отвечает на вопрос: «Можно ли снова показать предложение этому пользователю?»

Например, тимлид может решить: показывать не чаще одного раза в сутки.

### Таймер на открытом экране

Это цифры, которые видит пользователь: например `09:59`, `09:58`, `09:57`.

Он создаёт ощущение ограниченного предложения, но не подтверждает оплату и не
выдаёт Premium.

Значения обоих таймеров сообщает тимлид. Платформа не назначает их сама.

## Что должно быть на экране

Показывайте только подтверждённые данные:

- название предложения;
- текущую цену;
- старую цену, если её действительно передали;
- срок Premium;
- доступные способы оплаты;
- таймер, если он нужен;
- обязательные согласия для RU-оплаты;
- email для чека, если его требует backend;
- ссылки на условия и политику;
- кнопку Restore для Apple.

Не пишите «скидка 50%», если такого подтверждённого значения нет. Не называйте
разовую покупку подпиской с автопродлением.

## Что уже делает платформа

`BroadMonetization` уже умеет:

- хранить полученный список товаров;
- находить товар по точному ID;
- проверять `ru_pay` и регион;
- запускать RU-оплату;
- хранить состояние «оплата ещё проверяется»;
- повторно проверять Premium.

Приложение добавляет свои настройки, экран, тексты и таймеры. Новая библиотека
или второй платёжный движок для этого не нужны.

## Короткий план для разработчика

1. Получите заполненную таблицу с настройками.
2. Подключите `BroadMonetization`.
3. После закрытия обычного paywall проверьте разрешающий флаг.
4. Загрузите Apple-товар и RU-товар.
5. Найдите нужные товары по точным ID.
6. Покажите доступные способы оплаты.
7. Для СБП/карты откройте ссылку, полученную от backend.
8. После возврата проверьте статус на backend.
9. Откройте Premium только после `active`.

## Что проверить без настоящей оплаты

- флаг `false` → второго экрана нет;
- нет ответа от настройки → второго экрана нет;
- RU backend сломан, Apple работает → остаётся Apple;
- `ru_pay=false` → СБП и карта скрыты;
- product ID отличается одним символом → товар не выбирается;
- пользователь вернулся из браузера без `active` → Premium закрыт;
- статус `pending` → новый платёж автоматически не создаётся;
- Premium уже активен → второй экран не показывается.
