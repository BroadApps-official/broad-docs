# RU Billing: спешл оффер для разработчика

Это инструкция по коду приложения. Настройка кабинета и A/B-теста вынесена в
отдельную страницу: [RU Billing для аккаунт-менеджера](./ru-billing-account-manager.md).

## Что строим

```text
Пользователь закрыл обычный paywall без покупки
                    ↓
приложение проверило явное разрешение
                    ↓
загрузило доступные Apple- и RU-продукты
                    ↓
показало второй экран
                    ↓
после оплаты дождалось подтверждённого Premium
```

Это не второй платёжный движок. Используйте существующий `BroadMonetization`.

## Что разработчику должны сообщить до кода

- точное условие показа;
- обычный и Special Offer product IDs;
- цена, валюта, тип и период;
- разрешённые способы оплаты;
- Adapty placement, если нужен Apple-продукт;
- backend catalog, checkout и status methods;
- пауза между повторными показами;
- визуальный таймер на экране;
- тексты, изображения и legal-ссылки;
- режим A/B: нет теста, Adapty или RU Billing;
- experiment и segment codes, если выбран RU Billing Experiment.

Если чего-то нет, задайте короткий вопрос и остановитесь. Не копируйте значения
из другого приложения.

## Шесть шагов реализации

### 1. Закрытие обычного paywall

Продолжайте к офферу только если:

- purchase не был подтверждён;
- restore не был подтверждён;
- Premium ещё не активен;
- пользователь явно закрыл обычный paywall.

### 2. Явное разрешение

```text
true  → можно загружать предложение
false → открыть main
нет значения или ошибка → открыть main
```

Отсутствующий флаг не превращайте в `true`.

### 3. Независимая загрузка двух источников

```text
Adapty / Apple → Apple-продукты
RU backend     → продукты для СБП и карты
```

Отказ одного источника не обязан скрывать рабочий второй источник.

### 4. Точное сопоставление продуктов

Ищите продукт только по подтверждённому product ID. Нельзя выбирать первый,
самый дешёвый или похожий по названию.

BroadUIFlows показывает все продукты, которые ему передал платёжный слой. Если
приложению нужен ограниченный набор, это должно быть явным app-owned правилом.

### 5. Checkout

Для Apple используйте обычный purchase-маршрут.

Для СБП или карты:

1. передайте backend точный выбранный product ID;
2. получите безопасный `https` checkout URL;
3. откройте браузер;
4. после возвращения начните проверку статуса.

Возврат из браузера не равен успешной оплате.

### 6. Подтверждение Premium

```text
active  → открыть Premium
pending → показать проверку и продолжить существующий polling
failed  → показать ошибку и разрешить согласованный Retry
```

Новый checkout нельзя автоматически создавать, пока прежняя операция находится
в `pending`.

## Регион и RU-способы оплаты

Текущее правило платформы: СБП и карта доступны при свежем `ru_pay = true` и
если Storefront App Store российский **или** регион iPhone — Россия.

Русский язык сам по себе ничего не включает. Отсутствующий, `false` или
устаревший `ru_pay` не разрешает RU checkout. Для конкретного приложения
сверьте правило с тимлидом.

## Два таймера — две разные задачи

| Таймер | Что решает |
|---|---|
| Пауза между показами | когда этому пользователю снова можно открыть оффер |
| Таймер на экране | какие цифры сейчас видит пользователь |

Значения сообщает команда продукта. Таймер на экране не выдаёт Premium и не
подтверждает оплату.

## Что проверить без настоящей оплаты

- `false` или отсутствующее разрешение → оффера нет;
- Premium уже активен → оффера нет;
- Apple работает, RU backend недоступен → остаётся Apple;
- RU работает, Apple-продукта нет → остаются разрешённые RU-методы;
- product ID отличается одним символом → продукт не выбирается;
- `ru_pay=false` → СБП и карта скрыты;
- browser return без `active` → Premium закрыт;
- `pending` → новый checkout не создаётся;
- правильный A/B segment приводит в правильный UI-вариант.

## Задание для Codex или Claude

```text
Добавь RU Billing Special Offer в текущее приложение.

Сначала проверь карточку входных данных: условие показа, product IDs,
способы оплаты, backend methods, таймеры, тексты и режим A/B.
Если данных нет — задай короткие вопросы и не меняй код.

Используй существующий BroadMonetization. Не создавай второй платёжный движок.
Показывай только фактически загруженные способы оплаты.
Возврат из браузера не считай оплатой.
Premium открывай только после подтверждённого active.
Настоящий платёж не выполняй.
```
