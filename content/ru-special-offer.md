# Спешл оффер RU Billing

Это дополнительное предложение после обычного экрана подписки. Пользователь
сначала видит основной paywall. Если он закрыл его без покупки, приложение
может показать специальную цену и предложить Apple, СБП или карту.

Главная мысль: **показ предложения, доступность российской оплаты и успешная
покупка — три разные проверки**. Один флаг или один экран не доказывает всё
сразу.

> Важно: страница описывает фактический reference 232 и безопасное правило для
> новых приложений. Она не утверждает, что кампания 232 сейчас включена. На
> момент аудита 30 августа 2026 года связанные эксперименты RU-кабинета были
> неактивны, но код 232 отдельно читает `kupon` из Adapty. Тимлид должен назвать,
> какая из этих систем сейчас действительно управляет показом.

## Чем он отличается от спешл оффера Adapty

| Вопрос | Спешл оффер от Adapty | Спешл оффер RU Billing |
|---|---|---|
| Откуда берётся предложение | отдельный placement Adapty | coupon-продукт RU backend; Apple-вариант может параллельно прийти из Adapty |
| Что разрешает показ | `special_offer = true` | отдельное решение кампании приложения |
| Как платит пользователь | Apple | Apple, СБП или карта — только реально доступные варианты |
| Как подтверждается результат | новая проверка Premium | backend policy/entitlement после возврата из браузера |
| Как работает таймер | визуальный цикл 24 часа | приложение отдельно задаёт окно показа и экранный countdown |

[Спешл оффер от Adapty](./special-offer.md) остаётся отдельной страницей. Его
циклический таймер нельзя переносить сюда автоматически.

## Весь маршрут на одном экране

```text
1. Обычный paywall
   ├─ покупка/restore подтвердили Premium → открыть приложение
   └─ крестик без покупки → проверить кампанию

2. Главный сигнал кампании
   ├─ выключен или состояние неизвестно → открыть приложение
   └─ разрешена → загрузить варианты специальной цены

3. Два независимых источника
   ├─ Adapty placement kupon → Apple-вариант
   └─ RU backend catalog → coupon для СБП/карты

4. Пользователь выбирает способ
   ├─ Apple → покупка через StoreKit/Adapty
   └─ СБП/карта → внешний HTTPS checkout

5. После оплаты
   ├─ backend подтвердил active → Premium и закрытие paywall
   ├─ pending/timeout → продолжаем проверку, Premium не выдаём
   └─ inactive/failed → показываем понятную ошибку или повтор
```

## Что именно нашли в приложении 232

Reference лежит в папке `Claude232` и исследовался только для чтения. У
Release-приложения:

- название на устройстве — Claimva;
- App Store ID — `6758451701`;
- Release bundle ID — `com.arm.232C1aude`;
- product IDs чувствительны к регистру.

В коде есть, например:

- `yearly_49.99_nottrial`;
- `monthly_19.99_nottrial`;
- `monthly_12.99_nottrial`;
- `week_6.99_nottrial`;
- `100_tokens_9.99`.

Эти значения нужны не как шаблон названий для нового приложения, а как
отпечаток, по которому можно отличить правильную запись кабинета от копий.

## Как нашли правильную запись в кабинете

В кабинете есть три очень похожие записи. Выбирать ту, где красивее или
актуальнее название, нельзя.

| Запись | Совпало с локальным 232 | Не совпало | Решение |
|---|---|---|---|
| `232 Claude` | App Store ID, lowercase product IDs и campaign binding | старое название | это reference текущего кода 232 |
| `232 Claude AI New T-Bank` | большинство lowercase product IDs | нет доказанной привязки к текущему App Store ID и эксперименту | похожая копия |
| `232 Claimva AI Chatbot (Т-Банк)` | текущее display name Claimva | token product IDs имеют другой регистр | другая копия конфигурации |

Правильная проверка всегда состоит из трёх частей:

1. App Store ID или другой неизменяемый ID приложения.
2. Полный набор product ID с точным регистром.
3. Фактическая привязка кампании или эксперимента.

Название — только подсказка. Оно меняется при ребрендинге и часто остаётся у
копий.

## Важное расхождение в рабочей записи 232

Аудит нашёл ещё один момент, который нельзя молча копировать:

| Где | Что найдено |
|---|---|
| рабочая запись кабинета | включён режим «сделать все продукты разовыми» |
| экран 232 | discount называется рекуррентной подпиской и просит согласие на регулярные списания |
| код checkout | используется CloudPayments-path |
| служебная настройка кабинета | поле payment gateway называет другой маршрут |

Это не правило платформы. До следующего rollout тимлид, backend-разработчик и
legal должны одним ответом зафиксировать:

1. покупка разовая или автоматически продлевается;
2. какой текст согласия должен видеть пользователь;
3. кто выдаёт и продлевает Premium и на какой срок;
4. какой платёжный route реально используется в production;
5. как работает отмена.

Пока ответы противоречат друг другу, этот пункт помечается `BLOCKED`. Не нужно
пытаться «исправить» несоответствие новым слоем платформы или копировать toggle
в другое приложение.

## Почему сейчас нельзя назвать один coupon SKU «наверняка»

В evidence 232 есть конфликт:

- локальная история связывает `widgetTitle = kupon` с
  `monthly_12.99_nottrial`;
- названия dashboard-экспериментов упоминают вариант `Cupon9.99`;
- в рабочей записи существуют и `monthly_12.99_nottrial`, и
  `monthly_9.99_nottrial`;
- связанные эксперименты RU-кабинета на момент аудита неактивны, но Adapty
  `kupon` является отдельным сигналом.

Поэтому инструкция не угадывает продукт и не считает один dashboard
единственным gate. Перед новым rollout владелец кампании должен назвать главный
источник решения и точный product ID, либо backend должен вернуть его как
`kind = coupon`. Это намного безопаснее, чем выбирать «самый дешёвый месяц».

## Как 232 решает, показывать ли второй экран

На основном paywall код читает `kupon` из remote config и отдельно проверяет
hard paywall. Дополнительный экран возможен, только когда:

1. remote config основного paywall действительно загрузился;
2. `kupon = true`;
3. основной paywall можно закрыть;
4. на основном paywall не было подтверждённой покупки;
5. у пользователя ещё нет активной подписки;
6. 24-часовое окно eligibility ещё не закончилось.

Если основной paywall hard, крестик заблокирован — значит перехода на
дополнительный экран нет. Если данные кампании не загрузились, приложение
закрывает ветку, а не вспоминает старое `true`.

Для нового приложения название ключа, система-источник и владелец кампании
записываются в Integration Plan. Не нужно делать `kupon` обязательным именем
для всей платформы. Неактивный эксперимент в RU-кабинете сам по себе не
отменяет Adapty-флаг — и наоборот.

## Откуда приходят продукты

232 запускает два запроса параллельно.

### Apple

Adapty placement `kupon` возвращает Apple-продукты. Они покупаются тем же
безопасным маршрутом Adapty/StoreKit, что и обычная подписка.

### СБП и карта

RU backend отдаёт каталог подписок. Reference 232 оставляет строки, у которых
`widgetTitle` после удаления пробелов и приведения к lowercase равен `kupon`.
Из строки используются:

- стабильный product ID;
- период;
- текущая цена;
- старая цена, если backend её прислал;
- тип подписки.

Для новых приложений предпочтительнее явное `kind = coupon`:

```json
{
  "products": [
    {
      "productId": "premium_offer_month_ru",
      "appStoreProductId": "premium_offer_month",
      "title": "Premium по специальной цене",
      "kind": "coupon",
      "period": "month",
      "price": 799,
      "currency": "RUB",
      "paymentMethods": ["sbp", "card"]
    }
  ]
}
```

Так разработчику и агенту не приходится знать внутреннее слово `kupon`.

## Почему не копируем выбор «лучшего» тарифа из 232

Reference 232 сортирует coupon-продукты и предпочитает год, затем неделю,
месяц и остальные варианты. Это локальная продуктовая политика, которая
случайно оказалась в коде.

Платформа делает проще:

- получает весь catalog;
- выделяет все продукты `kind = coupon`;
- сохраняет порядок и одинаковые строки;
- сопоставляет только по exact case-sensitive ID;
- показывает все разрешённые предложения;
- если приложению нужен один offer, host явно передаёт его ID.

Цена, период, название и место в массиве не являются идентификатором.

## Когда доступны СБП и карта

Coupon в каталоге ещё не включает российскую оплату. Одновременно нужны:

1. RU Billing подключён в host app;
2. свежий проверенный remote payload содержит `ru_pay = true`;
3. Storefront равен `RU/RUS` **или** регион iPhone равен `RU/RUS`;
4. coupon найден по точному ID;
5. backend разрешает checkout.

Язык, клавиатура, IP и timezone не участвуют. Если `ru_pay` отсутствует,
равен `false`, повреждён или пришёл только из кеша, СБП и карта скрываются.
Apple-вариант при этом может остаться.

Актуальное региональное правило платформы действует с 30 августа 2026 года.
Конкретный старый app мог ещё не перейти на него — перед релизом разработчик
сверяется с тимлидом.

## Почему Apple и RU-продукт должны быть совместимы

На одном экране нельзя написать «на месяц», а по Apple купить год. 232 после
параллельной загрузки сравнивает период RU и Apple. При несовпадении Apple
вариант скрывается.

Для нового приложения лучше зафиксировать явную пару:

| Поле | Пример |
|---|---|
| RU coupon product ID | `premium_offer_month_ru` |
| Apple product ID | `premium_offer_month` |
| Период | `month` |
| Что делать при несовпадении | скрыть несовместимый способ и показать причину в Debug |

Не связывайте продукты только по цене: валюты и эксперименты могут отличаться.

## Два таймера в 232

На первый взгляд кажется, что таймер один. На самом деле их два.

| Таймер | Для чего нужен | Старт | Что делает ноль |
|---|---|---|---|
| 24 часа | eligibility между показами | при первом разрешённом закрытии основного paywall | запрещает следующий показ offer |
| 10 минут | визуальная срочность открытого экрана | при каждом открытии дополнительного экрана | закрывает экран, если не идёт проверка внешней оплаты |

24-часовая дата сохраняется в `UserDefaults` reference app. 10-минутный
countdown живёт только в state текущего экрана.

Это не таймер Adapty-оффера `24:00:00 → 00:00:00 → 24:00:00`. Для RU Special
Offer платформа пока не назначает общий default. Тимлид должен отдельно
ответить:

- сколько действует eligibility;
- когда оно начинается;
- относится к установке или аккаунту;
- сколько длится экранный countdown;
- закрывает ли ноль экран;
- что делать, если пользователь вернулся из оплаты после нуля.

## Что видит пользователь

Reference 232 показывает:

1. карточку специального предложения;
2. текущую и старую цену, если старая пришла с backend;
3. период — месяц, неделя или год;
4. экранный countdown;
5. кнопку «Продолжить»;
6. выбор Apple, СБП или карты в зависимости от доступных продуктов;
7. обязательные согласия и email для чека для RU-оплаты;
8. ссылки на политику, условия и Restore.

Фраза «-50%» в 232 захардкожена в конкретном UI. Платформа не должна обещать
эту скидку без данных backend или app-owned copy.

## Как проходит оплата картой или СБП

```text
точный RU coupon product ID
  → POST checkout текущего backend
  → HTTPS payment URL
  → Safari
  → пользователь возвращается в app
  → синхронизация подписки
  → новая effective policy / entitlement проверка
  → active открывает Premium
```

232 передаёт в checkout именно resolved product ID из каталога. Он не заменяет
его на похожий App Store SKU и не пересобирает из периода.

Возврат из Safari не является оплатой. Пользователь мог закрыть форму,
остановиться на 3-D Secure или заплатить, пока webhook ещё идёт. Поэтому 232
ограниченно повторяет проверку backend и только `active` считает успехом.

При timeout результат остаётся неизвестным. Можно повторить проверку, но нельзя
автоматически создать второй checkout: пользователь рискует заплатить дважды.

## Что делает платформа, а что приложение

| Платформа | Конкретное приложение |
|---|---|
| модели RU catalog и `kind = coupon` | адрес backend и авторизация |
| сохранение всего массива | campaign key и владелец rollout |
| exact ID mapping | точный coupon product ID, если нужен один |
| strict `ru_pay` + Storefront/region gate | eligibility и countdown policy |
| общий checkout/pending/reconciliation | тексты, иллюстрация, скидка и цвета |
| authoritative entitlement refresh | связь Apple/RU продуктов и analytics naming |

Отдельные `BroadRUBillingSpecialOffer` или новый entitlement engine не нужны.
Всё собирается внутри существующего BroadMonetization.

## Пошагово для разработчика

1. Выпишите App Store ID, Release bundle ID и все product ID приложения.
2. В кабинете найдите запись, где совпадают immutable app ID, точные product ID
   и campaign binding. Не выбирайте по display name.
3. Уточните у владельца кампании: какая система является главным gate, активна
   ли она сейчас, какой rollout и какой exact coupon product ID используется.
4. Сверьте recurring/one-time mode, actual payment route, entitlement duration,
   cancellation и legal copy. Противоречие блокирует rollout.
5. Получите endpoint, JSON, единицу цены и способ авторизации текущего backend.
6. Если backend умеет `kind = coupon`, используйте готовый decoder. Если отдаёт
   legacy `widgetTitle = kupon`, напишите маленький app-owned decoder.
7. Сохраните весь coupon-массив. Не сортируйте и не оставляйте «лучший» тариф
   без явного продуктового решения.
8. Настройте Apple placement и правило совместимости периода.
9. Запишите отдельно campaign gate, strict RU gate, eligibility и countdown.
10. Перед внешним checkout ещё раз проверьте `ru_pay`, Storefront/регион и exact
   product ID.
11. Откройте только HTTPS payment URL и сохраните pending operation.
12. После возврата запросите policy/entitlement. Только `active` открывает
   Premium.
13. Вручную проверьте безопасные ветки без реальной оплаты.

## Безопасная ручная проверка

Проверка не совершает настоящий платёж:

1. Главный campaign gate false/unknown — второй экран не появляется; статус
   вспомогательного dashboard не подменяет главный gate.
2. Кампания active, `ru_pay` false — второй экран может показать только Apple.
3. `ru_pay` true, оба региональных сигнала non-RU — только Apple.
4. Storefront RU или регион iPhone RU — RU-способ появляется при точном coupon.
5. Coupon-массив содержит 0, 1 и несколько строк — UI остаётся понятным.
6. Почти одинаковый ID с другим регистром не совпадает.
7. Apple и RU периоды отличаются — несовместимый способ скрыт.
8. Backend catalog недоступен — Apple не блокируется, если его продукт загружен.
9. Возврат из mock payment URL без `active` не открывает Premium.
10. Pending/timeout показывает проверку и не создаёт новый checkout.
11. Ноль countdown не обрывает незавершённую reconciliation внешней оплаты.
12. Restore/покупка на первом paywall обходят дополнительный экран.

   а не по display name. Ничего в кабинете не меняй.

   подменяй Adapty-флаг статусом эксперимента другого кабинета.

   cancellation и legal copy. Противоречие пометь BLOCKED.
5. Найди RU catalog method/path, authorization dependency, JSON и price units.
6. Определи coupon marker: kind=coupon или подтверждённое legacy-поле.

- выбор dashboard app по похожему имени;
