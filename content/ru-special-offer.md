# RU Billing: спешл оффер

Это один из сценариев **монетизации**. После закрытия основного экрана подписки
приложение может показать специальное предложение и разрешить оплату через
Apple, СБП или банковскую карту.

Разработчик отвечает за поведение приложения. Настройки платёжного кабинета,
кампании и продуктов готовит ответственная команда. **Разработчику не нужно
искать приложение в кабинете или угадывать его настройки.** До начала работы он
получает подтверждённые значения и использует их в app-side flow.

Главное правило: **разрешение показать предложение, доступность RU-оплаты и
успешная покупка — три отдельные проверки**.

## Что должны сообщить разработчику до начала работы

Заполните эту таблицу в плане приложения. Если обязательного ответа нет,
остановитесь и задайте вопрос тимлиду — не подставляйте значение из другого
приложения.

| Что нужно получить | Пример формата | Для чего это нужно в коде |
|---|---|---|
| источник решения о показе | Adapty remote config | понять, откуда читать разрешение |
| точный ключ и разрешающее значение | `special_offer_ru = true` | не придумывать имя флага |
| RU product ID специального предложения | `premium_offer_month_ru` | отправить правильный продукт в checkout |
| Apple product ID, если Apple тоже доступен | `premium_offer_month` | показать совместимый вариант Apple |
| период обоих продуктов | `month` | не продавать год под текстом «на месяц» |
| тип покупки | разовая или с автопродлением | показать правильный текст и правила отмены |
| срок Premium | 30 дней, год или другой срок | правильно обновить доступ после оплаты |
| способы оплаты | Apple, СБП, карта | не показывать неработающие кнопки |
| API-контракт backend | catalog, checkout, status/policy | загрузить продукт и подтвердить результат |
| правила двух таймеров | окно повторного показа и countdown экрана | не смешивать продуктовую логику и анимацию |
| тексты, цена, старая цена, скидка и изображения | готовая спецификация экрана | не хардкодить неподтверждённые обещания |
| события аналитики | имена показа, выбора и результата | не придумывать несовместимые события |

За полноту этого набора отвечает владелец задачи. Разработчик проверяет, что
все значения получены и не противоречат друг другу.

## Весь маршрут на одной схеме

```text
основной paywall
  ├─ покупка или Restore подтвердили Premium → закрыть paywall
  └─ пользователь закрыл экран без покупки
       ↓
проверить разрешение кампании
  ├─ false или значение не загрузилось → продолжить без второго экрана
  └─ true
       ↓
загрузить варианты специального предложения
  ├─ Adapty / StoreKit → Apple-продукт
  └─ RU backend → продукт для СБП и карты
       ↓
показать только реально доступные способы оплаты
       ↓
Apple → purchase/restore → новая проверка Premium
СБП/карта → HTTPS checkout → Safari → status/policy → новая проверка Premium
       ↓
только подтверждённый active открывает Premium
```

## Чем RU Billing-оффер отличается от Adapty-оффера

Оба сценария относятся к монетизации, но используют разные способы оплаты.

| Вопрос | Оффер только через Adapty | Оффер с RU Billing |
|---|---|---|
| Где покупает пользователь | Apple | Apple, СБП или карта |
| Откуда приходит Apple-продукт | Adapty placement | Adapty placement, если Apple разрешён |
| Откуда приходит RU-продукт | не используется | backend-каталог приложения |
| Что разрешает СБП и карту | не используется | свежий `ru_pay=true`, RU-регион и точный RU-продукт |
| Что подтверждает успех | StoreKit/Adapty и новая проверка Premium | backend status/policy и новая проверка Premium |

[Спешл оффер от Adapty](./special-offer.md) описан отдельно, потому что у него
нет внешнего RU checkout.

## Какие части уже даёт BroadMonetization

Платформа предоставляет общую безопасную механику:

- модели RU-каталога и тип продукта `coupon`;
- сохранение всех продуктов в порядке backend;
- поиск продукта по точному case-sensitive ID;
- проверку `ru_pay` и региона;
- состояния checkout: loading, pending, active, failed и unknown;
- повторную проверку Premium после внешней оплаты.

Приложение передаёт только свои подтверждённые значения:

- конфигурацию backend и авторизацию текущего пользователя;
- ключ кампании и точный RU product ID;
- Apple placement и Apple product ID, если нужен Apple;
- правила показа и таймеров;
- SwiftUI, тексты, изображения и аналитику.

Отдельная библиотека для спешл оффера не нужна: этот flow собирается внутри
существующего `BroadMonetization`.

## Когда можно показать второй экран

Проверьте условия последовательно:

1. Основной paywall можно закрыть.
2. На основном paywall не было подтверждённой покупки или Restore.
3. У пользователя ещё нет активного Premium.
4. Решение кампании успешно загрузилось.
5. Подтверждённый ключ кампании разрешает показ.
6. Окно повторного показа ещё не закончилось.
7. Загружен хотя бы один подходящий способ оплаты.

Если решение кампании не загрузилось, не используйте старое `true` из
непроверенного кеша. Без подтверждённого разрешения дополнительный экран не
появляется.

## Откуда приходят продукты

Apple и RU-каталог загружайте параллельно. Ошибка одного источника не должна
скрывать рабочий продукт другого.

### Apple

Приложение загружает подтверждённый placement Adapty и сохраняет все полученные
продукты. Нельзя оставлять только первые две карточки или выбирать продукт по
позиции в массиве.

### СБП и карта

Backend возвращает продукт специального предложения. Предпочтительный контракт
помечает его явно как `coupon`:

```json
{
  "products": [
    {
      "productId": "premium_offer_month_ru",
      "appStoreProductId": "premium_offer_month",
      "title": "Premium по специальной цене",
      "kind": "coupon",
      "period": "month",
      "price": 799,
      "oldPrice": 1299,
      "currency": "RUB",
      "paymentMethods": ["sbp", "card"]
    }
  ]
}
```

Если backend использует другое поле-маркер, приложение подключает маленький
decoder для своего подтверждённого JSON. Универсальная библиотека не должна
угадывать смысл произвольной строки.

## Как выбрать правильный продукт

Используйте только точный ID, который передали для текущего приложения:

```text
requested RU product ID
          exact equality
catalog product.productId
```

Нельзя выбирать продукт:

- по самой низкой цене;
- по периоду «месяц» или «год»;
- по названию;
- по месту в массиве;
- по похожему ID с другим регистром.

Если разрешено несколько предложений, показывайте все в порядке backend. Если
нужно одно предложение, host app передаёт один точный ID.

## Когда доступны СБП и карта

Наличие coupon в каталоге ещё не включает российскую оплату. Одновременно
нужны все условия:

```text
RU Billing подключён в приложении
AND свежий проверенный remote payload содержит ru_pay = true
AND (App Store Storefront RU/RUS OR регион iPhone RU/RUS)
AND найден точный RU product ID
AND backend разрешает checkout
AND Premium ещё не активен
```

Если `ru_pay` отсутствует, равен `false`, повреждён или получен только из
устаревшего кеша, СБП и карта скрываются. Apple-продукт при этом может остаться.

Язык, клавиатура, IP, timezone и валюта форматирования не включают RU Billing.

## Как связать Apple и RU-продукт

На одной карточке должны совпадать смысл и период предложения.

| Поле | Пример |
|---|---|
| RU product ID | `premium_offer_month_ru` |
| Apple product ID | `premium_offer_month` |
| Период | `month` |
| При несовпадении | скрыть несовместимый способ оплаты и записать причину в безопасный Debug-лог |

Не связывайте продукты только по цене: Apple и RU backend используют разные
валюты, скидки и моменты обновления данных.

## Два разных таймера

Таймеры решают разные задачи и не должны использовать одно состояние.

| Таймер | Что решает | Где хранится | Что происходит на нуле |
|---|---|---|---|
| окно повторного показа | можно ли снова открыть offer между сессиями | app-owned persistent state | следующий показ запрещён до новой разрешённой даты |
| countdown экрана | сколько времени показывать срочность на открытом экране | state текущего экрана | действие берётся из подтверждённой спецификации |

До разработки тимлид должен сообщить:

- длительность каждого таймера;
- момент старта;
- привязан ли первый таймер к установке или аккаунту;
- должен ли ноль закрывать экран;
- что делать на нуле, если уже проверяется внешняя оплата.

У платформы нет общего значения «24 часа» или «10 минут» для RU Billing. Эти
числа нельзя переносить из другого приложения.

## Что должен показать экран

Экран собирается только из подтверждённых данных:

1. заголовок и объяснение предложения;
2. текущая цена;
3. старая цена, только если её прислал backend или утвердил владелец задачи;
4. период покупки;
5. countdown, если он предусмотрен;
6. доступные способы оплаты;
7. обязательные согласия и email для чека при RU-оплате;
8. ссылки на условия, политику и Restore.

Не вычисляйте и не пишите «−50%», если скидка не пришла из подтверждённого
контракта. Текст о продлении должен точно соответствовать типу покупки:
разовая покупка не описывается как подписка с автопродлением и наоборот.

## Как проходит оплата картой или СБП

```text
точный RU product ID
  → POST checkout backend текущего приложения
  → получить только HTTPS payment URL
  → сохранить pending operation
  → открыть Safari
  → пользователь возвращается в приложение
  → запросить status/policy/entitlement
  → active открывает Premium
```

Возврат из Safari не является подтверждением оплаты. Пользователь мог закрыть
форму, остановиться на 3-D Secure или вернуться раньше webhook.

При `pending` приложение ограниченно повторяет проверку. При timeout результат
остаётся неизвестным: можно продолжить проверку, но нельзя автоматически
создавать второй checkout — иначе пользователь может заплатить дважды.

## Пошагово для разработчика

1. Получите заполненный набор входных данных из первой таблицы.
2. Запишите неизвестные значения отдельными вопросами и дождитесь ответа.
3. Подключите `BroadMonetization` к target приложения.
4. Передайте app-owned backend configuration и авторизацию.
5. Загрузите решение кампании; `false` или ошибка означают отсутствие второго экрана.
6. Параллельно загрузите Apple placement и RU-каталог.
7. Сохраните все продукты без сортировки и удаления дублей.
8. Найдите RU coupon по точному ID.
9. Проверьте совместимость периода Apple и RU-продукта.
10. Отдельно примените RU gate: `ru_pay`, Storefront/регион и backend allow.
11. Постройте экран из реально доступных способов оплаты.
12. Перед checkout повторно проверьте gate и отправьте точный backend product ID.
13. После возврата из браузера запросите новый status/policy/entitlement.
14. Откройте Premium только после `active`.
15. Проверьте безопасные ветки без настоящего платежа.

## Ручная проверка без настоящей оплаты

1. Campaign false или не загрузился — второй экран не появляется.
2. Campaign true, но оба источника продуктов недоступны — понятная ошибка или закрытие.
3. RU-каталог недоступен, Apple-продукт загружен — Apple остаётся доступен.
4. `ru_pay=false` — СБП и карта скрыты.
5. Оба региональных сигнала non-RU — СБП и карта скрыты.
6. Storefront RU или регион iPhone RU — RU-способ доступен при точном продукте.
7. Похожий product ID с другим регистром не совпадает.
8. Периоды Apple и RU не совпадают — несовместимый способ скрыт.
9. Каталог содержит 0, 1 и несколько coupon — экран остаётся понятным.
10. Возврат из mock payment URL без `active` не открывает Premium.
11. `pending` не создаёт второй checkout автоматически.
12. Покупка или Restore на основном paywall обходят дополнительный экран.

## Готовое задание для Codex или Claude

```text
Добавь RU Billing Special Offer только в текущий host app.

Сначала прочитай код приложения, AppIntegrationPlan и подтверждённый API-контракт.
Не открывай и не изменяй платёжный кабинет. Не копируй настройки, URL, product ID
или таймеры из другого приложения.

До изменений верни три блока:
1. GIVEN — какие значения уже переданы: campaign source/key, exact RU и Apple
   product IDs, периоды, тип покупки, entitlement duration, backend methods,
   payment methods, timers, UI copy и analytics.
2. MISSING — каких обязательных ответов не хватает. Сформулируй вопросы для
   разработчика/тимлида и не угадывай ответы.
3. PLAN — какие app-side файлы и существующие API BroadMonetization будут изменены.

После подтверждения:
- campaign false/unknown не показывает второй экран;
- Apple и RU catalog загружаются независимо;
- весь массив продуктов и backend order сохраняются;
- RU coupon ищется только по exact case-sensitive ID;
- RU payment требует fresh ru_pay=true и Storefront RU или регион iPhone RU;
- browser return остаётся pending;
- только authoritative active открывает Premium;
- отдельный payment engine или новый package target не создаётся.

Не выполняй настоящий purchase, restore или RU payment.
```

## Чего не должно быть в реализации

- доступа разработчика или агента к платёжному кабинету;
- выбора продукта по цене, периоду, названию или позиции;
- production URL, ключей и product IDs внутри public package;
- включения RU Billing по языку;
- одного состояния для eligibility и экранного countdown;
- Premium сразу после возврата из браузера;
- нового платёжного движка поверх `BroadMonetization`;
- неподтверждённых скидок и текста об автопродлении.
