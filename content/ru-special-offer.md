# RU Billing: спешл оффер для разработчика

Сначала полностью подключите обычный RU Billing по инструкции
[«RU Billing: карта и СБП»](./ru-billing.md): загрузите каталог, настройте
`ru_pay` и региональный gate, checkout, проверку статуса и подтверждение
Premium. Эта страница не повторяет базовую интеграцию — ниже только то, что
нужно добавить для Special Offer.

> **Главное правило.** После закрытия обычного paywall без покупки или restore
> прочитайте `special_offer` из Remote Config текущего полученного ответа
> Adapty. Точное булево `true` означает: **всегда показать Special Offer**.
> Любое другое значение означает: **не показывать Special Offer**. Других gate
> нет.

До разработки аккаунт-менеджер должен завести отдельный продукт Special Offer
в кабинете RU Billing — российской админке. Его название и технический product
ID должны совпадать с Special Offer в Adapty; ID сравнивается символ в символ
и с учётом регистра.

## Что добавляем поверх RU Billing

```text
Пользователь закрыл обычный paywall без покупки или restore
                    ↓
special_offer из текущего Adapty Remote Config
    ├─ false / нет поля / неверный тип / ошибка → главный экран приложения
    └─ true → всегда загрузить продукт Special Offer из RU Billing
                    ↓
точный product ID RU Billing == product ID Adapty
    ├─ нет совпадения → безопасная ошибка / главный экран приложения
    └─ совпал → показать Special Offer
                    ↓
Premium открыть только после подтверждённой оплаты
```

Используйте уже подключённый `BroadMonetization`; второй платёжный движок для
Special Offer не нужен.

## Что должно быть готово до кода

- обычный RU Billing уже работает по [базовой инструкции](./ru-billing.md);
- известен Adapty placement, из текущего ответа которого читается Remote Config;
- имя и тип флага зафиксированы точно: `special_offer: true`;
- отдельный продукт Special Offer создан в RU Billing;
- название и product ID Special Offer в RU Billing совпадают с Adapty;
- согласованы тексты, изображения и legal-ссылки второго экрана.

Если базовый RU Billing не подключён или продукта Special Offer нет в
российской админке, сначала исправьте это. Не копируйте значения из другого
приложения и не подставляйте обычный тариф вместо отсутствующего оффера.

## Порядок в коде

### 1. Дождитесь закрытия обычного paywall

Переходите к проверке Special Offer только когда пользователь явно закрыл
обычный paywall, purchase и restore не подтвердили Premium, а Premium ещё не
активен.

### 2. Прочитайте единственный gate

Используйте `special_offer` именно из текущего фактически полученного ответа
Adapty. Не подменяйте его локальным `Bool`, старым кешем, наличием RU-продукта
или любым другим условием.

```text
special_offer == true → всегда показать Special Offer
всё остальное         → открыть главный экран приложения
```

Не добавляйте второе условие поверх Remote Config.

### 3. Покажите локальный таймер

Таймер — независимая часть интерфейса, а не условие показа. Он работает по
жёстко заданному локальному циклу:

```text
24:00:00 → 00:00:00 → 24:00:00 → …
```

После первого показа цикл продолжается между следующими открытиями: через час
на экране около `23:00:00`. На нуле немедленно начинается новый 24-часовой
круг. Серверное время и дата окончания не используются; ноль не влияет на
доступность оффера или покупки.

### 4. Загрузите точный продукт из RU Billing

```text
Adapty Remote Config → разрешает показ
RU Billing backend   → возвращает продукт, цену и RU-способы оплаты
```

Продукт должен быть заранее создан в RU Billing как Special Offer (`coupon`,
если backend использует это поле). Сопоставляйте только по подтверждённому
product ID: `appStoreProductId`, а в простом каталоге — `productId`.

Нельзя выбирать первый продукт, самый дешёвый или похожий по названию. Если
точного совпадения нет, не показывайте подменённый оффер.

### 5. Используйте готовый платёжный маршрут

Apple purchase, СБП, карта, browser return, polling статуса и подтверждение
Premium работают так же, как в [основной статье RU Billing](./ru-billing.md).
Возврат из браузера не означает успешную оплату; Premium открывается только
после подтверждённого результата.

## Что проверить без настоящей оплаты

- `special_offer = true` → Special Offer показывается всегда;
- `false`, нет поля, неверный тип или ошибка Adapty → открывается главный экран
  приложения;
- продукт есть в RU Billing, но флаг не равен `true` → Special Offer не
  появляется;
- флаг равен `true`, но product ID отличается хотя бы одним символом → обычный
  продукт не подставляется;
- purchase или restore уже подтвердили Premium → второй экран не появляется;
- закрытие Special Offer без подтверждённой оплаты → главный экран приложения
  без Premium;
- через час после запуска локального цикла таймер показывает около `23:00:00`;
- на `00:00:00` таймер сразу начинает новый круг с `24:00:00`, а экран и кнопка
  покупки остаются доступны.

## Задание для Codex или Claude

```text
Сначала подключи обычный RU Billing строго по статье «RU Billing: карта и СБП».
Не дублируй его checkout, status polling и подтверждение Premium.

После закрытия обычного paywall без покупки или restore прочитай special_offer
из Remote Config текущего ответа Adapty. Только точное булево true всегда
показывает второй экран. При любом другом значении не показывай его и открой
главный экран приложения. Не добавляй другие gate.

Таймер реализуй отдельно как локальный визуальный цикл
24:00:00 → 00:00:00 → 24:00:00. Запусти цикл при первом показе и продолжай его
между следующими открытиями, поэтому через час должно остаться примерно 23
часа. Не используй серверное время или дату окончания. Ноль не скрывает оффер
и не блокирует покупку.

При true загрузи отдельный продукт Special Offer из RU Billing. Он должен быть
заранее создан в российской админке, а его название и product ID должны
совпадать с Adapty. Не выбирай продукт по цене, позиции или похожему названию.

Используй существующий BroadMonetization. Возврат из браузера не считай
оплатой. Premium открывай только после подтверждённого результата. Настоящий
платёж не выполняй.
```
