# Запуск, ошибки и восстановление

Надёжное приложение отвечает на три вопроса: **что сейчас происходит, что осталось доступно и что можно сделать дальше**. Медленная сеть не должна оставлять бесконечную загрузку. Ошибка обновления не обязана стирать уже показанный список. Неизвестный результат оплаты нельзя превращать в новую покупку.

На этой странице — отдельные правила для запуска, обычных данных и финансовых операций. Их нельзя заменить одним общим `isLoading` или одной кнопкой Retry.

## Посмотрите состояния на работающем примере

В [BroadStart](./getting-started.md) можно открыть список, получить пустой ответ и ошибку, затем повторить загрузку. Это локальные учебные сценарии, без сети и финансовых операций. Три состояния ниже записаны на iPhone Simulator и показаны рядом для сравнения.

![Ответ пустой: объяснение вместо бесконечной загрузки](../public/guides/start/app-empty.png)
![Ошибка: понятный текст и действие для повторной загрузки](../public/guides/start/app-error.png)

Скачайте [проект BroadStart](../public/downloads/BroadStart.zip), откройте его в Xcode и попробуйте кнопки «Пусто», «Ошибка» и «Список». Если вызвать ошибку после успешной загрузки, пример сохранит прежние материалы и покажет сообщение рядом с ними.

## Сначала разделите три вида состояния

| Что описываем | Тип платформы | На какой вопрос отвечает |
|---|---|---|
| Запуск общих сервисов | `AppBootstrapState` | Можно ли уже открыть безопасный первый экран? |
| Содержимое конкретного экрана | `LoadableState<Value>` | Есть ли данные, идёт ли обновление и что показать при ошибке? |
| Свежесть записи в хранилище | `CacheReadResult<Value>` | Данные свежие, устаревшие или отсутствуют? |

Сбой фоновой аналитики может сделать запуск `degraded`, но не превращает загруженный список в устаревший. Устаревший кеш, наоборот, не всегда допустимо показывать: это решает сценарий, которому принадлежат данные.

## Что должно происходить при запуске

Приложение один раз создаёт сервисы в [точке сборки зависимостей](./architecture.md). Затем Core выполняет переданные ему шаги запуска. Он не знает, какие ключи, серверы и экраны нужны конкретному продукту.

**Критические шаги** выполняются последовательно. Без них нельзя безопасно выбрать первый маршрут. **Фоновые шаги** запускаются после завершения критической части и не удерживают loader. Координатор сообщает готовность, а фактическое отображение первого экрана выполняет приложение: Core не ждёт подтверждения от нарисованного SwiftUI-окна.

| Возможный шаг | Как принять решение |
|---|---|
| Прочитать локальный прогресс onboarding | Нужен для выбора маршрута; обработать повреждённую запись |
| Восстановить текущий app account | Нужен до чтения данных, привязанных к этому аккаунту |
| Активировать используемый SDK | Если без него нельзя выполнить следующий сценарий — ограниченный критический шаг; не создавать SDK повторно |
| Заранее загрузить необязательную картинку или аналитику | Фоновый шаг, если отсутствие результата не мешает первому экрану |
| ATT, отзыв, саппорт-чат | Не шаг bootstrap; выполняется в своём пользовательском контексте |

Не отмечайте всё критическим «на всякий случай». Сначала ответьте, какой безопасный экран доступен без каждого результата.

## Состояния запуска и кнопка повтора

| Состояние | Что оно означает | Что показывает приложение |
|---|---|---|
| `idle` | Запуск ещё не начался или отменён | Начальное состояние |
| `starting` | Идут критические шаги | Загрузка с конечным временем ожидания |
| `ready` | Критическая часть завершена | Первый маршрут приложения |
| `degraded` | Допустимый запасной результат или ошибка фонового шага | Рабочий экран; сообщение только о затронутой функции |
| `failed(error)` | Критический шаг не завершился, безопасного обхода нет | Причина и кнопка повтора запуска |

Публичный вызов координатора — `await bootstrap()`. Повторный вызов во время запуска присоединяется к текущему выполнению. `await bootstrap.retry()` создаёт новый запуск из `failed`; это не универсальная команда заново активировать все сервисы из любого состояния.

Поздний ответ предыдущего запуска не должен переписывать новый результат. Координатор различает поколения запуска и отбрасывает такие ответы. [Полный контракт bootstrap](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Documentation/Bootstrap.md).

## Как ограничить ожидание и повторы

В примере ниже приложение передаёт настоящую операцию чтения настройки через `loadConfiguration`. Функция только собирает координатор: она не создаёт сеть и не подставляет выдуманный успешный ответ. Размещайте её в точке сборки зависимостей.

```swift
import BroadCore

func makeBootstrap(
    loadConfiguration: @escaping BootstrapStep.Operation
) -> AppBootstrapCoordinator {
    let step = BootstrapStep(
        id: BootstrapStepID(rawValue: "app-configuration"),
        name: "Настройка приложения",
        criticality: .critical,
        timeoutPolicy: .seconds(6),
        retryPolicy: .fixed(retryCount: 2, delay: 0.3),
        operation: loadConfiguration
    )

    return AppBootstrapCoordinator(
        steps: [step],
        errorMessages: BootstrapErrorMessages(
            timeout: "Подготовка заняла слишком много времени. Повторите попытку.",
            unknown: "Не удалось подготовить приложение. Повторите попытку."
        )
    )
}
```

Здесь 6 секунд — **общее время шага**, включая все попытки и паузы, а не 6 секунд на каждую попытку. `retryCount: 2` означает максимум три попытки: первую и два повтора. Значения выбраны для объяснения; у реального действия должен быть согласованный срок ожидания.

Повтор выполняется только для подходящей ошибки с `isRetryable == true`. Для неидемпотентного действия — такого, которое при повторе может ещё раз что-то изменить, — автоматические повторы нельзя включать по аналогии с чтением. Активации SDK обычно нужен `.none` и собственная защита от повторного запуска.

Timeout прекращает ожидание результата. Он не гарантирует, что внешняя система остановила работу. Swift не может насильно отменить SDK, который не поддерживает отмену.

## Как экран сообщает о состоянии данных

| LoadableState | Что увидит человек | Доступное действие |
|---|---|---|
| `idle` | Начальное состояние | Начать загрузку по сценарию |
| `loading(previousValue: nil)` | Первая загрузка | Повторный запуск заблокирован |
| `loading(previousValue: value)` | Прежний список и индикатор обновления | Можно читать разрешённый контент |
| `loaded(value)` | Актуальные данные | Обычные действия экрана |
| `empty` | Ответ получен, элементов нет | Подходящее действие: создать, изменить фильтр или вернуться |
| `stale(value:error:)` | Разрешённые старые данные с пояснением | Повторить чтение |
| `error(error:previousValue:)` | Ошибка; прежние данные только по явному решению UI | Безопасный повтор или выход |

Успешный пустой массив не является ошибкой сети. Сам `LoadableState.loaded([])` не превратится в `.empty`: вызывающий код должен выбрать состояние. В BroadStart это делает [LessonListModel](https://github.com/BroadApps-official/broad-docs/blob/main/examples/first-app/Sources/LessonListModel.swift).

При обновлении не заменяйте весь список полноэкранным loader, если старый контент можно продолжать читать. Сохраните ту же ветку списка в SwiftUI, его идентичность и позицию прокрутки. Иначе даже правильно сохранённые данные могут визуально исчезать и появляться заново.

## Защита от двойного нажатия начинается до Task

Проверка «запрос уже идёт» и перевод в загрузку должны выполняться синхронно на `MainActor`, до создания `Task` и первого `await`. Иначе два быстрых нажатия успеют создать две задачи.

В BroadStart перед `Task` стоят эти строки. Это фрагмент метода `load`; полный метод по ссылке выше также обрабатывает результат, отмену и ошибку.

```swift
guard !state.isLoading else { return }
let previousState = state
let previousValue = state.value
state = state.beginLoading()
```

У бизнес-действий есть и второй уровень защиты: общий сервис не должен позволять двум разным экранам одновременно начать одну финансовую операцию. Блокировка одной кнопки не заменяет общий `MonetizationOperationGate`.

## Что делать с кешем

Кеш — сохранённая копия данных. У него есть срок свежести (TTL), версия формата и область владельца: например, текущий аккаунт и placement. Нельзя показать данные одного аккаунта после переключения на другой.

| Данные | Что допустимо | Что нельзя выводить из кеша |
|---|---|---|
| Учебные материалы или другой безопасный список | Показать старую копию с пояснением, если это разрешает продукт | Что обновление прошло успешно |
| Каталог обычного paywall | Показать пригодные сохранённые данные; перед покупкой заново сверить исходный продукт и его условия | Что продукт уже куплен или старые условия всё ещё действуют |
| Remote Config из постоянного кеша платформы | Использовать только разрешённые данные для отображения | Разрешение `special_offer` или `ru_pay` |
| Ранее подтверждённый доступ | Доверить решение Entitlement Engine с его сроками и привязкой к пользователю | Произвольное бессрочное `isPremium = true` в UserDefaults |
| Баланс токенов | Показать допустимый снимок с корректным состоянием обновления | Начислить или списать токены без серверного результата |

Важно различать постоянный кеш платформы и текущий ответ Adapty, который может использовать внутренний кеш SDK. Последний может разрешать Special Offer; обычный `ru_pay` требует подтверждённого свежего ответа. При недоступном Adapty есть отдельно подключаемый [резерв с серверным каталогом](./ru-billing.md): российский Storefront или регион iPhone, без обхода полученного `false`. Кеш не восстанавливает это разрешение. [Контракты кеша](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Documentation/CachingAndOffline.md).

У Entitlement Engine есть специальное ограниченное продолжение ранее подтверждённого `active` без сети — **offline grace**. Оно действует только в рамках настроенной политики, того же пользователя и срока права. Это не новая покупка и не возможность UI самостоятельно продлевать доступ. Просроченный `inactive` такого продления не получает. [Правила проверки доступа](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Documentation/Entitlements.md).

## Если сеть пропала во время оплаты

Время ожидания закончилось — приложение не знает результат. Сервер или Apple могли успеть завершить операцию. Поэтому следующий шаг — **проверка той же операции**, а не создание новой.

| Момент сбоя | Правильное продолжение |
|---|---|
| Чтение каталога | Повторить чтение с ограничением времени; использовать допустимый кеш |
| Покупка или restore ещё не дали определённого результата | Сохранить ожидание и выяснить результат прежней операции |
| Возврат из банковского приложения | Запросить серверный статус; сам возврат не доказывает оплату |
| Сервер не ответил на начисление токенов | Сверить результат по идентификатору операции и баланс аккаунта |
| Неясен результат отмены подписки | Перечитать статус; новую отмену не отправлять автоматически |
| Появилась сеть | Запустить разрешённую сверку, не повторную покупку или списание |

Кнопку в неопределённом финансовом состоянии называйте по действию: «Проверить статус». Общий Retry допустим для чтения, но не должен скрыто означать повторное списание. [Обрыв сети и восстановление операции](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Documentation/NetworkInterruptions.md).

## После перезапуска, смены аккаунта и переустановки

При обычном перезапуске приложение может прочитать сохранённую незавершённую операцию и продолжить её сверку. Это не даёт права создавать новый платёж автоматически.

После смены аккаунта старые кеш, callbacks и операции не должны менять состояние нового пользователя. Сначала установите текущую идентичность, затем загружайте её данные. При выходе не стирайте историю незавершённой оплаты без предусмотренного доменного решения.

После переустановки нельзя рассчитывать на локальные записи как на источник покупок. Подписки Apple восстанавливаются через StoreKit и серверные источники, токены и RU-покупки — через backend того же app account. Transaction ID нужен для однократного учёта операции; он не заменяет вход в аккаунт при обычном восстановлении. [Account Recovery](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Documentation/AccountRecovery.md).

Подробности сохранения ID, миграции, задержки iCloud и защиты от повторной выдачи
лимитов — в статье [Keychain: аккаунт и восстановление](./keychain-account-recovery.md).

## Ошибка для человека и данные для диагностики

Сообщение должно объяснять, что не получилось и что доступно дальше: «Не удалось обновить список. Сохранённые материалы доступны». Не показывайте raw JSON, receipt, токен, платёжный URL или полный SDK error.

`AppError` содержит тип, безопасный текст, очищенный диагностический код и признак возможного повтора. `CancellationError` обычно означает завершение задачи по жизненному циклу и не должна появляться как авария приложения.

В BroadStart отмена возвращает предыдущее состояние. В собственном сценарии явно определите, что делать при уходе с экрана; незавершённая покупка должна жить в общем сервисе, а не теряться вместе с ViewModel. [Безопасные логи](https://github.com/BroadApps-official/broad-platform-integration/blob/main/Documentation/Logging.md).

## Как проверить поведение

В локальном примере воспроизведите: медленную первую загрузку, пустой ответ, ошибку без данных, ошибку обновления с данными, быстрый двойной тап и уход с экрана. Для каждого случая проверьте видимое состояние, доступное действие и отсутствие второго запроса.

Отдельно проверьте поздний ответ после timeout, смену аккаунта и перезапуск с незавершённой операцией. Для финансовых случаев используйте предусмотренные платформой подставные ответы и исполняемые примеры, без настоящей покупки, restore и RU-платежа. Успешная проверка таких сценариев подтверждает логику обработки; она не доказывает работу production backend вашего приложения.
